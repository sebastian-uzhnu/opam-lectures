# Наслідування: побудова ієрархій класів

У темі 15 ми навчилися писати один клас якісно: приватні поля, властивості
з валідацією, конструктори, статичні члени. Тепер настав час навчитися писати
**кілька пов'язаних класів** так, щоб не переписувати той самий код по колу.

Механізм, який це дозволяє, називається **наслідуванням** (inheritance).
Це другий із чотирьох принципів ООП, який ми оглядово бачили в темі 14.
Зараз розберемо його докладно.

## Проблема: три класи, які майже однакові

Уявіть, що ви пишете систему обліку для коледжу. У ній є три види людей:
студент, викладач і адміністратор. Почнімо чесно: напишемо три класи.

```csharp
class Student
{
    public string Name { get; set; } = "";
    public int Age { get; set; }
    public string Email { get; set; } = "";
    public string Phone { get; set; } = "";

    public string Group { get; set; } = "";
    public double AverageGrade { get; set; }

    public void Introduce()
    {
        Console.WriteLine($"{Name}, {Age} років, {Email}");
    }
}

class Teacher
{
    public string Name { get; set; } = "";
    public int Age { get; set; }
    public string Email { get; set; } = "";
    public string Phone { get; set; } = "";

    public string Subject { get; set; } = "";
    public int ExperienceYears { get; set; }

    public void Introduce()
    {
        Console.WriteLine($"{Name}, {Age} років, {Email}");
    }
}

class Admin
{
    public string Name { get; set; } = "";
    public int Age { get; set; }
    public string Email { get; set; } = "";
    public string Phone { get; set; } = "";

    public string Department { get; set; } = "";

    public void Introduce()
    {
        Console.WriteLine($"{Name}, {Age} років, {Email}");
    }
}
```

Подивіться уважно. Чотири властивості й один метод повторюються **тричі**,
слово в слово. Це не просто некрасиво — це джерело майбутнього болю.

### Чому дублювання коду боляче

Уявімо чотири звичайні ситуації з життя проєкту.

**Ситуація 1. Треба додати дату народження.** Ви йдете й додаєте властивість
`BirthDate` у `Student`. Потім у `Teacher`. Потім… забуваєте про `Admin`.
Через тиждень хтось знаходить баг: «у адміністраторів не показується вік».

**Ситуація 2. Треба виправити помилку в `Introduce`.** Ви помітили, що
телефон не виводиться. Виправляєте в одному місці, тестуєте, комітите.
У двох інших класах помилка залишилася.

**Ситуація 3. Треба перевіряти email на наявність символу «собачка».**
Валідацію треба написати тричі. І тричі підтримувати.

**Ситуація 4. Треба скласти загальний список усіх людей у коледжі.**
І ось тут дублювання стає не просто незручністю, а **стіною**. Ви не можете
написати `Student[]`, бо там є ще й викладачі. Не можете написати `Teacher[]`.
Спільного типу немає, тому спільного списку теж немає.

:::info Цікаво
Правило, яке порушує цей код, називається **DRY** — Don't Repeat Yourself,
«не повторюйся». Сформулював його Енді Гант у книзі «The Pragmatic Programmer»
1999 року так: кожен фрагмент знання в системі повинен мати єдине,
однозначне представлення. Наслідування — один із головних інструментів,
якими мова C# допомагає це правило дотримати.
:::

## Розв'язок: базовий клас

Помітимо очевидне: студент, викладач і адміністратор — це все **люди**.
У них спільне те, що властиве людині: ім'я, вік, контакти. А відрізняються
вони тим, що властиве їхній ролі: група, предмет, відділ.

Винесімо спільне в окремий клас `Person`:

```csharp
class Person
{
    public string Name { get; set; } = "";
    public int Age { get; set; }
    public string Email { get; set; } = "";
    public string Phone { get; set; } = "";

    public void Introduce()
    {
        Console.WriteLine($"{Name}, {Age} років, {Email}, тел. {Phone}");
    }
}
```

А тепер — найголовніший синтаксис теми. Двокрапка після назви класу означає
«цей клас успадковує той»:

```csharp
class Student : Person
{
    public string Group { get; set; } = "";
    public double AverageGrade { get; set; }
}

class Teacher : Person
{
    public string Subject { get; set; } = "";
    public int ExperienceYears { get; set; }
}

class Admin : Person
{
    public string Department { get; set; } = "";
}
```

Три класи, у кожному — тільки те, що робить його особливим. Жодного
дублювання. І при цьому студент **має всі члени** `Person`:

```csharp
var student = new Student
{
    Name = "Олена Кравчук",
    Age = 17,
    Email = "o.kravchuk@college.ua",
    Phone = "+380671234567",
    Group = "ПЗ-21",
    AverageGrade = 4.7
};

student.Introduce();                          // метод з Person
Console.WriteLine($"Група: {student.Group}"); // властивість з Student
```

**Вивід:**

```
Олена Кравчук, 17 років, o.kravchuk@college.ua, тел. +380671234567
Група: ПЗ-21
```

Зверніть увагу: у класі `Student` немає ні поля `Name`, ні методу `Introduce`.
Але об'єкт `Student` ними користується так, ніби вони його власні. Бо вони
і є його власні — успадковані.

## Термінологія

Ці слова треба знати напам'ять, бо ними користуються всі й усюди.

| Термін | Синоніми | Що це в нашому прикладі |
|---|---|---|
| **Базовий клас** | батьківський, предок, superclass | `Person` |
| **Похідний клас** | дочірній, нащадок, subclass | `Student`, `Teacher`, `Admin` |
| **Ієрархія класів** | дерево наслідування | `Person` і три його нащадки разом |

Похідний клас **розширює** (extends) базовий: він завжди має щонайменше
стільки ж членів, скільки базовий, і зазвичай більше. Тому вислів «похідний
клас — це урізана версія базового» — груба помилка, все навпаки.

## Що успадковується, а що ні

Похідний клас отримує від базового майже все, але не все.

| Член базового класу | Успадковується? | Примітка |
|---|---|---|
| Публічні поля й властивості | так | доступні напряму |
| `protected` члени | так | доступні всередині нащадка |
| Публічні й `protected` методи | так | можна викликати й перевизначати |
| `private` члени | формально ні | існують в об'єкті, але нащадок їх не бачить |
| Статичні члени | так | але вони спільні для всієї ієрархії |
| **Конструктори** | **ні** | це найважливіший виняток |
| Деструктор (фіналізатор) | ні | генерується автоматично |

Пункт про приватні члени варто пояснити точніше. Коли ви створюєте об'єкт
`Student`, у пам'яті виділяється місце **під усі поля**, зокрема й під
приватні поля `Person`. Вони фізично там є, об'єкт без них працювати
не зможе. Просто код класу `Student` не має права до них звертатися —
компілятор не дозволить. Це і є інкапсуляція: `Person` захищає свої нутрощі
навіть від власних нащадків.

:::danger Часта помилка
**Конструктори не успадковуються.** Якщо в `Person` є конструктор
`Person(string name, int age)`, то написати `new Student("Олена", 17)`
не вийде — у `Student` такого конструктора немає, і компілятор про це скаже.
Конструктори треба оголошувати в кожному класі заново. Як при цьому не
дублювати код — читайте нижче про `base`.
:::

## Ключове слово `base`

Слово **base** — це посилання на «батьківську частину» поточного об'єкта.
Воно має два застосування, і обидва вам знадобляться постійно.

### Застосування 1. Виклик конструктора базового класу

Додамо в `Person` нормальний конструктор:

```csharp
class Person
{
    public string Name { get; }
    public int Age { get; }
    public string Email { get; set; } = "";

    public Person(string name, int age)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Ім'я не може бути порожнім.");
        if (age < 0 || age > 120)
            throw new ArgumentException("Некоректний вік.");

        Name = name;
        Age = age;
    }

    public void Introduce()
    {
        Console.WriteLine($"{Name}, {Age} років");
    }
}
```

Тепер у конструкторі `Student` ми не хочемо переписувати цю валідацію.
Замість цього передамо роботу батьківському конструктору через `: base(...)`:

```csharp
class Student : Person
{
    public string Group { get; }
    public double AverageGrade { get; set; }

    public Student(string name, int age, string group)
        : base(name, age)          // спочатку відпрацює конструктор Person
    {
        if (string.IsNullOrWhiteSpace(group))
            throw new ArgumentException("Група не може бути порожньою.");

        Group = group;
    }
}
```

Синтаксис `: base(аргументи)` пишеться після списку параметрів конструктора,
перед відкриваючою фігурною дужкою. Він означає: «перш ніж виконувати моє
тіло, виконай конструктор базового класу з такими аргументами».

Це схоже на `: this(...)` з теми 15, тільки `this` делегує іншому конструктору
**того самого** класу, а `base` — конструктору **батьківського** класу.

:::warning Обережно
Якщо базовий клас має **лише** конструктор з параметрами, а ви в похідному
не написали `: base(...)`, компілятор видасть помилку:

```
CS7036: There is no argument given that corresponds to the required
parameter 'name' of 'Person.Person(string, int)'
```

Причина: коли `: base(...)` не написано явно, компілятор дописує `: base()`
сам — а конструктора без параметрів у `Person` немає. Розв'язок один:
написати `: base(...)` з потрібними аргументами.
:::

### Застосування 2. Виклик методу базового класу

Друге застосування `base` — звернутися до реалізації методу з батьківського
класу зсередини нащадка. Це знадобиться нам у наступному підрозділі, коли
вивчимо перевизначення, але синтаксис виглядає так:

```csharp
class Student : Person
{
    // ...

    public void IntroduceFull()
    {
        base.Introduce();                              // те, що вміє Person
        Console.WriteLine($"Група {Group}, середній бал {AverageGrade}");
    }
}
```

## Порядок виклику конструкторів

Це улюблене питання на екзамені, і воно не випадкове: розуміння цього порядку
рятує від дуже неприємних багів.

Правило одне: **конструктори виконуються знизу вгору за викликом і згори вниз
за виконанням тіла**. Тобто спочатку до кінця відпрацьовує найдальший предок,
потім його нащадок, і так до самого вашого класу.

Перевірмо на трирівневій ієрархії:

```csharp
class Person
{
    public Person()
    {
        Console.WriteLine("1. Конструктор Person");
    }
}

class Student : Person
{
    public Student()
    {
        Console.WriteLine("2. Конструктор Student");
    }
}

class GraduateStudent : Student
{
    public GraduateStudent()
    {
        Console.WriteLine("3. Конструктор GraduateStudent");
    }
}

// Головна програма
Console.WriteLine("Створюємо аспіранта...");
var grad = new GraduateStudent();
```

**Вивід:**

```
Створюємо аспіранта...
1. Конструктор Person
2. Конструктор Student
3. Конструктор GraduateStudent
```

Хоча ми написали `new GraduateStudent()`, першим виконався конструктор
найдальшого предка. Схематично:

```
new GraduateStudent()
        │
        │  крок 1: керування піднімається вгору ланцюжком
        ▼
  GraduateStudent()  ──base()──▶  Student()  ──base()──▶  Person()
                                                              │
        крок 2: тіла виконуються згори вниз                   │
        ┌─────────────────────────────────────────────────────┘
        ▼
   тіло Person()            "1. Конструктор Person"
        │
        ▼
   тіло Student()           "2. Конструктор Student"
        │
        ▼
   тіло GraduateStudent()   "3. Конструктор GraduateStudent"
        │
        ▼
   об'єкт готовий
```

Логіка тут абсолютно природна: щоб добудувати другий поверх, треба спершу
мати перший. Конструктор `Student` може покладатися на те, що поля `Person`
вже коректно заповнені — бо конструктор `Person` гарантовано відпрацював
раніше.

:::info Цікаво
Насправді порядок трохи складніший. Спочатку виконуються **ініціалізатори
полів похідного класу** (те, що ви написали прямо в оголошенні поля), потім
конструктор базового класу, і лише потім тіло конструктора похідного.
На практиці це майже ніколи не має значення, але якщо колись побачите дивну
поведінку з ініціалізаторами — згадайте цей абзац.
:::

## Модифікатор `protected`: навіщо він саме тут

У темі 15 ми познайомилися з `protected` і, чесно кажучи, він виглядав
трохи безглуздо: навіщо потрібен рівень доступу «між» приватним і публічним?
Тепер його сенс стає очевидним.

Розгляньмо ситуацію. У `Person` є приватне поле-лічильник спроб входу,
до якого нащадкам треба доступ:

```csharp
class Person
{
    private int loginAttempts;    // нащадки НЕ бачать
    protected string secretCode;  // нащадки бачать, зовнішній світ — ні

    public string Name { get; set; } = "";
}

class Student : Person
{
    public void ShowInfo()
    {
        Console.WriteLine(Name);          // OK: public
        Console.WriteLine(secretCode);    // OK: protected, ми нащадок
        // Console.WriteLine(loginAttempts);  // ПОМИЛКА: private
    }
}

class Program
{
    static void Main()
    {
        var s = new Student();
        Console.WriteLine(s.Name);        // OK
        // Console.WriteLine(s.secretCode);   // ПОМИЛКА: ми не нащадок
    }
}
```

Повна таблиця видимості — вивчіть її, вона знадобиться на кожній лабораторній:

| Модифікатор | У самому класі | У похідному класі | В іншому класі тієї ж збірки | В іншій збірці |
|---|---|---|---|---|
| `private` | так | ні | ні | ні |
| `protected` | так | так | ні | ні (крім нащадків) |
| `internal` | так | так | так | ні |
| `protected internal` | так | так | так | тільки нащадкам |
| `private protected` | так | тільки в цій збірці | ні | ні |
| `public` | так | так | так | так |

На практиці вам вистачить трьох рядків: `private`, `protected`, `public`.
Решта — для авторів бібліотек.

:::tip Порада
Правило вибору просте. Поле або метод потрібні **лише** цьому класу —
`private`. Потрібні класу і його нащадкам, але не стороннім — `protected`.
Потрібні всім — `public`, і подумайте ще раз, чи справді всім.

Не робіть поля `protected` «про всяк випадок». `protected` поле — це
такий самий публічний контракт, тільки для нащадків: змінити його тип
чи назву потім буде так само боляче.
:::

## Клас `object` — корінь усього

А тепер факт, який дивує всіх, хто чує його вперше. Подивіться на цей клас:

```csharp
class Point
{
    public int X { get; set; }
    public int Y { get; set; }
}
```

Він нічого не успадковує — принаймні так здається. Але спробуйте:

```csharp
var p = new Point { X = 3, Y = 4 };

Console.WriteLine(p.ToString());
Console.WriteLine(p.GetType());
Console.WriteLine(p.GetHashCode());
Console.WriteLine(p.Equals(p));
```

**Вивід:**

```
Point
Point
43942917
True
```

Звідки взялися ці чотири методи, якщо ми їх не писали? З класу **object**.

У C# **кожен** тип неявно успадковує від `System.Object` (псевдонім — `object`).
Якщо ви не написали двокрапку й базовий клас, компілятор дописує `: object`
за вас. Тобто `class Point` і `class Point : object` — це одне й те саме.

Через це в `object` живуть методи, які є абсолютно в кожного об'єкта в .NET:

| Метод | Що робить | Що повертає за замовчуванням |
|---|---|---|
| `ToString()` | текстове представлення об'єкта | повне ім'я типу |
| `Equals(object)` | порівняння з іншим об'єктом | для класів — порівняння посилань |
| `GetHashCode()` | числовий «відбиток» об'єкта | число на основі адреси |
| `GetType()` | інформація про тип під час виконання | об'єкт `Type` |

Метод `ToString()` за замовчуванням майже некорисний — він виводить назву
типу. Тому його майже завжди перевизначають, і саме це ми зробимо в наступному
підрозділі.

Ієрархія нашого прикладу насправді виглядає так:

```
                        object
                          │
                          │  (неявно, дописує компілятор)
                          ▼
                       Person
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
     Student           Teacher            Admin
        │
        ▼
 GraduateStudent
```

Наслідування **транзитивне**: `GraduateStudent` успадковує все від `Student`,
а через нього — все від `Person`, а через нього — все від `object`.
Об'єкт класу `GraduateStudent` є одночасно і студентом, і людиною, і об'єктом.

:::info Цікаво
Спільний корінь `object` — це не примха авторів C#. Саме завдяки йому працює
`Console.WriteLine(будь-що)`: цей метод має перевантаження, яке приймає
`object`, тобто взагалі все. Так само працюють колекції на кшталт
`List<object>` і механізм пакування значеннєвих типів (boxing).
:::

## Клас `sealed`: наслідування заборонено

Іноді автор класу хоче сказати: «від цього класу успадковувати не можна».
Для цього є модифікатор **sealed** (запечатаний):

```csharp
sealed class Admin : Person
{
    public string Department { get; set; } = "";
}

// class SuperAdmin : Admin   // ПОМИЛКА компіляції:
                              // cannot derive from sealed type 'Admin'
```

Навіщо це потрібно?

- **Безпека логіки.** Якщо клас відповідає за щось критичне (перевірка прав,
  шифрування), нащадок міг би змінити його поведінку в непередбачуваний спосіб.
- **Швидкодія.** Компілятор і JIT знають, що методи запечатаного класу
  ніхто не перевизначить, і можуть викликати їх напряму, без пошуку в таблиці
  віртуальних методів.
- **Чесність.** Проєктувати клас так, щоб від нього було безпечно успадковувати,
  насправді складно. Якщо ви цього не робили — краще чесно запечатати.

Найвідоміший `sealed` клас у .NET — це `System.String`. Спробуйте написати
`class MyString : string` і подивіться на помилку.

## Чому в C# лише одиничне наслідування

У C# клас може мати **рівно один** базовий клас. Написати
`class Student : Person, Employee` не можна.

Деякі мови (наприклад, C++) множинне наслідування дозволяють. І майже завжди
це закінчується так званою **проблемою ромба**:

```
          Device
        (метод Reset)
          ╱      ╲
         ╱        ╲
     Phone       Camera
   (Reset)       (Reset)
         ╲        ╱
          ╲      ╱
        PhoneCamera
              │
              ▼
       phoneCamera.Reset()  ← а чий саме Reset викликати?
```

Клас `PhoneCamera` успадкував `Reset` двома різними шляхами, і компілятор
не має способу вгадати, який із них ви мали на увазі. У C++ це розв'язують
складними правилами, які мало хто пам'ятає. Автори C# вирішили не давати
розробникові такої зброї.

При цьому потреба «бути кількома речами одночасно» нікуди не зникає.
Її в C# закриває інший механізм — **інтерфейси**, які можна реалізовувати
скільки завгодно. Про них — уся тема 17. Там само буде і про **абстрактні
класи** — базові класи, від яких не можна створити об'єкт, а можна лише
успадкувати.

## Коли наслідування — помилка

І тепер найважливіше в усьому підрозділі. Наслідування виглядає так зручно,
що студенти починають застосовувати його всюди, де є однаковий код.
Це помилка.

:::tip Порада
Запам'ятайте два питання:

- **Наслідування — це «є» (is-a).** Студент **є** людиною. Коло **є** фігурою.
  Менеджер **є** співробітником. Якщо речення звучить природно — наслідування
  доречне.
- **Композиція — це «має» (has-a).** Автомобіль **має** двигун. Замовлення
  **має** список товарів. Студент **має** заліковку. Тут потрібне не
  наслідування, а поле відповідного типу.
:::

Класичний приклад помилки. Студент бачить, що в класі `Engine` є корисний
метод `Start()`, і пише:

```csharp
// ТАК РОБИТИ НЕ ТРЕБА
class Car : Engine
{
    public string Model { get; set; } = "";
}
```

Формально працює: `car.Start()` викликається. Логічно — катастрофа, бо
автомобіль не є двигуном. І це одразу дасть наслідки: автомобіль
успадкує властивість `Displacement` (робочий об'єм), матиме безглузді методи
в підказках IntelliSense, а коли з'явиться потреба в другому двигуні
(гібрид) — доведеться все переписувати.

Правильно — композиція:

```csharp
class Car
{
    public string Model { get; set; } = "";
    public Engine Engine { get; }        // автомобіль МАЄ двигун

    public Car(string model, Engine engine)
    {
        Model = model;
        Engine = engine;
    }

    public void Start() => Engine.Start();   // делегуємо
}
```

Ще одна поширена помилка тієї самої природи: `class Stack : List<T>`.
Стек не є списком: у списку можна вставити елемент у середину, а в стеку —
ні. Успадкувавши список, ви віддали назовні методи, які ламають правила стеку.

## Типові помилки

**1. Забути `: base(...)` при конструкторі з параметрами.**
Компілятор скаржиться на «no argument given». Це не про ваш конструктор,
а про батьківський — допишіть `: base(name, age)`.

**2. Робити всі поля `protected` «щоб нащадкам було зручно».**
`protected` — це теж публічний контракт. Спочатку `private`, і підвищуйте
до `protected` лише тоді, коли конкретному нащадку справді знадобилося.

**3. Наслідувати заради повторного використання коду.**
«У цих класів є однаковий метод, зроблю базовий клас» — недостатня причина.
Спершу перевірте речення «А є Б». Якщо воно звучить дивно, вам потрібна
композиція або звичайний допоміжний клас.

**4. Будувати ієрархію на п'ять поверхів.**
`Object` → `Entity` → `Person` → `Employee` → `Manager` → `SeniorManager`.
Щоб зрозуміти, що вміє об'єкт, доводиться відкривати п'ять файлів.
Практичне правило: два-три рівні — норма, більше — привід зупинитися
й подумати про композицію.
