# Поліморфізм

**Поліморфізм** (від грецьких _polys_ — багато і _morphe_ — форма) — це
здатність одного й того самого інтерфейсу мати різні реалізації. Простіше:
**один виклик — багато різних поведінок**.

Ви вже користувалися поліморфізмом, навіть не знаючи цього слова.
`Console.WriteLine(5)`, `Console.WriteLine("текст")`, `Console.WriteLine(3.14)` —
назва методу одна, а працює він щоразу інакше. І `person.Introduce()`
з минулого підрозділу, який виводив різне для студента й викладача, — теж
поліморфізм.

У C# є два різновиди поліморфізму, і вони працюють у різні моменти часу.

| Вид | Інша назва | Коли вирішується | Механізм |
|---|---|---|---|
| **Статичний** | compile-time, ad hoc | під час компіляції | перевантаження методів і операторів |
| **Динамічний** | runtime, subtype | під час виконання | `virtual` / `override` |

Почнемо з простішого.

## Статичний поліморфізм

### Перевантаження методів

**Перевантаження** (overloading) — це кілька методів з однаковою назвою
в одному класі, які відрізняються **списком параметрів**. Ми вже робили
так з конструкторами в темі 15.

```csharp
class Calculator
{
    public int Add(int a, int b) => a + b;

    public double Add(double a, double b) => a + b;

    public int Add(int a, int b, int c) => a + b + c;

    public string Add(string a, string b) => a + b;
}
```

```csharp
var calc = new Calculator();

Console.WriteLine(calc.Add(2, 3));           // int, int
Console.WriteLine(calc.Add(2.5, 3.1));       // double, double
Console.WriteLine(calc.Add(1, 2, 3));        // три int
Console.WriteLine(calc.Add("ПЗ-", "21"));    // string, string
```

**Вивід:**

```
5
5,6
6
ПЗ-21
```

Який саме `Add` викликати, компілятор вирішує **під час компіляції**,
дивлячись на типи аргументів. У скомпільованій програмі на місці кожного
виклику вже стоїть конкретний метод. Саме тому це «статичний» поліморфізм.

Перевантаження відрізняються за:

- кількістю параметрів;
- типами параметрів;
- порядком типів параметрів.

І **не** відрізняються за типом повернення. Ці два методи не скомпілюються
разом:

```csharp
public int GetValue() => 5;
public double GetValue() => 5.0;   // ПОМИЛКА CS0111
```

Причина проста: у виклику `var x = GetValue();` компілятор не зміг би вгадати,
який метод ви мали на увазі.

:::warning[Обережно]
Не плутайте **перевантаження** (overloading) і **перевизначення** (overriding).
Слова схожі, а сенс різний:

- перевантаження — кілька методів з однією назвою і **різними параметрами**
  в **одному** класі;
- перевизначення — метод з **тією самою сигнатурою** у **похідному** класі,
  який замінює батьківський.
:::

### Перевантаження операторів

C# дозволяє навчити ваш власний клас працювати зі звичними операторами
`+`, `-`, `==` тощо. Коротко подивімося, як це виглядає, на класі грошей:

```csharp
class Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }

    // Перевантаження оператора додавання
    public static Money operator +(Money a, Money b)
    {
        if (a.Currency != b.Currency)
            throw new InvalidOperationException("Різні валюти не додаються.");

        return new Money(a.Amount + b.Amount, a.Currency);
    }

    // Множення суми на число
    public static Money operator *(Money m, int times)
        => new Money(m.Amount * times, m.Currency);

    public override string ToString() => $"{Amount:N2} {Currency}";
}
```

```csharp
var lunch = new Money(180m, "грн");
var coffee = new Money(65m, "грн");

Console.WriteLine(lunch + coffee);
Console.WriteLine(coffee * 5);
```

**Вивід:**

```
245,00 грн
325,00 грн
```

Оператор — це просто статичний метод з особливою назвою. Тому це теж
статичний поліморфізм: який саме `+` викликати, компілятор бачить одразу.

:::tip[Порада]
Перевантажуйте оператори тільки там, де їхній сенс **очевидний** усім:
гроші, вектори, дроби, дати, комплексні числа. Оператор `+` для класу
`Student` («додати студента до студента») зробить код загадковим,
а не коротким.
:::

## Динамічний поліморфізм — головна ідея теми

Тепер найважливіше. Динамічний поліморфізм дозволяє писати код, який працює
з **базовим** типом і при цьому автоматично викликає правильну реалізацію
кожного нащадка.

Класичний приклад цієї теми — геометричні фігури.

### Ієрархія фігур

```csharp
class Shape
{
    public string Name { get; protected set; } = "Фігура";

    public virtual double Area() => 0;

    public virtual double Perimeter() => 0;

    public override string ToString()
        => $"{Name,-12} площа {Area(),8:F2}   периметр {Perimeter(),8:F2}";
}

class Circle : Shape
{
    public double Radius { get; }

    public Circle(double radius)
    {
        if (radius <= 0)
            throw new ArgumentException("Радіус має бути додатним.");

        Radius = radius;
        Name = "Коло";
    }

    public override double Area() => Math.PI * Radius * Radius;

    public override double Perimeter() => 2 * Math.PI * Radius;
}

class Rectangle : Shape
{
    public double Width { get; }
    public double Height { get; }

    public Rectangle(double width, double height)
    {
        if (width <= 0 || height <= 0)
            throw new ArgumentException("Сторони мають бути додатними.");

        Width = width;
        Height = height;
        Name = width == height ? "Квадрат" : "Прямокутник";
    }

    public override double Area() => Width * Height;

    public override double Perimeter() => 2 * (Width + Height);
}

class Triangle : Shape
{
    public double A { get; }
    public double B { get; }
    public double C { get; }

    public Triangle(double a, double b, double c)
    {
        // Нерівність трикутника
        if (a + b <= c || a + c <= b || b + c <= a)
            throw new ArgumentException("Такого трикутника не існує.");

        A = a;
        B = b;
        C = c;
        Name = "Трикутник";
    }

    public override double Perimeter() => A + B + C;

    // Формула Герона
    public override double Area()
    {
        double p = Perimeter() / 2;
        return Math.Sqrt(p * (p - A) * (p - B) * (p - C));
    }
}
```

### Масив базового типу з різними нащадками

Ось заради чого все затівалося:

```csharp
Shape[] shapes =
[
    new Circle(5),
    new Rectangle(4, 6),
    new Rectangle(3, 3),
    new Triangle(3, 4, 5),
    new Circle(2.5)
];

Console.WriteLine("=== ФІГУРИ ===\n");

foreach (Shape shape in shapes)
{
    Console.WriteLine(shape);          // викликається ToString(), а в ньому — Area()
}

double totalArea = 0;
foreach (Shape shape in shapes)
{
    totalArea += shape.Area();         // у кожного нащадка своя формула
}

Console.WriteLine($"\nУсього фігур: {shapes.Length}");
Console.WriteLine($"Сумарна площа: {totalArea:F2}");
```

**Вивід:**

```
=== ФІГУРИ ===

Коло           площа    78,54   периметр    31,42
Прямокутник    площа    24,00   периметр    20,00
Квадрат        площа     9,00   периметр    12,00
Трикутник      площа     6,00   периметр    12,00
Коло           площа    19,63   периметр    15,71

Усього фігур: 5
Сумарна площа: 137,17
```

Проаналізуймо цикл підрахунку площі. У ньому **немає жодного `if`**. Немає
перевірок «а якщо це коло, то множимо на пі». Код нічого не знає про кола
й трикутники — він знає лише, що кожна фігура вміє `Area()`.

І тепер найголовніше питання: **що станеться, коли нам знадобиться додати
шестикутник?** Відповідь: ми напишемо клас `Hexagon : Shape` і додамо його
в масив. Цикл підрахунку площі **не зміниться жодним символом**. Ось це
й називається розширюваністю, і саме за це ООП цінують у великих проєктах.

:::info[Цікаво]
Принцип, який ми щойно застосували, називається **принципом відкритості
та закритості** (Open/Closed Principle): програмний модуль має бути
відкритий для розширення, але закритий для змін. Тобто нову поведінку
додають новим кодом, а не правками старого. Це одна з п'яти літер
абревіатури SOLID, з якою ви познайомитеся на старших курсах.
:::

## Як це працює: пізнє зв'язування

Виникає резонне питання. У циклі змінна `shape` має тип `Shape`. Компілятор
компілює цей цикл один раз. Як же виходить, що виклик `shape.Area()` щоразу
потрапляє в різний метод?

Відповідь — **пізнє зв'язування** (late binding, dynamic dispatch): рішення
про те, який код виконати, приймається не під час компіляції, а **під час
виконання**, на основі **реального типу об'єкта**.

```
   ЗМІННА (стек)              ОБ'ЄКТ (купа)
 ┌───────────────┐          ┌──────────────────────┐
 │ Shape shape ──┼─────────▶│  тип: Circle         │
 └───────────────┘          │  Radius = 5          │
   тип змінної:             │  Name = "Коло"       │
   Shape                    └──────────┬───────────┘
                                       │ у кожного об'єкта є
                                       │ прихований вказівник на
                                       ▼
                            ┌──────────────────────────────────────┐
                            │ Таблиця методів Circle               │
                            ├──────────────────────────────────────┤
                            │ Area()       ──▶  Circle.Area()      │
                            │ Perimeter()  ──▶  Circle.Perimeter() │
                            │ ToString()   ──▶  Shape.ToString()   │
                            └──────────────────────────────────────┘

   shape.Area()  ──▶  «подивитись у таблицю об'єкта»  ──▶  Circle.Area()
```

Кожен об'єкт у .NET несе в собі прихований службовий вказівник на таблицю
методів свого типу (її традиційно називають **vtable**, virtual method table).
Коли виконується виклик віртуального методу, середовище виконання (CLR)
не йде за адресою, зашитою в код, а бере адресу з таблиці **цього конкретного
об'єкта**.

Тому в рядку `shape.Area()`:

- **тип змінної** (`Shape`) визначає, **що дозволено викликати** — компілятор
  перевіряє, що метод `Area()` у класі `Shape` існує;
- **тип об'єкта** (`Circle`) визначає, **що саме виконається**.

Це і є та єдина відмінність від `new`, яку ми розібрали в минулому підрозділі:
приховані методи в таблицю не потрапляють, тому для них працює тип змінної.

:::note
Виклик віртуального методу трохи повільніший за звичайний — потрібне
додаткове звертання до таблиці. Різниця — одиниці наносекунд, і в 99,9 %
програм її неможливо помітити. Оптимізувати «прибиранням `virtual`» —
класична передчасна оптимізація. Пишіть зрозумілий код.
:::

## Приведення типів в ієрархії

Коли є ієрархія, з'являється потреба перетворювати посилання одного типу
на інший. Тут два напрямки, і вони дуже різні за безпечністю.

### Висхідне приведення (upcast) — завжди безпечне

Перетворення нащадка на предка. Робиться **автоматично**, без жодного
синтаксису:

```csharp
Circle circle = new Circle(5);
Shape shape = circle;              // upcast: Circle -> Shape, неявно
object obj = circle;               // і аж до object
```

Чому це безпечно? Бо кожне коло **є** фігурою — за визначенням наслідування.
Ми нічого не втрачаємо: об'єкт залишається колом, ми просто дивимося на нього
«крізь вужчі окуляри» й бачимо лише члени `Shape`.

Саме завдяки upcast працює `Shape[] shapes = [new Circle(5), ...]` —
кожен елемент неявно приводиться до `Shape`.

### Низхідне приведення (downcast) — потенційно небезпечне

Перетворення предка на нащадка. Вимагає **явного** запису й може впасти:

```csharp
Shape shape = new Circle(5);

Circle c = (Circle)shape;          // OK: об'єкт справді коло
Console.WriteLine(c.Radius);       // тепер видно Radius

Shape another = new Rectangle(2, 3);
Circle wrong = (Circle)another;    // InvalidCastException під час виконання!
```

**Вивід:**

```
System.InvalidCastException: Unable to cast object of type 'Rectangle'
to type 'Circle'.
```

Компілятор такий код пропускає: він бачить, що `Rectangle` і `Circle` в одній
ієрархії, і вірить вам на слово. Помилка вилізе тільки під час виконання.
Тому downcast без перевірки — погана практика.

### Оператор `is`

Оператор **is** перевіряє, чи є об'єкт заданим типом, і повертає `bool`:

```csharp
Shape shape = new Circle(5);

Console.WriteLine(shape is Circle);     // True
Console.WriteLine(shape is Rectangle);  // False
Console.WriteLine(shape is Shape);      // True  (коло є фігурою)
Console.WriteLine(shape is object);     // True  (усе є object)
```

### Pattern matching: `is` із оголошенням змінної

Класична пара «перевірити, потім привести» виглядала так:

```csharp
// Старий стиль
if (shape is Circle)
{
    Circle c = (Circle)shape;      // друга перевірка типу, зайва робота
    Console.WriteLine(c.Radius);
}
```

Сучасний C# дозволяє зробити те саме одним рядком — це називається
**pattern matching**:

```csharp
if (shape is Circle c)             // перевірка + приведення + оголошення
{
    Console.WriteLine($"Радіус: {c.Radius}");
}
```

Читається так: «якщо `shape` — це коло, назви його `c` і виконай блок».
Змінна `c` доступна всередині `if` і має тип `Circle`. Це коротше,
швидше і без ризику винятку. Саме такий запис треба використовувати.

### Оператор `as`

Оператор **as** намагається привести тип і повертає `null`, якщо не вийшло
(замість винятку):

```csharp
Shape shape = new Rectangle(2, 3);

Circle? c = shape as Circle;       // null, бо це не коло

if (c is not null)
    Console.WriteLine(c.Radius);
else
    Console.WriteLine("Це не коло.");
```

**Вивід:**

```
Це не коло.
```

Порівняльна таблиця трьох способів:

| Спосіб | Якщо тип не той | Коли використовувати |
|---|---|---|
| `(Circle)shape` | `InvalidCastException` | коли ви **гарантовано** знаєте тип |
| `shape as Circle` | повертає `null` | коли треба перевірити й одразу мати змінну |
| `shape is Circle c` | `false`, блок не виконується | **у більшості випадків** |

### `switch`-вираз по типу

Коли варіантів багато, замість драбинки з `if` пишуть `switch`-вираз —
дуже виразна можливість сучасного C#:

```csharp
static string Describe(Shape shape) => shape switch
{
    Circle c                              => $"Коло радіусом {c.Radius}",
    Rectangle r when r.Width == r.Height  => $"Квадрат зі стороною {r.Width}",
    Rectangle r                           => $"Прямокутник {r.Width} на {r.Height}",
    Triangle t                            => $"Трикутник зі сторонами {t.A}, {t.B}, {t.C}",
    null                                  => "Фігури немає",
    _                                     => "Якась інша фігура"
};
```

```csharp
Shape[] shapes = [new Circle(5), new Rectangle(3, 3), new Triangle(3, 4, 5)];

foreach (var s in shapes)
    Console.WriteLine(Describe(s));
```

**Вивід:**

```
Коло радіусом 5
Квадрат зі стороною 3
Трикутник зі сторонами 3, 4, 5
```

Розберемо синтаксис:

- гілки перевіряються **згори вниз**, спрацьовує перша відповідна;
- `when` додає додаткову умову до зразка;
- `null` — окремий зразок, дуже зручно;
- `_` — «усе інше», обов'язковий, якщо компілятор не впевнений, що ви
  покрили всі варіанти.

## Коли перевірки типу — це погано

Ми щойно вивчили гарні інструменти. А тепер попередження про те, як їх
не треба вживати.

:::warning[Обережно]
Якщо у вашому коді часто зустрічається `if (x is Circle) ... else if
(x is Rectangle) ...`, це майже завжди означає, що **поліморфізм використано
неправильно**. Логіка, яка залежить від типу, має жити **всередині** класу
як перевизначений метод, а не зовні у драбинці перевірок.
:::

Порівняйте два способи розв'язати одну задачу: намалювати кожну фігуру.

**Погано — драбинка перевірок:**

```csharp
// НЕ РОБІТЬ ТАК
static void Draw(Shape shape)
{
    if (shape is Circle c)
        Console.WriteLine($"Малюю коло r={c.Radius}");
    else if (shape is Rectangle r)
        Console.WriteLine($"Малюю прямокутник {r.Width}x{r.Height}");
    else if (shape is Triangle t)
        Console.WriteLine($"Малюю трикутник {t.A},{t.B},{t.C}");
    else
        Console.WriteLine("Не знаю, як це малювати");
}
```

Проблеми очевидні: додали шестикутник — треба знайти й виправити цей метод.
А якщо таких методів десять (`Draw`, `Export`, `Scale`, `Describe`)? Треба
виправити всі десять і жодного не забути.

**Добре — віртуальний метод:**

```csharp
class Shape
{
    public virtual void Draw() => Console.WriteLine("Малюю фігуру");
}

class Circle : Shape
{
    public override void Draw() => Console.WriteLine($"Малюю коло r={Radius}");
}
// і так далі
```

Тепер уся інформація про коло живе в класі `Circle`. Додали шестикутник —
написали один новий файл, старий код не чіпали.

Коли перевірка типу **виправдана**:

- на межі системи, коли до вас приходить `object` невідомого походження
  (наприклад, дані з мережі чи з файлу);
- коли базовий клас чужий і ви не можете додати в нього віртуальний метод;
- коли поведінка не належить об'єкту логічно (наприклад, серіалізація
  у формат, про який класу фігури знати не потрібно).

## Типові помилки

**1. Плутати перевантаження й перевизначення.**
Overloading — різні параметри в одному класі. Overriding — та сама сигнатура
в нащадку. Різні слова, різні механізми, різні моменти часу.

**2. Робити downcast без перевірки.**
`var c = (Circle)shape;` у циклі по масиву фігур гарантовано впаде на першому
ж прямокутнику. Пишіть `if (shape is Circle c)`.

**3. Оголошувати масив похідного типу замість базового.**
`Circle[] shapes` не дасть покласти туди прямокутник. Уся сила поліморфізму
з'являється саме тоді, коли колекція оголошена **базовим** типом:
`Shape[]` або `List<Shape>`.

**4. Замінювати поліморфізм драбинкою `if (x is ...)`.**
Це «процедурне програмування з класами». Якщо тягне написати таку драбинку —
спитайте себе, який віртуальний метод ви забули додати в базовий клас.
