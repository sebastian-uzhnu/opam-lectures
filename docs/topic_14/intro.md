# Платформа .NET: як це працює

Ви вже написали десятки програм на C#: цикли, масиви, колекції, робота з файлами,
обробка винятків. Увесь цей час ви натискали «Запустити» у Visual Studio і бачили
результат. Але що саме відбувається між натисканням кнопки і появою вікна консолі?

Цей підрозділ — про «двигун», який усе це запускає. Знати його не обов'язково,
щоб написати `Console.WriteLine`. Але без цього знання ви не зрозумієте, чому
C#-програма запускається і на Windows, і на Linux; чому не треба вручну
звільняти пам'ять; звідки береться папка `bin/Debug` і що це за файл `.dll`
у ній. А ще — чому ту саму мову використовують і для ігор в Unity, і для сайтів.

## Що таке .NET

**.NET** — це платформа для розробки й виконання програм: середовище виконання
(те, що запускає ваш код), компілятори, величезна бібліотека готових класів
і набір інструментів командного рядка.

Важливо одразу розділити два поняття, які початківці плутають:

| Поняття | Що це | Приклад |
|---|---|---|
| **C#** | мова програмування — синтаксис, правила | `for`, `class`, `string` |
| **.NET** | платформа — те, що виконує програму і дає готові класи | CLR, `Console`, `List` |

Мова і платформа — різні речі. На .NET можна писати не лише на C#: є ще **F#**
(функціональна мова) і **Visual Basic .NET**. Усі вони компілюються в один
проміжний формат і працюють на одному середовищі виконання. Ми весь курс
використовуємо зв'язку «мова C# + платформа .NET», але корисно розуміти,
що це два різні шари.

:::info Цікаво
Назва «.NET» з'явилася у 2000 році, коли Microsoft оголосила цілу стратегію
навколо інтернет-сервісів. Крапка на початку назви — маркетинговий хід тих часів,
натяк на доменні імена. Сьогодні від тієї стратегії залишилася лише назва,
а сама платформа стала повністю відкритою і кросплатформною.
:::

## Коротка історія: чому існує плутанина в назвах

Якщо ви шукатимете відповідь у гуглі, натрапите на три схожі назви. Розберімося
раз і назавжди, бо це реально економить години на форумах.

**.NET Framework** (2002–2019, остання версія 4.8) — найперша версія платформи.
Працювала **тільки на Windows**, була частиною операційної системи. Досі жива
в корпоративних програмах, які ніхто не переписує, але нових проєктів на ній
не починають.

**.NET Core** (2016–2019, версії 1.0–3.1) — переписана з нуля кросплатформна
версія: Windows, Linux, macOS. Відкритий код, набагато швидша. Спершу вміла
менше, ніж Framework, але швидко наздогнала.

**.NET 5, 6, 7, 8, 9…** (з 2020 року) — об'єднання. Microsoft прибрала слова
«Framework» і «Core» з назви й залишила просто **.NET** з номером версії.
Це продовження .NET Core, а не Framework. Версію 4 пропустили навмисно,
щоб не плутати з .NET Framework 4.x.

```
1990-ті        2002 ────────────────► 2019
               .NET Framework (тільки Windows)
                                        │
                                        │ (підтримка є, розвитку немає)
                                        ▼
                2016 ──────► 2019
                .NET Core (кросплатформний)
                        │
                        ▼
                2020 ──────────────────────────────►
                .NET 5 → 6 → 7 → 8 → 9 → …
                (один .NET для всього)
```

Ми в курсі працюємо з **.NET 8** — це версія з довгою підтримкою (**LTS**,
Long-Term Support). Такі версії виходять раз на два роки і підтримуються три роки,
тому саме їх обирають для навчання і реальних проєктів.

:::tip Порада
Коли шукаєте відповідь в інтернеті, додавайте до запиту «.NET 8» або хоча б рік.
Відповідь із 2013 року може стосуватися .NET Framework і містити код, який
у сучасному проєкті просто не скомпілюється.
:::

## Що відбувається, коли ви тиснете «Запустити»

Ось головна схема цього підрозділу. Запам'ятайте її — далі ми розберемо кожен крок.

```
  Ваш код                Компілятор            Проміжний формат
┌──────────────┐        ┌────────────┐        ┌──────────────────┐
│ Program.cs   │───────▶│  Roslyn    │───────▶│  MyApp.dll       │
│ Student.cs   │        │ (csc.exe)  │        │  ── IL-код ──    │
│ (текст C#)   │        └────────────┘        │  + метадані      │
└──────────────┘                              └────────┬─────────┘
                                                       │
                                    запуск програми    │
                                                       ▼
                                              ┌──────────────────┐
                                              │      CLR         │
                                              │ (середовище      │
                                              │  виконання)      │
                                              └────────┬─────────┘
                                                       │
                                       JIT-компіляція  │ (метод за методом)
                                                       ▼
                                              ┌──────────────────┐
                                              │  Машинний код    │
                                              │  для вашого CPU  │
                                              │  (x64 / ARM64)   │
                                              └────────┬─────────┘
                                                       │
                                                       ▼
                                                   Виконання
```

Тепер по кроках.

### Крок 1. Компілятор Roslyn перетворює C# на IL

**Компілятор** — програма, яка перекладає текст вашої програми в інший формат.
Компілятор C# називається **Roslyn**. Він теж написаний на C# і має відкритий код.

Але Roslyn перекладає ваш код **не** в машинні команди процесора. Він перекладає
його в **IL** (Intermediate Language, проміжна мова; ще її називають MSIL або CIL).
IL — це низькорівнева мова, схожа на асемблер, але не прив'язана до конкретного
процесора. Вона однакова і для Intel, і для ARM.

Ось як виглядає простий метод на C#:

```csharp
int Add(int a, int b)
{
    return a + b;
}
```

А ось приблизно те саме в IL:

```
.method private hidebysig instance int32 Add(int32 a, int32 b) cil managed
{
  .maxstack 2
  ldarg.1      // покласти на стек перший аргумент
  ldarg.2      // покласти на стек другий аргумент
  add          // додати два верхніх значення зі стека
  ret          // повернути результат
}
```

Вам не треба вміти писати IL. Але корисно бачити, що це реальна мова з реальними
командами, а не магія.

### Крок 2. Результат — збірка

Результат компіляції — **збірка** (assembly): файл `.dll` або `.exe`, який містить
IL-код і **метадані** — опис усіх типів, методів, полів і їхніх сигнатур.

Саме завдяки метаданим Visual Studio показує вам підказки IntelliSense для чужих
бібліотек: вона просто читає метадані зі збірки, навіть якщо початкового коду немає.

Загляньте у свій проєкт: після компіляції там з'явиться папка
`bin/Debug/net8.0/`, а в ній — `MyApp.dll` (сама програма) і `MyApp.exe`
(маленький запускач, який знаходить .NET і передає йому `.dll`).

### Крок 3. CLR запускає збірку

**CLR** (Common Language Runtime, загальномовне середовище виконання) — це серце
платформи. Воно:

- завантажує збірки в пам'ять;
- перевіряє IL на безпеку (щоб код не поліз у чужу пам'ять);
- керує пам'яттю і збирає сміття;
- обробляє винятки;
- запускає JIT-компіляцію.

CLR — це те, що встановлюється разом із .NET на комп'ютер. Коли ви віддаєте другові
свою програму, а вона не запускається зі словами «потрібно встановити .NET» —
це саме про CLR.

### Крок 4. JIT перетворює IL на машинний код

Процесор не розуміє IL. Тому перед першим викликом кожного методу CLR запускає
**JIT-компілятор** (Just-In-Time, «саме вчасно»): він бере IL цього методу
й перетворює на машинні інструкції конкретного процесора.

Ключове слово — **перед першим викликом**. Метод, який жодного разу не викликали,
взагалі не компілюється. Метод, який викликали сто разів, компілюється один раз,
а далі використовується вже готовий машинний код.

```
Перший виклик Add():   IL ──JIT──▶ машинний код ──▶ виконати
Другий виклик Add():   ────────────────────────────▶ виконати (готове)
Сотий виклик Add():    ────────────────────────────▶ виконати (готове)
```

:::info Цікаво
Може здатися, що це повільніше за звичайну компіляцію в машинний код (як у C++).
Частково так — програма трохи довше стартує. Але JIT знає, на якому саме процесорі
вона зараз працює, і може використати сучасні інструкції, яких не було, коли
програму компілювали. Понад те, у .NET є **tiered compilation**: спершу метод
компілюється швидко й «абияк», а якщо його викликають часто — перекомпільовується
вдруге, уже з агресивною оптимізацією.
:::

### Альтернатива: AOT

Іноді довгий старт неприйнятний — наприклад, для маленької утиліти або хмарної
функції, яка живе півсекунди. Для таких випадків є **AOT** (Ahead-Of-Time,
«заздалегідь»): увесь код компілюється в машинний ще на етапі збірки.

| Що | JIT | AOT |
|---|---|---|
| Коли компілюється в машинний код | під час роботи, метод за методом | заздалегідь, під час збірки |
| Старт програми | повільніший | миттєвий |
| Розмір результату | менший | більший |
| Потрібен встановлений .NET | так | ні, файл самодостатній |
| Коли обирати | звичайні застосунки, ігри, сайти | утиліти CLI, мікросервіси, хмарні функції |

Ми в курсі користуємося стандартним JIT — AOT згадуємо, щоб ви знали слово.

## Бібліотека базових класів

**BCL** (Base Class Library, бібліотека базових класів) — це тисячі готових класів,
які постачаються разом із .NET. Ви ними користуєтеся щодня, навіть не думаючи:
`Console`, `string`, `List`, `File`, `Math`, `Random`, `DateTime` — усе це BCL.

Класи BCL згруповані у **простори імен** (namespace) — це як папки для типів.
Наприклад:

| Простір імен | Що там лежить |
|---|---|
| `System` | базове: `Console`, `Math`, `Random`, `String`, `DateTime`, `Exception` |
| `System.Collections.Generic` | колекції: `List`, `Dictionary`, `HashSet`, `Queue` |
| `System.IO` | файли й папки: `File`, `Directory`, `Path`, `StreamReader` |
| `System.Linq` | запити до колекцій: `Where`, `Select`, `OrderBy` |
| `System.Text` | текст: `StringBuilder`, кодування |
| `System.Threading.Tasks` | асинхронність: `Task` |

Щоб скористатися класом із простору імен, його треба «підключити» директивою
`using`:

```csharp
using System.Text;

var builder = new StringBuilder();
builder.Append("Привіт");
builder.Append(", світе!");
Console.WriteLine(builder.ToString());
```

**Вивід:**

```
Привіт, світе!
```

Ви, певно, помітили, що у ваших проєктах на .NET 8 директив `using` майже немає,
а `Console.WriteLine` все одно працює. Це через **неявні using** (implicit usings):
у нових проєктах компілятор сам додає найпоширеніші простори імен. Побачити
це можна у файлі `.csproj`:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

:::note
Повне ім'я класу складається з простору імен і назви: `System.Collections.Generic.List`.
Директива `using` дозволяє писати коротко — `List`. Якщо два різні простори імен
містять клас з однаковою назвою, компілятор поскаржиться на неоднозначність,
і тоді доведеться писати повне ім'я.
:::

## Керована пам'ять і збирач сміття

У мовах на кшталт C програміст сам просить пам'ять і сам її повертає. Забув
повернути — програма поступово з'їдає всю оперативну пам'ять. Повернув двічі —
програма падає.

У .NET пам'ять **керована** (managed). Ви створюєте об'єкти, коли треба,
а звільняє їх **GC** (Garbage Collector, збирач сміття) — фонова частина CLR.

Логіка проста: GC періодично перевіряє, на які об'єкти в пам'яті вже ніхто
не посилається. Якщо на об'єкт немає жодного посилання зі змінних вашої
програми — до нього неможливо дістатися, отже, він більше не потрібен,
і його пам'ять можна звільнити.

```csharp
var numbers = new List<int> { 1, 2, 3 };
numbers = new List<int> { 4, 5, 6 };
// Перший список більше нікому не потрібен:
// на нього не лишилося жодного посилання.
// Колись GC його прибере — вам нічого робити не треба.
```

:::tip Порада
Не намагайтеся «допомагати» збирачеві сміття викликом `GC.Collect()`. У 99 %
випадків це лише сповільнює програму. GC розумніший за наші здогади про те,
коли саме варто прибирати.
:::

Детально пристрій GC (покоління, компактизація купи) ми не розбираємо — це тема
просунутого курсу. Головне, що треба винести: **ви не звільняєте пам'ять вручну**.

## Де ще працює C#

Одна з причин вивчати саме цю зв'язку — вона всюди. Одна мова, одна бібліотека
базових класів, різні типи застосунків:

| Технологія | Що це дозволяє |
|---|---|
| **Console** | консольні утиліти, скрипти, те, що ми пишемо зараз |
| **ASP.NET Core** | вебсайти й API — величезна частина корпоративного бекенду |
| **Unity** | ігри: 2D, 3D, мобільні, консольні. Логіка ігор пишеться на C# |
| **.NET MAUI** | мобільні й десктопні застосунки з одного коду: Android, iOS, Windows, macOS |
| **Blazor** | вебінтерфейси на C# замість JavaScript, працює прямо в браузері |
| **WPF / WinForms** | класичні десктопні програми під Windows |

І все це запускається на Windows, Linux і macOS. Ваша консольна програма,
скомпільована на Windows, той самий `.dll` запуститься на Linux-сервері без
жодних змін — бо на сервері свій CLR, який виконає той самий IL.

:::info Цікаво
Величезна частина .NET має відкритий код і лежить на GitHub у репозиторії
`dotnet/runtime`. Ви можете зайти й подивитися, як насправді реалізовано
`List` або `string.Split`. Це не найлегше читання для другого курсу, але
відчуття «магії немає, там просто код» дуже корисне.
:::

## Що можна робити без Visual Studio

.NET має повноцінний інструмент командного рядка — `dotnet`. Він робить усе те саме,
що кнопки у Visual Studio:

```
dotnet new console -o MyApp     # створити консольний проєкт у папці MyApp
dotnet build                    # скомпілювати
dotnet run                      # скомпілювати і запустити
dotnet --version                # перевірити версію .NET
```

Спробуйте виконати `dotnet --version` у терміналі — побачите, яка версія
встановлена саме у вас. Це найпростіший спосіб переконатися, що середовище
взагалі є.

## Типові помилки

**«C# і .NET — це одне й те саме».** Ні. C# — мова, .NET — платформа, яка виконує
код цією мовою і дає готові класи. Мову можна вивчити за тиждень, платформу — ні.

**«.NET працює тільки на Windows».** Це було правдою до 2016 року. Сучасний .NET 8
однаково добре працює на Linux — більшість серверів на ньому саме на Linux.

**«Треба вручну звільняти пам'ять після роботи з об'єктом».** Ні, цим займається
збирач сміття. Виняток — зовнішні ресурси (файли, з'єднання), для них є `using`-блок,
який ви вже бачили в темі про роботу з файлами.

**«Файл .exe містить машинний код».** У .NET це не так: `.exe` — це переважно
запускач, а справжній код лежить в IL усередині `.dll` і перетворюється на машинний
уже під час роботи програми.
