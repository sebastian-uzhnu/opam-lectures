# Чотири принципи ООП оглядово

Ви вже знаєте, що таке клас і об'єкт. Але клас — це лише інструмент.
**Об'єктно-орієнтоване програмування** (ООП) — це спосіб думати про програму:
розкладати задачу не на послідовність дій, а на сутності, які взаємодіють.

Цей підхід тримається на чотирьох принципах: **інкапсуляція**, **наслідування**,
**поліморфізм**, **абстракція**. Їх часто вимагають назвати на співбесіді,
але сенс не в тому, щоб зазубрити чотири слова. Сенс у тому, що кожен принцип
розв'язує конкретну біль, яка виникає, коли програма росте.

Цей підрозділ — **оглядовий**. Ми пройдемося по всіх чотирьох, щоб ви побачили
цілісну картину. Кожен принцип детально розбиратиметься далі: інкапсуляція —
у темі 15, наслідування — у темі 16, поліморфізм і абстракція — у темі 17.

```
                    ОБ'ЄКТНО-ОРІЄНТОВАНЕ ПРОГРАМУВАННЯ
                                    │
       ┌────────────────┬───────────┴────────┬────────────────────┐
       ▼                ▼                    ▼                    ▼
  Інкапсуляція     Наслідування        Поліморфізм          Абстракція
       │                │                    │                    │
  «сховати те,    «не повторювати     «однаковий виклик   «показувати лише
   що всередині»   спільний код»       для різних типів»   те, що важливо»
       │                │                    │                    │
    тема 15          тема 16              тема 17              тема 17
```

## Інкапсуляція

**Інкапсуляція** — це об'єднання даних і методів, які з ними працюють, в одному
класі **плюс** приховування внутрішнього стану від зовнішнього коду. Об'єкт сам
відповідає за коректність своїх даних; ззовні до них не дістатися напряму.

Проблема, яку це розв'язує: якщо будь-хто ззовні може записати в поле будь-що,
об'єкт може опинитися у неможливому стані — від'ємний вік, порожнє прізвище,
баланс мінус мільйон. І коли програма впаде, ви не знатимете, хто саме зіпсував
дані, бо зіпсувати їх могли з будь-якого з п'ятдесяти місць у коді.

```csharp
class BankAccount
{
    private decimal balance;          // ззовні не видно

    public decimal Balance => balance;   // читати можна

    public void Deposit(decimal amount)  // змінювати — лише через метод
    {
        if (amount <= 0)
        {
            Console.WriteLine("Сума поповнення має бути додатною.");
            return;
        }
        balance += amount;
    }
}
```

```csharp
var account = new BankAccount();
account.Deposit(500);
account.Deposit(-1000);          // не пройде: об'єкт себе захистив
Console.WriteLine(account.Balance);
```

**Вивід:**

```
Сума поповнення має бути додатною.
500
```

Спробувати `account.balance = -1000;` не вийде — компілятор навіть не побачить
такого поля ззовні класу.

**Аналогія з життя.** Банкомат. Усередині нього є сейф із готівкою, механізм
подачі купюр, зв'язок із банком. Ви не маєте до цього доступу — вам дали
кнопки й екран. Це не тому, що вам не довіряють, а тому, що так неможливо
випадково зламати механізм і так значно простіше користуватися: замість
двадцяти важелів — п'ять кнопок.

:::tip[Порада]
Проста перевірка на інкапсуляцію: чи може зовнішній код привести ваш об'єкт
у стан, який не має існувати? Якщо так — інкапсуляції немає, скільки б
приватних полів там не було.
:::

## Наслідування

**Наслідування** — це створення нового класу на основі наявного. Новий клас
(**нащадок**, або похідний клас) автоматично отримує всі поля й методи
батьківського класу (**базового**) і може додати свої.

Проблема, яку це розв'язує: дублювання. Уявіть, що в програмі коледжу є класи
`Student` і `Teacher`. В обох є ім'я, прізвище, дата народження, телефон, метод
виведення контактів. Написати це двічі — означає надалі виправляти кожну помилку
двічі й неминуче забути про один із класів.

```csharp
class Person
{
    public string Name = "";
    public int Age;

    public void Introduce()
    {
        Console.WriteLine($"Мене звати {Name}, мені {Age}.");
    }
}

class Student : Person          // двокрапка = "наслідує Person"
{
    public string Group = "";

    public void ShowGroup()
    {
        Console.WriteLine($"Навчаюсь у групі {Group}.");
    }
}
```

```csharp
var student = new Student();
student.Name = "Олена";       // поле дісталося від Person
student.Age = 18;
student.Group = "ПЗ-21";

student.Introduce();          // метод дістався від Person
student.ShowGroup();          // власний метод
```

**Вивід:**

```
Мене звати Олена, мені 18.
Навчаюсь у групі ПЗ-21.
```

Схема відношення:

```
              ┌─────────────────┐
              │     Person      │      базовий клас
              │  Name, Age      │
              │  Introduce()    │
              └────────┬────────┘
                       │  наслідують
          ┌────────────┴────────────┐
          ▼                         ▼
   ┌─────────────┐          ┌──────────────┐
   │   Student   │          │   Teacher    │   нащадки
   │  + Group    │          │  + Subject   │
   │  + ShowGroup│          │  + Lecture() │
   └─────────────┘          └──────────────┘
```

Читається відношення так: «студент **є** особою», «викладач **є** особою».
Це головний тест на доречність наслідування — англійською його називають
«is-a test».

**Аналогія з життя.** Біологічна класифікація. Кіт — це ссавець, ссавець —
це тварина. Усе, що вміє тварина (дихати, рухатися), уміє й кіт, бо він тварина.
Але кіт додає своє: муркотіти. Не треба переписувати «дихати» окремо
для кожного виду.

:::warning[Обережно]
Наслідування виглядає привабливо, і новачки починають наслідувати все підряд:
«у машини є двигун, отже, `Car : Engine`». Ні. Машина **не є** двигуном,
вона його **має**. У такому випадку треба просто поле типу `Engine` всередині
класу `Car`. Наслідування — тільки там, де проходить тест «A є B».
:::

## Поліморфізм

**Поліморфізм** (з грецької — «багато форм») — це можливість працювати
з об'єктами різних класів через один спільний інтерфейс, коли кожен клас
реагує на однаковий виклик по-своєму.

Проблема, яку це розв'язує: нескінченні `if`-и та `switch`-і за типом. Без
поліморфізму код виглядає так:

```csharp
// ТАК НЕ ТРЕБА
foreach (var shape in shapes)
{
    if (shape.Type == "circle") DrawCircle(shape);
    else if (shape.Type == "square") DrawSquare(shape);
    else if (shape.Type == "triangle") DrawTriangle(shape);
    // додали нову фігуру — треба знайти всі такі if-и в програмі
}
```

З поліморфізмом кожен клас сам знає, як себе намалювати:

```csharp
class Shape
{
    public virtual void Draw()          // virtual = "нащадок може перевизначити"
    {
        Console.WriteLine("Якась фігура");
    }
}

class Circle : Shape
{
    public override void Draw() => Console.WriteLine("Малюю коло");
}

class Square : Shape
{
    public override void Draw() => Console.WriteLine("Малюю квадрат");
}
```

```csharp
List<Shape> shapes = [new Circle(), new Square(), new Circle()];

foreach (Shape shape in shapes)
{
    shape.Draw();      // однаковий рядок коду, різна поведінка
}
```

**Вивід:**

```
Малюю коло
Малюю квадрат
Малюю коло
```

Зверніть увагу: у циклі змінна має тип `Shape`, а викликається метод конкретного
класу. Рішення, який саме метод виконати, ухвалюється **під час роботи програми**,
на підставі реального типу об'єкта. Додасте клас `Triangle` — цикл не зміниться
взагалі.

**Аналогія з життя.** Кнопка «Пуск» на різній техніці. На пральній машині
вона запускає прання, на мікрохвильовці — розігрів, на дрилі — обертання.
Дія називається однаково, а результат залежить від того, що це за пристрій.
Вам не треба знати влаштування кожного, щоб натиснути кнопку.

:::info[Цікаво]
Ви вже користувалися поліморфізмом, навіть не знаючи цього слова. Метод
`Console.WriteLine` викликає `ToString()` для будь-якого об'єкта — і кожен клас
повертає свій рядок. `int` повертає число, `DateTime` — дату, ваш власний клас
поверне назву типу, якщо ви не перевизначили `ToString()` самі.
:::

## Абстракція

**Абстракція** — це виділення суттєвих характеристик об'єкта і свідоме
ігнорування всього іншого. Модель у програмі не повторює реальність — вона
бере з реальності лише те, що потрібне саме цій програмі.

Проблема, яку це розв'язує: спокуса змоделювати «все». Реальний студент має
зріст, колір очей, улюблену музику, історію хвороб. Для програми обліку
успішності все це — шум. Уключити зайве означає ускладнити клас, ускладнити
введення даних і зрештою заплутатися.

Одна й та сама сутність у різних програмах абстрагується по-різному:

| Програма | Що важливо про людину | Що ігноруємо |
|---|---|---|
| Електронний журнал | ПІБ, група, оцінки | зріст, група крові |
| Медична картка | зріст, вага, група крові, алергії | оцінки з математики |
| Плейлист | нічого — там важливі треки, а не люди | усе |

У коді абстракція — це також уміння сховати складну реалізацію за простою
назвою. Порівняйте:

```csharp
// Без абстракції: щоб зберегти рядок у файл, треба знати про потоки й буфери
using var stream = new FileStream("data.txt", FileMode.Create);
using var writer = new StreamWriter(stream);
writer.Write("Привіт");

// З абстракцією: один метод, деталі сховані
File.WriteAllText("data.txt", "Привіт");
```

`File.WriteAllText` усередині робить те саме, що й перший варіант. Але вам
не треба про це знати — вам дали просту назву для складної дії. Це і є
абстракція, якою ви користуєтеся щодня.

У C# для абстракції є спеціальні інструменти — **абстрактні класи**
(`abstract class`) та **інтерфейси** (`interface`). Вони описують, **що** тип
уміє, не кажучи, **як** саме він це робить:

```csharp
interface IPlayable
{
    void Play();      // тільки опис, без тіла
    void Stop();
}
```

Будь-який клас, який заявить `class Track : IPlayable`, зобов'язаний реалізувати
обидва методи. Код, який працює зі змінною типу `IPlayable`, знає лише, що там
можна викликати `Play()` і `Stop()`, — і йому цього достатньо.

**Аналогія з життя.** Кермо автомобіля. Ви крутите його праворуч — машина їде
праворуч. Що там усередині — рейкова передача, гідропідсилювач чи електромотор —
для водія неважливо. Абстракція «кермо» дозволяє водити будь-яку машину,
не будучи автомеханіком.

## Як принципи пов'язані між собою

Чотири принципи не існують окремо — вони підсилюють один одного:

```
   Абстракція вирішує, ЩО ми моделюємо
              │
              ▼
   Інкапсуляція ховає, ЯК це влаштовано всередині
              │
              ▼
   Наслідування дозволяє будувати нове на основі готового
              │
              ▼
   Поліморфізм дозволяє працювати з різним однаково
```

Наприклад, у грі: ви абстрагуєте сутність «ворог» (важливі здоров'я, шкода,
швидкість); інкапсулюєте здоров'я, щоб ніхто ззовні не поставив мінус сто;
успадковуєте від «ворога» «зомбі» та «боса»; і викликаєте `enemy.Attack()`
в одному циклі для всіх — це вже поліморфізм.

## Підсумкова таблиця

| Принцип | Яку проблему розв'язує | Ключові слова C# | Де у курсі |
|---|---|---|---|
| **Інкапсуляція** | зовнішній код псує стан об'єкта; дані окремо від логіки | `private`, `public`, властивості | тема 15 |
| **Наслідування** | дублювання спільного коду в схожих класах | `:` , `base`, `protected` | тема 16 |
| **Поліморфізм** | нескінченні `if` за типом об'єкта | `virtual`, `override`, `abstract` | тема 17 |
| **Абстракція** | зайва складність, моделювання непотрібного | `abstract class`, `interface` | тема 17 |

:::note
Іноді до цього списку додають п'ятий пункт — **композицію** («об'єкт містить
інші об'єкти»). Формально це не принцип ООП, але на практиці композиція
використовується частіше за наслідування. Побачите її у темі 16 разом
із правилом «композиція замість наслідування».
:::

## Типові помилки

**Вважати, що ООП — це просто «писати класи».** Можна написати клас на тисячу
рядків із публічними полями і статичними методами — і це не буде ООП. Класи —
інструмент; принципи — спосіб ним користуватися.

**Наслідувати заради економії кількох рядків.** Якщо між класами немає
відношення «A є B», спільний код краще винести в окремий клас-помічник
або скористатися композицією.

**Плутати поліморфізм із перевантаженням методів.** Перевантаження
(два методи `Print` з різними параметрами) вирішується компілятором під час
компіляції. Поліморфізм — під час виконання, за реальним типом об'єкта.
Це різні механізми.

**Моделювати реальність «як є».** Клас не мусить містити все, що має реальний
об'єкт. Він містить лише те, що потрібне цій конкретній програмі.
