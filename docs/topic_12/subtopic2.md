# CSV та бінарні файли

## Навіщо формат

Записати текст у файл ми вміємо. Але дані у програмах рідко бувають просто
текстом. Частіше це **таблиця**: студент, оцінка, дата. Тренування, дистанція,
час. Товар, кількість, ціна.

Щоб зберегти таблицю у файлі, потрібна домовленість: як відрізнити один
стовпчик від іншого, а один рядок таблиці — від наступного. Така домовленість
і називається **форматом файлу**.

Найпростіший і найпоширеніший табличний формат — CSV.

## Що таке CSV

**CSV** (*Comma-Separated Values*, «значення, розділені комами») — це звичайний
текстовий файл, у якому:

- один рядок файлу = один рядок таблиці;
- значення всередині рядка розділені комою;
- перший рядок часто містить назви стовпчиків (**заголовок**).

```
Name,Score,Date
Олена,11,2026-09-01
Тарас,8,2026-09-01
Марія,12,2026-09-02
```

Це відкривається в Excel, у LibreOffice, у Google Таблицях, читається
будь-якою мовою програмування і чудово переглядається у «Блокноті».
Саме за простоту CSV і люблять.

## Найпростіший варіант, який працює

Поки дані «слухняні» — усе справді просто.

```csharp
using System.Globalization;

// Кортеж — це «склейка» кількох значень в одне без створення класу.
// Звертатись до частин можна за іменами: item.Name, item.Score
(string Name, int Score, string Date)[] results =
[
    ("Олена", 11, "2026-09-01"),
    ("Тарас", 8,  "2026-09-01"),
    ("Марія", 12, "2026-09-02")
];

string path = "grades.csv";

using (StreamWriter writer = new StreamWriter(path))
{
    writer.WriteLine("Name,Score,Date");        // заголовок

    foreach (var r in results)
    {
        writer.WriteLine($"{r.Name},{r.Score},{r.Date}");
    }
}

Console.WriteLine(File.ReadAllText(path));
```

**Вивід:**

```
Name,Score,Date
Олена,11,2026-09-01
Тарас,8,2026-09-01
Марія,12,2026-09-02
```

І читання назад:

```csharp
string[] lines = File.ReadAllLines("grades.csv");

for (int i = 1; i < lines.Length; i++)      // з 1, бо 0 — заголовок
{
    string[] parts = lines[i].Split(',');
    Console.WriteLine($"{parts[0],-10} {parts[1],3}  {parts[2]}");
}
```

**Вивід:**

```
Олена       11  2026-09-01
Тарас        8  2026-09-01
Марія       12  2026-09-02
```

Виглядає, ніби тема закрита. Насправді ми щойно написали код, який зламається
на реальних даних щонайменше чотирма способами.

## Чому CSV — це не «просто split по комі»

### Проблема 1: кома всередині значення

```
Name,Comment,Score
Олена,"Гарна робота, але є помилки",11
```

`Split(',')` розріже цей рядок на **чотири** частини замість трьох:
`Олена`, `"Гарна робота`, ` але є помилки"`, `11`. Далі
`int.Parse(parts[2])` впаде з `FormatException`, і ви довго не зрозумієте чому.

Стандарт CSV (він справді існує — RFC 4180) вирішує це так: якщо значення
містить кому, воно береться в **подвійні лапки**. А якщо всередині значення
є самі лапки — вони подвоюються:

```
Олена,"Він сказав ""добре"" і пішов",11
```

### Проблема 2: перенос рядка всередині значення

Значення в лапках може містити навіть перехід на новий рядок. Тоді один рядок
таблиці займає два рядки файлу, і `File.ReadAllLines` розріже його навпіл.

### Проблема 3: кома як десятковий розділювач

Ось найпідступніше для нас. В українській локалі дробові числа пишуться
з комою: `3,14`. Записуємо у CSV:

```
Distance,Time
5,2,00:31:15
```

Що це — «5,2 км» і «00:31:15», чи «5», «2» і «00:31:15»? Файл зіпсовано.

Саме тому в Україні та більшості Європи Excel за замовчуванням використовує
для CSV не кому, а **крапку з комою**:

```
Distance;Time
5,2;00:31:15
```

### Проблема 4: локаль при записі чисел

```csharp
double distance = 5.2;
writer.WriteLine($"Біг,{distance}");
```

На вашому комп'ютері запишеться `Біг,5,2`. На комп'ютері з англійською
локаллю — `Біг,5.2`. Той самий код, різні файли. І коли ви передасте файл
однокурснику, його програма прочитає ваші дані неправильно.

:::danger Часта помилка
Найгірше в цій історії те, що на вашій машині все працює. Помилка вилізе
у викладача, на іншому комп'ютері або через півроку. **Числа у файл
завжди пишуться і читаються з `CultureInfo.InvariantCulture`.**
:::

## Правила безпечного CSV

Зведемо в чіткі правила, яких достатньо для навчальних і більшості реальних
задач.

| Правило | Чому |
| --- | --- |
| Розділювач — крапка з комою `;` | не конфліктує з десятковою комою, і Excel в українській локалі відкриє коректно |
| Числа — через `InvariantCulture` | файл однаково читається на будь-якому комп'ютері |
| Дати — у форматі `yyyy-MM-dd` | однозначно, сортується як текст, це стандарт ISO 8601 |
| Значення екрануються, якщо містять `;`, `"` або перенос | інакше рядок «розлізеться» |
| Перший рядок — заголовок | і людині зрозуміло, і програмі є що перевірити |
| Кодування — UTF-8 | кирилиця не перетвориться на кракозябри |

### Функція екранування

```csharp
string Escape(string value)
{
    // Якщо є розділювач, лапки або перенос рядка — беремо в лапки,
    // а внутрішні лапки подвоюємо
    if (value.Contains(';') || value.Contains('"') ||
        value.Contains('\n') || value.Contains('\r'))
    {
        return "\"" + value.Replace("\"", "\"\"") + "\"";
    }
    return value;
}

Console.WriteLine(Escape("Олена"));                  // Олена
Console.WriteLine(Escape("Добре; але не дуже"));     // "Добре; але не дуже"
Console.WriteLine(Escape("Він сказав \"так\""));     // "Він сказав ""так"""
```

:::info Цікаво
У промислових проєктах CSV руками не парсять — беруть готову бібліотеку,
наприклад `CsvHelper`. Вона знає всі тонкощі стандарту: лапки, переноси,
різні розділювачі, порожні значення. Але щоб розуміти, що робить бібліотека,
корисно один раз написати це самому — чим ми зараз і займемось.
:::

## Повний приклад: збереження результатів обчислень

Задача. Програма рахує результати серії вимірювань, зберігає їх у CSV
і вміє прочитати назад, перевіряючи кожен рядок.

### Запис

```csharp
using System.Globalization;

(string Label, double Value, DateTime Measured)[] measurements =
[
    ("Температура ранок", 12.4,  new DateTime(2026, 9, 14, 7, 0, 0)),
    ("Температура день",  21.75, new DateTime(2026, 9, 14, 14, 0, 0)),
    ("Температура вечір", 15.0,  new DateTime(2026, 9, 14, 20, 0, 0))
];

string path = "measurements.csv";
var culture = CultureInfo.InvariantCulture;

using (StreamWriter writer = new StreamWriter(path))
{
    writer.WriteLine("Label;Value;Measured");

    foreach (var m in measurements)
    {
        string label = Escape(m.Label);
        string value = m.Value.ToString(culture);              // крапка, не кома
        string date = m.Measured.ToString("yyyy-MM-dd HH:mm", culture);

        writer.WriteLine($"{label};{value};{date}");
    }
}

Console.WriteLine("Записано. Вміст файлу:");
Console.WriteLine(File.ReadAllText(path));

string Escape(string v) =>
    v.Contains(';') || v.Contains('"')
        ? "\"" + v.Replace("\"", "\"\"") + "\""
        : v;
```

**Вивід:**

```
Записано. Вміст файлу:
Label;Value;Measured
Температура ранок;12.4;2026-09-14 07:00
Температура день;21.75;2026-09-14 14:00
Температура вечір;15;2026-09-14 20:00
```

Зверніть увагу: `15.0` записалось як `15` — так працює `ToString()` для
`double`. Якщо потрібен фіксований формат, використовуйте
`m.Value.ToString("F2", culture)`.

### Читання з валідацією

Тут головна ідея: **жодного `Parse`**. Файл міг зіпсувати хто завгодно,
включно з вами, коли ви відкривали його в Excel.

```csharp
using System.Globalization;

string path = "measurements.csv";
var culture = CultureInfo.InvariantCulture;

if (!File.Exists(path))
{
    Console.WriteLine($"Файл {Path.GetFullPath(path)} не знайдено.");
    return;
}

string[] lines = File.ReadAllLines(path);

if (lines.Length < 2)
{
    Console.WriteLine("Файл порожній або містить лише заголовок.");
    return;
}

int goodCount = 0;
int badCount = 0;
double sum = 0;

Console.WriteLine($"{"Показник",-22} {"Значення",9}  Час");
Console.WriteLine(new string('-', 55));

for (int i = 1; i < lines.Length; i++)   // 0 — заголовок, пропускаємо
{
    string line = lines[i].Trim();

    if (line.Length == 0) continue;      // порожні рядки ігноруємо

    string[] parts = line.Split(';');

    if (parts.Length != 3)
    {
        Console.WriteLine($"[рядок {i + 1}] очікувалось 3 поля, знайдено {parts.Length} — пропущено");
        badCount++;
        continue;
    }

    string label = parts[0].Trim().Trim('"');

    if (!double.TryParse(parts[1], NumberStyles.Float, culture, out double value))
    {
        Console.WriteLine($"[рядок {i + 1}] «{parts[1]}» не є числом — пропущено");
        badCount++;
        continue;
    }

    if (!DateTime.TryParse(parts[2], culture, DateTimeStyles.None, out DateTime measured))
    {
        Console.WriteLine($"[рядок {i + 1}] «{parts[2]}» не є датою — пропущено");
        badCount++;
        continue;
    }

    goodCount++;
    sum += value;
    Console.WriteLine($"{label,-22} {value,9:F2}  {measured:dd.MM.yyyy HH:mm}");
}

Console.WriteLine(new string('-', 55));
Console.WriteLine($"Прочитано записів: {goodCount}, пропущено рядків: {badCount}");

if (goodCount > 0)
{
    Console.WriteLine($"Середнє значення: {sum / goodCount:F2}");
}
```

**Вивід** (для файлу, у який хтось дописав зіпсований рядок):

```
Показник                Значення  Час
-------------------------------------------------------
Температура ранок          12,40  14.09.2026 07:00
[рядок 3] «двадцять» не є числом — пропущено
Температура вечір          15,00  14.09.2026 20:00
-------------------------------------------------------
Прочитано записів: 2, пропущено рядків: 1
Середнє значення: 13,70
```

Програма не впала. Вона пояснила, який саме рядок поганий і чому,
і порахувала статистику по тому, що вдалося прочитати. Це і є правильна
поведінка при роботі з зовнішніми даними.

:::tip Порада
Шаблон валідації рядка CSV завжди однаковий:

1. `Trim()` і пропустити порожні рядки;
2. `Split` і перевірити **кількість полів**;
3. `TryParse` для кожного числового та датового поля;
4. при невдачі — повідомити номер рядка і `continue`, а не `return`.

Номер рядка обов'язково виводьте як `i + 1`: у файлі нумерація з одиниці,
а в масиві з нуля.
:::

:::warning Обережно
`Split(';')` на порожньому рядку поверне масив з одного порожнього елемента,
а не порожній масив. Тому перевірка `line.Length == 0` має бути **до**
`Split`, інакше отримаєте безглузде повідомлення «очікувалось 3 поля,
знайдено 1».
:::

## Бінарні файли

Досі ми зберігали все як текст. Число `1000000` займало у файлі 7 байтів —
по одному на кожну цифру. Але в пам'яті це `int`, тобто рівно 4 байти.
Виникає питання: а чи не можна записати ці 4 байти як є?

Можна. Такий файл називають **бінарним** (двійковим): у ньому лежать не
символи, а внутрішнє представлення даних.

### BinaryWriter

```csharp
string path = "scores.bin";

using (BinaryWriter writer = new BinaryWriter(File.Open(path, FileMode.Create)))
{
    writer.Write(3);              // int:    кількість записів
    writer.Write("Олена");        // string
    writer.Write(11);             // int
    writer.Write(9.75);           // double
    writer.Write("Тарас");
    writer.Write(8);
    writer.Write(7.20);
    writer.Write("Марія");
    writer.Write(12);
    writer.Write(11.90);
}

FileInfo info = new FileInfo(path);
Console.WriteLine($"Розмір бінарного файлу: {info.Length} байт");
```

**Вивід:**

```
Розмір бінарного файлу: 71 байт
```

Метод `Write` перевантажений для всіх базових типів: `int`, `double`, `bool`,
`char`, `string`, `byte`, `decimal`. Компілятор сам обирає потрібну версію
за типом аргументу.

### BinaryReader

```csharp
using (BinaryReader reader = new BinaryReader(File.Open("scores.bin", FileMode.Open)))
{
    int count = reader.ReadInt32();
    Console.WriteLine($"Записів у файлі: {count}");

    for (int i = 0; i < count; i++)
    {
        string name = reader.ReadString();
        int score = reader.ReadInt32();
        double average = reader.ReadDouble();

        Console.WriteLine($"{name,-10} оцінка {score,2}, середнє {average:F2}");
    }
}
```

**Вивід:**

```
Записів у файлі: 3
Олена      оцінка 11, середнє 9,75
Тарас      оцінка  8, середнє 7,20
Марія      оцінка 12, середнє 11,90
```

Методи читання:

| Метод | Читає |
| --- | --- |
| `ReadInt32()` | `int` (4 байти) |
| `ReadInt64()` | `long` (8 байтів) |
| `ReadDouble()` | `double` (8 байтів) |
| `ReadSingle()` | `float` (4 байти) |
| `ReadBoolean()` | `bool` (1 байт) |
| `ReadChar()` | `char` |
| `ReadString()` | рядок (довжина + символи) |
| `ReadByte()` | один байт |

### Головне правило бінарних файлів

:::danger Порядок запису = порядок читання

Бінарний файл **не містить жодної інформації про свою структуру**. Це просто
байти. Якщо ви записали `int`, потім `string`, потім `double`, то читати
треба рівно в тій самій послідовності і тими самими типами.

```csharp
// Записали:
writer.Write(11);        // int
writer.Write(9.75);      // double

// Читаємо у неправильному порядку:
double d = reader.ReadDouble();   // прочитає 4 байти int + 4 байти double
int i = reader.ReadInt32();       // сміття або EndOfStreamException
```

Помилки тут не буде — буде просто сміття. Це найнеприємніша властивість
бінарних форматів.
:::

Наочно, що лежить у файлі:

```
Текстовий файл "11;9.75\n"       Бінарний файл
┌──┬──┬──┬──┬──┬──┬──┬──┐        ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│'1'│'1'│';'│'9'│'.'│'7'│'5'│LF│  │ 0B 00 00 00  │ 00 00 00 00 00 80 23 40│
└──┴──┴──┴──┴──┴──┴──┴──┘        └──────────────┴────────────────────────┘
   8 байтів                          4 байти (int 11)  8 байтів (double 9.75)
   можна прочитати очима              12 байтів, очима не прочитати
```

Ще одна деталь: `ReadString` працює лише тому, що `BinaryWriter.Write(string)`
записує **спочатку довжину рядка**, а потім самі символи. Тобто структура
у файлі все ж таки є — але мінімальна, і про типи вона нічого не знає.

### Кінець файлу

Якщо кількість записів наперед невідома, читають до кінця потоку:

```csharp
using BinaryReader reader = new BinaryReader(File.Open("scores.bin", FileMode.Open));

while (reader.BaseStream.Position < reader.BaseStream.Length)
{
    string name = reader.ReadString();
    Console.WriteLine(name);
}
```

Але надійніше — записати кількість першим числом, як у прикладі вище.
Саме так влаштована більшість реальних бінарних форматів.

## Текстовий чи бінарний

| Критерій | Текстовий (CSV, TXT) | Бінарний |
| --- | --- | --- |
| Розмір файлу | більший (`1000000` — 7 байтів) | менший (`1000000` — 4 байти) |
| Швидкість читання/запису | повільніше: треба перетворювати текст у числа | швидше: байти копіюються як є |
| Можна відкрити «Блокнотом» | ✅ так | ❌ каша з символів |
| Можна відкрити Excel | ✅ так | ❌ ні |
| Можна виправити руками | ✅ так | ❌ практично ні |
| Стійкість до дрібної помилки | ✅ зіпсується один рядок | ❌ зіпсується весь файл після місця помилки |
| Переносимість між мовами і ОС | ✅ висока | ❌ низька: залежить від порядку байтів, версії формату |
| Точність дробових чисел | можлива втрата при форматуванні | ✅ біт у біт |
| Зручність налагодження | ✅ видно все | ❌ потрібен спеціальний переглядач |
| Коли обирати | дані для людини, обмін, звіти, налаштування | великі обсяги, зображення, звук, швидкодія |

Просте правило: **якщо файл хоч колись побачить людина — беріть текстовий**.
Бінарний — коли обсяги великі, а вміст цікавий тільки програмі.

:::info Цікаво
Порядок байтів у бінарному файлі залежить від архітектури процесора.
На x86 і ARM використовується *little-endian* — молодший байт першим,
тому `int` 11 виглядає як `0B 00 00 00`, а не `00 00 00 0B`. Були
(і є) процесори з *big-endian*, і бінарний файл, записаний на одному,
на іншому читався б неправильно. Це одна з причин, чому для обміну даними
між різними системами обирають текстові формати — CSV, JSON, XML.
:::

## Робота з байтами напряму

Найпростіший спосіб працювати з бінарними даними — прочитати або записати
весь файл як масив байтів:

```csharp
// Прочитати будь-який файл у масив байтів
byte[] data = File.ReadAllBytes("photo.jpg");
Console.WriteLine($"Розмір: {data.Length} байт");
Console.WriteLine($"Перші 4 байти: {data[0]:X2} {data[1]:X2} {data[2]:X2} {data[3]:X2}");

// Записати масив байтів у файл (наприклад, скопіювати)
File.WriteAllBytes("photo_copy.jpg", data);
```

**Вивід:**

```
Розмір: 458752 байт
Перші 4 байти: FF D8 FF E0
```

Формат `X2` виводить байт у шістнадцятковому вигляді. `FF D8` на початку —
це «підпис» формату JPEG. Майже кожен формат файлу починається з такої
сигнатури: `50 4B` — це ZIP, `25 50 44 46` — це PDF (`%PDF` у тексті),
`89 50 4E 47` — PNG.

:::warning Обережно
`File.ReadAllBytes` завантажує **весь** файл у пам'ять. Для фотографії
це нормально, для відео на 4 ГБ — ні. У такому разі потрібен `FileStream`
із читанням порціями.
:::

## Обробка помилок доступу до файлів

Останнє і найпрактичніше. Файлові операції — територія, де щось іде не так
регулярно, і це **не ваша провина**. Ось повний перелік того, до чого треба
бути готовим.

| Виняток | Коли виникає | Правильна реакція |
| --- | --- | --- |
| `FileNotFoundException` | файлу немає за вказаним шляхом | вивести **повний** шлях через `Path.GetFullPath`, запропонувати створити файл або взяти значення за замовчуванням |
| `DirectoryNotFoundException` | немає папки у шляху | створити папку через `Directory.CreateDirectory` і повторити |
| `UnauthorizedAccessException` | немає прав; шлях указує на папку, а не файл; файл «лише для читання» | пояснити людині, запропонувати інше місце (наприклад, «Документи») |
| `IOException` | файл зайнятий іншою програмою; диск заповнено; носій від'єднано | попросити закрити файл в іншій програмі і повторити спробу |
| `PathTooLongException` | шлях довший за ліміт системи | скоротити шлях, перенести ближче до кореня |
| `ArgumentException` | у шляху заборонені символи або він порожній | перевірити ввід через `Path.GetInvalidFileNameChars` |
| `NotSupportedException` | формат шляху не підтримується | перевірити, що шлях не містить зайвої двокрапки тощо |
| `EndOfStreamException` | `BinaryReader` дійшов до кінця раніше, ніж очікував | файл пошкоджено або структура не та |

`FileNotFoundException`, `DirectoryNotFoundException`, `PathTooLongException`
і `EndOfStreamException` — усі нащадки `IOException`. Тому загальний
`catch (IOException)` завжди йде **останнім** з файлових.

### Робочий шаблон

```csharp
string path = Path.Combine("data", "training.csv");

try
{
    Directory.CreateDirectory(Path.GetDirectoryName(path)!);

    using StreamWriter writer = new StreamWriter(path, append: true);
    writer.WriteLine("Біг;5.2;2026-09-14");

    Console.WriteLine($"Збережено у {Path.GetFullPath(path)}");
}
catch (UnauthorizedAccessException)
{
    Console.WriteLine("Немає прав на запис у цю папку.");
    Console.WriteLine("Спробуйте зберегти у папку «Документи».");
}
catch (IOException ex)
{
    Console.WriteLine("Не вдалося записати файл.");
    Console.WriteLine($"Можливо, він відкритий в іншій програмі (наприклад, в Excel).");
    Console.WriteLine($"Деталі: {ex.Message}");
}
```

Знак `!` після `Path.GetDirectoryName(path)` — це **null-forgiving оператор**:
ми кажемо компілятору «я знаю, що тут не буде `null`, не попереджай». Метод
теоретично може повернути `null` для кореневого шляху, але у нашому випадку
цього не станеться.

:::tip Порада
Файл, відкритий в Excel, заблокований на запис. Це найчастіша причина
`IOException` у навчальних програмах із CSV: студент відкрив файл подивитись,
забув закрити і не розуміє, чому програма більше не працює. Перше, що варто
перевірити.
:::

:::danger Часта помилка
`File.Exists(path)` повертає `true` — і студент вважає, що читання
гарантовано вдасться. Не гарантовано: між перевіркою і читанням проходить
час, за який файл можуть видалити, перейменувати або відкрити на монопольний
доступ. Перевірка `Exists` потрібна для **гарного повідомлення**,
`try/catch` — для **надійності**. Робіть обидва.
:::

## Типові помилки

**1. Розрізати CSV через `Split(',')`, коли числа з комою.**
Використовуйте `;` як розділювач і `InvariantCulture` для чисел.

**2. Забути пропустити рядок заголовка.**

```csharp
for (int i = 0; i < lines.Length; i++)   // прочитає "Name" як ім'я студента
for (int i = 1; i < lines.Length; i++)   // правильно
```

**3. Використати `Parse` замість `TryParse` при читанні файлу.**
Файл — це зовнішні дані. Один зіпсований символ, і програма падає замість
того, щоб пропустити поганий рядок.

**4. Не перевірити `parts.Length` після `Split`.**
Класичний `IndexOutOfRangeException` на порожньому або обрізаному рядку.

**5. Читати бінарний файл не в тому порядку, у якому писали.**
Помилки не буде — будуть неправильні числа. Записуйте порядок полів
у коментарі поруч із кодом запису.

**6. Записувати числа з локальним розділювачем.**
Файл, створений на вашому комп'ютері, не прочитається на іншому.
`InvariantCulture` — і при записі, і при читанні.

## Підсумок теми

- **`System.IO`** — усе про файли й папки. `File`/`Directory` — статичні,
  зручні для простих задач; `FileInfo`/`DirectoryInfo` — об'єкти
  з властивостями.
- **Шляхи** склеюють через `Path.Combine`, пишуть у verbatim-рядках `@"..."`,
  і завжди перевіряють через `Path.GetFullPath`, коли файл «не знайшовся».
- **Відносний шлях** відлічується від `bin\Debug\net8.0`, а не від папки
  з `Program.cs`.
- **Прості методи** `File.ReadAllText`/`WriteAllText` — для маленьких файлів;
  **потоки** `StreamReader`/`StreamWriter` — для великих і для багатьох
  операцій поспіль.
- **`using` обов'язковий** для будь-якого потоку: інакше файл лишиться
  заблокованим, а дані — в буфері.
- **UTF-8** — кодування за замовчуванням у .NET 8; кракозябри виникають,
  коли пишуть в одному кодуванні, а читають в іншому.
- **CSV** — простий формат, але з пастками: кома всередині значення, лапки,
  локаль. Розділювач `;`, числа через `InvariantCulture`, кожен рядок
  перевіряти через `TryParse`.
- **Бінарні файли** компактніші й швидші, але читаються строго в тому
  порядку, у якому записані, і не переглядаються очима.
- **Файлові винятки** обробляти обов'язково: причини збоїв від вашого коду
  не залежать.
