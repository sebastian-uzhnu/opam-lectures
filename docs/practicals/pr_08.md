# Практичне заняття №8

## Тема
Вибір структури даних для задачі. Задачі з колекціями

## Мета
Навчитися обирати структуру даних під конкретну задачу й письмово обґрунтовувати цей вибір, спираючись на набір операцій, які над даними виконуватимуться найчастіше. Закріпити уявлення про вартість операцій у масиві, списку, словнику, множині, черзі та стеку. Набути навичок проєктування способу зберігання даних за власною темою наскрізного проєкту: визначити поля, їхні типи та ключ, за яким записи шукатимуться. Підготуватися до лабораторної роботи №12, з якої починається індивідуальний проєкт.

## Тривалість
2 академічні години.

## Обладнання та програмне забезпечення
Зошит у клітинку й олівець, перелік із 40 тем індивідуальних проєктів (додаток до плану), роздруківка або електронна копія цих методичних вказівок. Персональний комп'ютер із .NET 8 SDK — лише для перевірки окремих відповідей наприкінці заняття.

## Теоретичні відомості

### 1. Що таке структура даних і чому вибір впливає на швидкість

**Структура даних** — спосіб організації даних у пам'яті разом із набором операцій, які над ними можна виконувати, і вартістю кожної операції.

Ключове слово тут — **вартість**. Одні й ті самі дані можна зберегти кількома способами, і всі вони «працюватимуть». Різниця в тому, скільки дій доведеться зробити комп'ютеру, щоб виконати типовий запит.

Уявіть картотеку сервісного центру на 1000 записів. Треба знайти запис за номером замовлення.

```
   Спосіб 1: стос аркушів, складених у порядку надходження
   ┌───┐┌───┐┌───┐┌───┐┌───┐            щоб знайти потрібний, переглядаємо
   │ 1 ││ 2 ││ 3 ││...││1000│           аркуші один за одним:
   └───┘└───┘└───┘└───┘└───┘            у середньому 500 переглядів,
                                        у найгіршому випадку — 1000

   Спосіб 2: шухляда з роздільниками за номером замовлення
   ┌──────┬──────┬──────┬──────┐        одразу відкриваємо потрібний
   │ 0001 │ 0002 │ 0003 │ .... │        роздільник: 1 дія незалежно
   └──────┴──────┴──────┴──────┘        від того, 1000 записів чи 100 000
```

Обидва способи зберігають ті самі дані. Але перший потребує сотень дій, а другий — однієї. Саме це й означає «вибір структури даних впливає на швидкість».

Вартість операції прийнято оцінювати не в секундах (вони залежать від комп'ютера), а в **кількості елементарних дій залежно від кількості елементів n**:

| Позначення | Назва | Що означає словами | Приклад |
|---|---|---|---|
| Стала | не залежить від n | Кількість дій однакова для 10 і для 10 000 елементів | Доступ до елемента списку за індексом |
| Лінійна | пропорційна n | Удесятеро більше даних — удесятеро більше роботи | Пошук значення перебором |
| Квадратична | пропорційна n · n | Удесятеро більше даних — у сто разів більше роботи | Перевірка всіх пар елементів |

Правило вибору формулюється так: **визначте, яку операцію ваша програма виконуватиме найчастіше, і оберіть структуру, у якій саме ця операція найдешевша**. Немає «найкращої» структури — є структура, що пасує до набору операцій.

### 2. Масив проти списку

**Масив** — послідовність елементів одного типу з фіксованою кількістю, заданою при створенні. **Список** (`List<T>`, читається «список елементів типу T») — послідовність елементів одного типу, кількість яких змінюється під час роботи програми.

| Ознака | Масив | Список |
|---|---|---|
| Розмір | Задається при створенні й не змінюється | Зростає й зменшується під час роботи |
| Додавання елемента в кінець | Неможливе: треба створити більший масив і скопіювати дані | Одна операція додавання |
| Видалення елемента | Неможливе: лишається «дірка», яку доводиться затирати вручну | Одна операція видалення |
| Доступ за індексом | Стала вартість | Стала вартість |
| Що всередині | Суцільна ділянка пам'яті | Той самий масив усередині плюс лічильник заповнення |
| Коли брати | Кількість елементів відома наперед і не змінюється | Записи додаються й видаляються під час роботи |

Усередині список — це масив із запасом. Коли запас вичерпується, створюється більший масив і дані копіюються. Відбувається це рідко, тому середня вартість додавання все одно вважається сталою.

```
   список із 4 елементів, запас на 8:
   ┌───┬───┬───┬───┬───┬───┬───┬───┐
   │ A │ B │ C │ D │ _ │ _ │ _ │ _ │   кількість = 4, місткість = 8
   └───┴───┴───┴───┴───┴───┴───┴───┘
   додаємо E — просто записуємо в п'яту комірку, нічого не копіюючи
```

Для наскрізного проєкту (записи додають, змінюють і видаляють під час роботи) масив непридатний практично завжди. Тому основною структурою буде список.

### 3. Список: доступ за індексом швидкий, пошук за значенням повільний

Список уміє миттєво віддати елемент за його **номером**, але нічого не знає про те, що в цьому елементі записано. Щоб знайти запис за вмістом, доводиться переглядати елементи один за одним.

```
   пошук замовлення з номером 734 у списку на 1000 записів:

   [0] 512 ✗  →  [1] 118 ✗  →  [2] 907 ✗  →  ...  →  [681] 734 ✓
                                                           ▲
                                                    знайдено на 682-й
                                                    перевірці з 1000
```

| Операція над списком | Вартість | Пояснення |
|---|---|---|
| Узяти елемент за індексом | стала | Адреса обчислюється арифметично |
| Змінити елемент за індексом | стала | Те саме |
| Додати в кінець | стала (у середньому) | Іноді відбувається розширення буфера |
| Вставити в середину | лінійна | Усі наступні елементи зсуваються праворуч |
| Видалити з середини | лінійна | Усі наступні елементи зсуваються ліворуч |
| Знайти за значенням | лінійна | Перебір, поки не знайдено |
| Перебрати всі елементи | лінійна | Інакше й бути не може |

Висновок: список добре пасує, коли дані переважно **перебирають** (звіт, вивід усіх записів, підрахунок суми) і зрідка шукають поодинці. Якщо ж головна операція — «знайти запис за номером», список змушує щоразу платити лінійну вартість.

### 4. Словник: доступ за ключем швидкий, порядок не гарантований

**Словник** (`Dictionary<TKey, TValue>`) — набір пар «ключ — значення», у якому за ключем можна миттєво отримати значення. **Ключ** — це те, за чим шукають; **значення** — те, що зберігають.

```
                     ключ                значення
                  ┌─────────┐        ┌──────────────────────────┐
                  │  "L-104"│ ──────►│ Ноутбук, Acer, 2023, ... │
                  ├─────────┤        ├──────────────────────────┤
                  │  "L-217"│ ──────►│ Ноутбук, Asus, 2021, ... │
                  ├─────────┤        ├──────────────────────────┤
                  │  "L-330"│ ──────►│ Ноутбук, Dell, 2022, ... │
                  └─────────┘        └──────────────────────────┘

   Ключ перетворюється на число (хеш), число вказує на комірку —
   тому пошук не залежить від кількості записів.
```

Про словник треба знати три речі.

По-перше, ключі **унікальні**: спроба додати другий запис із наявним ключем спричиняє помилку. Це не вада, а захист: словник не дасть завести двох клієнтів з однаковим номером договору.

По-друге, **порядок перебору не гарантований**. Словник не зобов'язаний повертати записи в тому порядку, у якому їх додавали. Якщо у звіті потрібен порядок, записи треба окремо відсортувати.

По-третє, миттєвий пошук працює **лише за ключем**. Пошук за будь-яким іншим полем — це знову перебір усіх записів, як у списку.

| Операція над словником | Вартість | Примітка |
|---|---|---|
| Додати пару | стала | Ключ має бути новим |
| Отримати значення за ключем | стала | Головна перевага |
| Перевірити наявність ключа | стала | Виконувати **до** звернення за ключем |
| Видалити за ключем | стала | — |
| Знайти за значенням чи іншим полем | лінійна | Переваги немає |
| Перебрати всі пари | лінійна | Порядок не гарантований |

### 5. Множина: коли важлива лише унікальність

**Множина** (`HashSet<T>`) — набір значень без повторів, у якому швидко перевіряється, чи є в ньому задане значення.

Множина — це фактично словник без значень: самі ключі. Беруть її тоді, коли потрібно відповісти на питання «чи вже було таке?» або «скільки різних?».

| Задача | Чому множина |
|---|---|
| Перевірити, чи не зайнято номер квитка | Перевірка наявності — стала вартість |
| Порахувати, скільки різних жанрів у колекції | Повтори відкидаються самі |
| Скласти список унікальних міст із файлу | Додавання наявного значення просто нічого не робить |

Порівняння з тими самими даними у списку: щоб перевірити унікальність у списку на n елементів, доводиться щоразу перебирати всі n. Для 1000 записів це 1000 перевірок замість однієї.

### 6. Черга і стек

**Черга** (`Queue<T>`) працює за правилом **FIFO** (першим прийшов — першим вийшов). **Стек** (`Stack<T>`) працює за правилом **LIFO** (останнім прийшов — першим вийшов).

```
   ЧЕРГА (FIFO)                          СТЕК (LIFO)

   додаємо в кінець                      додаємо зверху
        │                                     │
        ▼                                     ▼
   ┌───┬───┬───┬───┐                        ┌───┐  ◄── беремо звідси
   │ A │ B │ C │ D │                        │ D │
   └───┴───┴───┴───┘                        ├───┤
     │                                      │ C │
     ▼                                      ├───┤
   беремо з початку                         │ B │
                                            ├───┤
   A обслуговується першим                  │ A │
                                            └───┘
                                     A обслуговується останнім
```

| Структура | Правило | Життєвий приклад | Типове застосування в програмі |
|---|---|---|---|
| Черга | FIFO | Черга до лікаря, замовлення в піцерії | Обробка заявок у порядку надходження |
| Стек | LIFO | Стос тарілок, стос книжок | Скасування останньої дії, повернення на попередній екран |

У наскрізному проєкті черга й стек зазвичай не є основним сховищем — вони стануть у пригоді для допоміжних задач: черга заявок в обробці, стек останніх дій для скасування.

### 7. Зведена таблиця: операція — вартість у кожній структурі

Ця таблиця — головний робочий інструмент заняття. За нею ви обґрунтовуватимете вибір.

| Операція | Масив | Список | Словник | Множина | Черга / стек |
|---|---|---|---|---|---|
| Доступ за індексом | стала | стала | немає індексів | немає індексів | немає |
| Доступ за ключем | немає | немає | стала | немає значень | немає |
| Пошук за значенням | лінійна | лінійна | лінійна | стала | лінійна |
| Додати в кінець | неможливо | стала | стала (за ключем) | стала | стала |
| Вставити в середину | неможливо | лінійна | поняття немає | поняття немає | немає |
| Видалити елемент | неможливо | лінійна | стала (за ключем) | стала | стала (з краю) |
| Перевірити наявність | лінійна | лінійна | стала (ключ) | стала | лінійна |
| Гарантований порядок | так | так | ні | ні | так (FIFO або LIFO) |
| Дозволені повтори | так | так | ключі — ні | ні | так |

Читати таблицю треба стовпцями «зверху вниз» для однієї структури й рядками «зліва направо» для однієї операції. Якщо ваша найчастіша операція в рядку має «стала» лише в одному стовпці — вибір зроблено.

### 8. Як обрати ключ для словника

Ключ — не просто «якесь поле». Поле годиться на роль ключа, якщо задовольняє чотири вимоги:

| Вимога до ключа | Пояснення | Приклад порушення |
|---|---|---|
| Унікальність | Двох записів з однаковим ключем бути не може | Прізвище клієнта: Іваненків двоє |
| Незмінність | Ключ не змінюється протягом життя запису | Статус замовлення змінюється щодня |
| Обов'язковість | Ключ є в кожного запису | Номер телефону: у частини клієнтів його немає |
| Зручність пошуку | Саме це користувач уводить, коли шукає запис | Внутрішній порядковий номер, якого користувач не знає |

Найчастіше ключем стає поле-ідентифікатор: інвентарний номер, артикул, код, номер замовлення, номер договору, VIN. У переліку тем проєкту таке поле є в кожній темі й, як правило, стоїть першим.

Окремий випадок — **складений ключ**: коли унікальність дає лише поєднання кількох полів. Наприклад, у розкладі занять пара однозначно визначається трійкою «день тижня + номер пари + аудиторія». Такий ключ складають у один рядок за домовленим зразком, наприклад `"Пн-3-214"`.

### 9. Кортеж як тимчасова заміна класу

Поки власних класів немає (вони з'являться в лабораторній роботі №13), один запис зручно зберігати **кортежем**.

**Кортеж** — значення, що складається з кількох іменованих частин різних типів, записаних разом.

```csharp
// один запис про ноутбук: кортеж із п'ятьма іменованими полями
(string Code, string Brand, int Year, decimal Price, bool Ready) laptop =
    ("L-104", "Acer", 2023, 4200m, false);

Console.WriteLine(laptop.Brand);   // Acer
Console.WriteLine(laptop.Year);    // 2023
```

Кортеж зручний тим, що дає іменовані поля без оголошення класу. Але він має обмеження, які треба розуміти вже зараз:

| Що вміє кортеж | Чого не вміє |
|---|---|
| Зберігати кілька полів різних типів під іменами | Мати власні методи (наприклад, «обчислити вартість») |
| Бути елементом списку чи значенням словника | Захищати поля від некоректних значень |
| Передаватися в метод і повертатися з нього | Брати участь в ієрархії «базовий тип — нащадки» |

Саме тому в лабораторній №13 кортеж замінять класом. На цьому занятті кортеж потрібен, щоб описати **склад запису**: які поля є і якого вони типу. Ця робота не пропаде — вона перетвориться на поля класу без змін.

## Приклад виконання

Приклад виконано на демонстраційній темі викладача — **«Облік ноутбуків у сервісному центрі»**. Вашої теми в переліку це не стосується: ви виконуватимете ті самі кроки для своєї предметної області.

**Умова.** Спроєктувати спосіб зберігання даних для програми обліку ноутбуків у сервісному центрі. Програма має вміти: додати ноутбук, показати всі записи, знайти запис за інвентарним кодом, змінити статус ремонту, видалити запис, вивести звіт «скільки ноутбуків кожного бренда». Кількість записів — до кількох тисяч. Потрібно: визначити поля запису та їхні типи, обрати ключ, обрати структуру даних і письмово обґрунтувати вибір, оцінити вартість кожної операції.

### Крок 1. Виписати операції та їхню частоту

Проєктування починається не з даних, а з операцій. Спочатку перелічимо, що програма робитиме, і оцінимо, як часто.

| Операція програми | Як часто | Яка дія над даними |
|---|---|---|
| Додати ноутбук | часто | Додавання одного запису |
| Знайти за інвентарним кодом | дуже часто | Пошук за одним конкретним полем |
| Змінити статус ремонту | часто | Пошук за кодом, потім зміна |
| Видалити запис | зрідка | Пошук за кодом, потім видалення |
| Показати всі записи | часто | Повний перебір |
| Звіт за брендами | зрідка | Повний перебір із групуванням |

Найчастіша операція — **пошук за інвентарним кодом**. Саме вона визначає вибір.

### Крок 2. Визначити поля запису та їхні типи

| Поле | Опис | Тип | Чому саме цей тип |
|---|---|---|---|
| Code | Інвентарний код | `string` | Містить літери й дефіс: `"L-104"` |
| Brand | Бренд | `string` | Текст |
| Model | Модель | `string` | Текст |
| Year | Рік випуску | `int` | Ціле число, дробової частини не буває |
| RepairCost | Вартість ремонту | `decimal` | Гроші: `decimal` не дає похибки округлення, на відміну від `double` |
| AcceptedOn | Дата прийому | `DateTime` | Дата, з якою рахують термін ремонту |
| Status | Статус | `string` | Одне зі значень: «прийнято», «в роботі», «готово» |
| IsUrgent | Чи терміновий | `bool` | Логічне значення, лише два стани |

Окремо — **обчислюване поле**: «скільки днів у ремонті». Його не зберігають, а рахують від дати прийому до сьогодні. Зберігати обчислюване значення шкідливо: воно застаріє вже наступного дня.

Запис описуємо кортежем — це готовий перелік майбутніх полів класу:

```csharp
(string Code, string Brand, string Model, int Year,
 decimal RepairCost, DateTime AcceptedOn, string Status, bool IsUrgent) item =
    ("L-104", "Acer", "Aspire 5", 2023, 4200m,
     new DateTime(2025, 9, 2), "в роботі", false);
```

### Крок 3. Обрати ключ

Перевіряємо поля за чотирма вимогами з пункту 8.

| Кандидат | Унікальний | Незмінний | Обов'язковий | Зручний для пошуку | Висновок |
|---|---|---|---|---|---|
| Code | так | так | так | так | **Ключ** |
| Brand | ні | так | так | ні | Не підходить: брендів мало, записів багато |
| Model | ні | так | так | частково | Не підходить: моделі повторюються |
| AcceptedOn | ні | так | так | ні | Не підходить: за день приймають кілька ноутбуків |
| Status | ні | ні | так | ні | Не підходить: змінюється щодня |

Ключ — `Code`, тип `string`.

### Крок 4. Обрати структуру даних і обґрунтувати

Розглянемо три варіанти й порівняємо їх на найчастішій операції.

```
   Варіант А: List<кортеж>          Варіант Б: Dictionary<string, кортеж>

   [0] L-104 ┐                      "L-104" ──► запис
   [1] L-217 │ пошук за кодом:      "L-217" ──► запис      пошук за кодом:
   [2] L-330 │ перебір усього       "L-330" ──► запис      одна дія
   ...       │ списку, у середньому ...
   [n] ...   ┘ n/2 перевірок
```

| Критерій | Варіант А: список | Варіант Б: словник | Варіант В: масив |
|---|---|---|---|
| Пошук за кодом (найчастіша операція) | лінійна | **стала** | лінійна |
| Додавання запису | стала | стала | неможливе без перестворення |
| Видалення за кодом | лінійна | **стала** | неможливе |
| Захист від дублікатів коду | немає, треба перевіряти вручну | **вбудований** | немає |
| Повний перебір для звіту | лінійна, порядок збережено | лінійна, порядок не гарантований | лінійна |
| Підсумок | придатний, але повільний на пошуку | **обраний варіант** | непридатний |

**Обґрунтування вибору (так його треба записати в зошиті).** Найчастіша операція програми — пошук запису за інвентарним кодом; у словнику вона має сталу вартість, у списку — лінійну. Словник додатково гарантує унікальність кодів, що для інвентарного обліку є обов'язковою вимогою. Недолік словника — негарантований порядок перебору — для цієї задачі не критичний: у звіті записи все одно доводиться впорядковувати за брендом, а не за порядком додавання. Отже, основне сховище — `Dictionary<string, кортеж>`, де ключ — інвентарний код.

### Крок 5. Оцінити вартість операцій у вибраній структурі

Порівняємо кількість дій для 2000 записів.

| Операція | У списку (дій) | У словнику (дій) | Виграш |
|---|---|---|---|
| Знайти за кодом | до 2000, у середньому 1000 | 1 | у сотні разів |
| Змінити статус | до 2000 + 1 | 1 + 1 | у сотні разів |
| Видалити за кодом | до 2000 + зсув решти | 1 | у сотні разів |
| Додати запис | 1 (плюс перевірка дубліката — до 2000) | 1 (перевірка вбудована) | у сотні разів |
| Вивести всі записи | 2000 | 2000 | немає |
| Звіт за брендами | 2000 | 2000 | немає |

Видно, що словник виграє саме там, де операція виконується часто, і не програє там, де все одно потрібен повний перебір.

### Крок 6. Допоміжні структури

Крім основного сховища, у програмі знадобляться допоміжні.

| Потреба | Структура | Обґрунтування |
|---|---|---|
| Перелік усіх брендів без повторів | `HashSet<string>` | Потрібна лише унікальність, порядок не важливий |
| Звіт «скільки ноутбуків кожного бренда» | `Dictionary<string, int>` | Ключ — бренд, значення — лічильник; збільшується за одну дію |
| Черга термінових ремонтів | `Queue<string>` | Обслуговування в порядку надходження — це FIFO |

Фрагмент для аналізу — саме так накопичують лічильники в словнику (без LINQ, звичайним циклом):

```csharp
var byBrand = new Dictionary<string, int>();

foreach (var item in items)              // items — основне сховище
{
    if (byBrand.ContainsKey(item.Brand))
        byBrand[item.Brand] = byBrand[item.Brand] + 1;
    else
        byBrand[item.Brand] = 1;         // перша зустріч бренда
}
```

|---|---|---|---|

## Критерії оцінювання

| Бали | Критерій |
|---|---|
| 2 | Виконано всі аудиторні завдання. Для кожної умови обрано структуру й наведено обґрунтування з посиланням на вартість операцій, а не «бо так зручніше». Проєкт зберігання за власною темою повний: поля з типами, обчислюване поле, перевірені кандидати в ключі, обрана структура з обґрунтуванням, допоміжні структури. Помилки у виборі структур знайдено всі, для кожної вказано, на яких даних вона проявиться. Студент упевнено відповідає на контрольні питання. Самостійні завдання виконано. |
| 1 | Виконано більшу частину завдань. Структури здебільшого обрано правильно, але обґрунтування поверхові або не спираються на таблицю вартостей. У проєкті за власною темою бракує частини пунктів: не визначено обчислюване поле, не перевірено кандидатів у ключі або не названо допоміжних структур. Знайдено не всі помилки у виборі структур. Самостійні завдання виконано частково. |
| 0 | Роботу не виконано або виконано менш ніж наполовину. Вибір структур не обґрунтовано, проєкт за власною темою відсутній або зведений до переліку полів без типів і ключа. Студент не може пояснити власні записи. |
