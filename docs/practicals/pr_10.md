# Практичне заняття №10

## Тема
Проєктування абстракцій та інтерфейсів. Аналіз принципів SOLID

## Мета
Навчитися відрізняти ситуації, у яких базовий клас має бути абстрактним, від ситуацій, у яких потрібен інтерфейс, і обґрунтовувати свій вибір словами, а не звичкою. Закріпити розуміння інтерфейсу як контракту між частинами програми: що саме він гарантує тому, хто ним користується, і чого не гарантує. Набути навичок аналізу готового опису класів на відповідність принципам SOLID та навичок перепроєктування там, де принцип порушено. Підготувати письмовий проєкт абстракцій для власної теми наскрізного проєкту, який на лабораторній роботі №15 буде перенесено в код.

## Тривалість
2 академічні години.

## Обладнання та програмне забезпечення
Персональний комп'ютер, .NET 8 SDK, будь-яке середовище розробки або текстовий редактор і термінал, система контролю версій Git. Зошит для практичних робіт, олівець і лінійка — схеми класів на цьому занятті креслять від руки. Роздруківка або електронна копія переліку 40 тем наскрізного проєкту.

На цьому занятті програм не пишуть. Усі фрагменти коду в тексті — це матеріал для читання й аналізу, а не завдання «наберіть і запустіть».

## Теоретичні відомості

### 1. Навіщо взагалі потрібна абстракція

На лабораторній роботі №14 ви побудували ієрархію класів: базовий клас із спільними полями і нащадки, які його доповнюють. І майже одразу натрапили на незручне питання: а чи має сенс створити об'єкт самого базового класу?

Розглянемо демонстраційну тему викладача — облік ноутбуків у сервісному центрі. Є базовий клас «Заявка» і три нащадки: «Гарантійний ремонт», «Платний ремонт», «Діагностика». Спробуємо створити просто «Заявку» — без уточнення, яка вона. Скільки вона коштує? Невідомо: у гарантійної вартість нульова, у платної рахується за прайсом, у діагностики фіксована. Який у неї термін виконання? Теж невідомо. Виходить об'єкт, у якого половина відповідей — «залежить від того, яка це насправді заявка».

**Абстракція** — це опис того, що спільне для групи об'єктів, без подробиць, які в кожного свої. «Заявка» як поняття існує: у неї є номер, клієнт, пристрій, дата прийому. А «заявка взагалі», як окремий предмет у реальному сервісному центрі, не існує — кожна заявка обов'язково якогось конкретного роду.

Мова програмування дає інструмент, щоб записати це прямо: **абстрактний клас** — клас, позначений словом `abstract`, об'єкт якого створити неможливо. Він існує тільки як спільна основа для нащадків.

```csharp
// Фрагмент для аналізу: abstract забороняє створити об'єкт цього класу.
public abstract class ServiceRequest
{
    public int Number { get; set; }
    public string Customer { get; set; } = "";
    public DateTime AcceptedOn { get; set; }

    // Метод без тіла: кожен нащадок зобов'язаний його реалізувати.
    public abstract decimal CalculateCost();
}
```

Спроба написати `new ServiceRequest()` тепер не скомпілюється: це підказка компілятора, що ви намагаєтеся створити те, чого не буває. **Абстрактний метод** — метод без тіла, оголошений в абстрактному класі. Він задає обов'язок: кожен нащадок мусить написати свою версію. Якщо нащадок цього не зробить, програма не скомпілюється. Порівняйте з віртуальним методом із лабораторної №14: віртуальний має тіло за замовчуванням і його можна не перевизначати, абстрактний тіла не має й не перевизначити його не можна.

| Ознака | Звичайний метод | `virtual` | `abstract` |
|---|---|---|---|
| Має тіло в базовому класі | так | так | ні |
| Нащадок може перевизначити | ні | так | зобов'язаний |
| Можна створити об'єкт базового класу | так | так | ні |
| Коли обирати | поведінка однакова для всіх | є розумне «за замовчуванням» | розумного «за замовчуванням» немає |

Правило, яке варто запам'ятати: **якщо ви не можете написати тіло методу в базовому класі, не вигадуючи, — метод має бути абстрактним.** Повертати з `CalculateCost()` нуль «щоб хоч щось повертало» — це вигадування, і воно рано чи пізно проявиться помилкою в звіті.

### 2. Коли базовий клас не має сенсу існувати сам по собі

Ознаки того, що базовий клас треба робити абстрактним, перевіряють за списком питань.

| Питання до базового класу | Якщо відповідь така — робіть `abstract` |
|---|---|
| Чи можна назвати реальний предмет, який є «просто цим класом», без уточнення роду? | не можна назвати |
| Чи знаєте ви, що повертатимуть усі його методи, не питаючи «а який це нащадок»? | не знаєте хоча б для одного методу |
| Чи доводиться писати «заглушку» в тілі методу, аби компілятор не лаявся? | доводиться |
| Чи є в базовому класі поле, яке для одних нащадків обов'язкове, а для інших безглузде? | є (це ще й сигнал переглянути ієрархію) |
| Чи створюєте ви об'єкт базового класу десь у програмі? | ніде не створюєте |

Зворотний випадок теж буває: якщо «просто товар» у магазині — цілком нормальна річ, а «товар зі знижкою» лише додає поле знижки, базовий клас абстрактним робити не треба.

### 3. Інтерфейс як контракт: що саме він гарантує

**Інтерфейс** — перелік членів (методів, властивостей), які зобов'язаний мати клас, що оголосив себе його реалізацією. Тіла в інтерфейсі немає, полів немає, стану немає. Є тільки обіцянка.

```csharp
// Фрагмент для аналізу. Інтерфейс не містить ані полів, ані тіл методів.
public interface IRepairCostCalculable
{
    decimal CalculateCost();
    int EstimatedDays { get; }
}
```

Слово **контракт** тут не метафора, а точний опис: контракт має дві сторони.

| Сторона | Що вона отримує | Що вона зобов'язана |
|---|---|---|
| Клас, який реалізує інтерфейс | право бути переданим усюди, де очікують цей інтерфейс | мати всі перелічені члени з тими самими іменами й типами |
| Код, який користується інтерфейсом | гарантію, що перелічені члени є і їх можна викликати | не розраховувати ні на що, крім перелічених членів |

Друге зобов'язання порушують найчастіше: якщо змінна оголошена як `IRepairCostCalculable`, викликати через неї `PrintWarrantyCard()` не можна, навіть якщо ви точно знаєте, що зараз там лежить гарантійна заявка — контракт про цей метод нічого не обіцяв. Чого інтерфейс **не** гарантує — теж треба знати напам'ять:

| Інтерфейс гарантує | Інтерфейс не гарантує |
|---|---|
| що метод із таким іменем і такою сигнатурою є | що він робить саме те, що ви уявляєте |
| що його можна викликати, не знаючи конкретного класу | що він працює швидко чи не кине виняток |
| що всі реалізації взаємозамінні за формою | що всі реалізації однаково коректні за змістом |

Звідси практичний висновок: інтерфейс без опису очікуваної поведінки — половина контракту. Другу половину пишуть коментарем над членом: що приймаємо, що повертаємо, коли кидаємо виняток. Саме тому в завданнях цього заняття від вас вимагатимуть не лише перелік методів, а й короткий опис обіцянки кожного з них.

### 4. Абстрактний клас проти інтерфейсу

Обидва інструменти дають змогу писати код, який працює з різними класами однаково. Різниця — у тому, що саме вони описують.

| Ознака | Абстрактний клас | Інтерфейс |
|---|---|---|
| Що описує | що об'єкт **є** | що об'єкт **вміє** |
| Може містити поля зі станом | так | ні |
| Може містити конструктор | так | ні |
| Може містити готові методи з тілом | так | лише як реалізацію за замовчуванням, у навчальному проєкті — не використовуємо |
| Скільки таких можна успадкувати одному класу | рівно один | скільки завгодно |
| Модифікатори доступу в членах | будь-які | члени завжди відкриті |
| Типова назва | іменник: `ServiceRequest`, `Employee` | прикметник або «вміння»: `IComparable`, `IPrintable`, `IStorage` |
| Що дає нащадку | і зобов'язання, і готовий спільний код | лише зобов'язання |
| Коли додати новий член | нащадки продовжують компілюватися, якщо член має тіло | усі реалізації одразу перестають компілюватися |

Останній рядок важливіший, ніж здається. Додати метод в інтерфейс, який реалізують п'ять класів, — це п'ять місць, де треба дописати код. Тому інтерфейс проєктують вужчим, ніж хочеться спочатку.

**Правило вибору**, якого достатньо для навчального проєкту:

1. Об'єкти однієї природи, мають спільні поля й спільний код — **абстрактний клас**. Перевірка: між класами можна поставити слово «є різновидом».
2. Об'єкти різної природи, але мають спільне вміння — **інтерфейс**. Перевірка: між класом і абстракцією можна поставити слово «вміє».
3. Треба і те, і те — **абстрактний клас плюс інтерфейс**. Це нормально й трапляється часто: `ServiceRequest` є абстрактним класом, а `IComparable` до нього додається окремо.
4. Сумніваєтесь між ними, і спільного коду немає — беріть інтерфейс. Його легше замінити пізніше, бо він не займає єдину «клітинку» спадкування.

Приклад застосування правила на демонстраційній темі:

| Поняття | Рішення | Обґрунтування одним реченням |
|---|---|---|
| Заявка на ремонт | абстрактний клас | гарантійний ремонт **є різновидом** заявки, у всіх спільні номер, клієнт, дата |
| Порівнянність за датою | інтерфейс `IComparable` | заявка **вміє** порівнюватися, і так само вміє співробітник, який заявкою не є |
| Сховище заявок | інтерфейс | у файлі й у пам'яті — різна природа, спільного коду нема, спільне лише вміння зберігати |
| Здатність друкувати квитанцію | інтерфейс | квитанцію друкує і заявка, і акт списання обладнання — це різні ієрархії |
| Клієнт сервісу | звичайний клас | «просто клієнт» — нормальний об'єкт, різновидів не потребує |

### 5. Один інтерфейс — кілька реалізацій

Це головна причина, заради якої інтерфейси взагалі вводять у навчальний проєкт. Розглянемо її на прикладі сховища заявок — без повного коду, тільки як опис ролей.

Нехай оголошено інтерфейс `IRequestStorage` з чотирма обіцянками:

| Член інтерфейсу | Що обіцяє |
|---|---|
| `Save(request)` | зберегти заявку; якщо заявка з таким номером уже є — замінити її |
| `LoadAll()` | повернути список усіх збережених заявок; якщо їх немає — порожній список, а не `null` |
| `Delete(number)` | видалити заявку із заданим номером; повернути `true`, якщо було що видаляти |
| `Count` | скільки заявок зараз у сховищі |

Тепер дві різні реалізації цього контракту.

**Реалізація перша — сховище у файлі.** Усередині тримає шлях до CSV-файлу. `Save` дописує або переписує рядок файлу, `LoadAll` читає файл цілком і розбирає рядки, `Delete` перечитує файл і записує його без одного рядка, `Count` рахує рядки. Працює повільно, залежить від диска, може кинути виняток, якщо файл зайнятий або папки не існує. Зате дані переживають завершення програми.

**Реалізація друга — сховище в пам'яті.** Усередині тримає `List` заявок. `Save` шукає заявку з таким номером і замінює або додає, `LoadAll` повертає копію списку, `Delete` видаляє елемент, `Count` повертає довжину списку. Працює миттєво, ніколи не звертається до диска, ніколи не кидає файлових винятків. Зате все зникає після закриття програми.

Тепер найважливіше. Меню програми, звіти, пошук, редагування — увесь код, який працює із заявками, оголошує змінну типу `IRequestStorage` і не знає, яка з двох реалізацій йому дісталася. Що це дає на практиці:

| Що змінюється | Що доводиться переписати |
|---|---|
| перехід із файлу на базу даних у другому семестрі | тільки новий клас-реалізацію; меню й звіти не чіпаємо |
| перевірка звітів без справжніх даних | підставляємо сховище в пам'яті, наповнюємо трьома тестовими заявками |
| демонстрація проєкту на чужому комп'ютері, де немає файлу з даними | підставляємо сховище в пам'яті, програма працює |
| виправлення помилки в розборі CSV | правимо один клас, решта програми навіть не перекомпільовується концептуально |

Схема залежностей виглядає так:

```
        ┌──────────────────────────┐
        │   Меню, звіти, пошук     │
        │   (логіка програми)      │
        └────────────┬─────────────┘
                     │ знає ТІЛЬКИ про контракт
                     ▼
        ┌──────────────────────────┐
        │   IRequestStorage        │   ← контракт
        │   Save / LoadAll /       │
        │   Delete / Count         │
        └────────┬────────┬────────┘
                 │        │  реалізують контракт
        ┌────────▼──┐  ┌──▼─────────────┐
        │ FileStor. │  │ InMemoryStor.  │
        │ (CSV)     │  │ (List)         │
        └───────────┘  └────────────────┘
```

Зверніть увагу на напрямок стрілок: логіка вказує на контракт, і реалізації теж вказують на контракт. Логіка й реалізація не з'єднані між собою напряму. До цієї схеми ми повернемося в підрозділі про інверсію залежностей.

### 6. П'ять принципів SOLID

**SOLID** — набір із п'яти принципів проєктування класів. Назва складена з перших літер англійських назв принципів. Це не правила мови й не те, що перевіряє компілятор: це поради, які пояснюють, чому один варіант поділу на класи виявляється зручнішим за інший, коли програму доводиться змінювати.

#### 6.1. S — принцип єдиної відповідальності

**Формулювання простою мовою:** у класу має бути одна причина для зміни.

Причина для зміни — це не «одна дія», а «одна зацікавлена сторона». Якщо клас доведеться правити і тоді, коли змінили формат файлу, і тоді, коли змінили правила нарахування вартості, і тоді, коли захотіли інший вигляд меню, — у нього три причини для зміни, а має бути одна.

**Погано.** Клас `ServiceRequest` містить: поля заявки, метод `CalculateCost()`, метод `SaveToFile(path)`, метод `PrintMenu()`, метод `ReadFromConsole()`. Такий клас змінюють усі: і бухгалтерія, і той, хто відповідає за формат файлу, і той, хто малює меню. Зміна формату CSV змушує чіпати той самий файл, у якому лежить формула вартості, — і випадково зламати формулу.

**Краще.** Три класи замість одного:

| Клас | Відповідальність | Хто змушує його змінюватися |
|---|---|---|
| `ServiceRequest` | зберігати дані заявки й рахувати її вартість | зміна правил обліку заявок |
| `FileRequestStorage` | читати й писати заявки у файл | зміна формату зберігання |
| `RequestMenu` | питати користувача і показувати результат | зміна сценарію роботи з користувачем |

Проста перевірка на занятті: спробуйте описати, що робить клас, одним реченням без слова «і». Якщо без «і» не виходить — відповідальностей більше однієї.

#### 6.2. O — принцип відкритості-закритості

**Формулювання простою мовою:** клас має бути відкритим для розширення й закритим для змін. Додавання нового різновиду не повинно змушувати правити вже написаний і вже перевірений код.

**Погано.** Вартість рахує один метод з перебором типів:

```csharp
// Фрагмент для аналізу: кожен новий різновид — правка цього методу.
public decimal CalculateCost(ServiceRequest request)
{
    if (request.Kind == "Гарантійний") return 0m;
    if (request.Kind == "Платний") return request.WorkCost + request.PartsCost;
    if (request.Kind == "Діагностика") return 250m;
    return 0m;   // а це взагалі що таке?
}
```

Тут дві біди. Перша: щоб додати виїзний ремонт, треба відкрити цей метод і дописати рядок — а він уже працює й перевірений. Друга: такий самий перебір неминуче з'явиться і в методі терміну виконання, і в методі друку квитанції, і рано чи пізно вони розійдуться між собою.

**Краще.** Абстрактний метод `CalculateCost()` у базовому класі та його реалізація в кожному нащадку. Додавання виїзного ремонту — це новий файл із новим класом; жоден наявний клас не змінюється. Код, який рахує суму по всіх заявках, залишається тим самим назавжди.

| Питання | Варіант з перебором типів | Варіант з абстрактним методом |
|---|---|---|
| Скільки файлів правити, щоб додати різновид | стільки, скільки є переборів | нуль, лише додати один новий |
| Чи можна зламати перевірений код | так | ні |
| Чи може компілятор нагадати про забутий різновид | ні | так, нащадок не скомпілюється без реалізації |

#### 6.3. L — принцип підстановки Лісков

**Формулювання простою мовою:** якщо код працює з базовим типом, то будь-який нащадок має підійти на його місце, не ламаючи очікувань.

Нащадок не повинен: кидати виняток там, де базовий клас нормально відпрацьовував; повертати значення, які базовий контракт забороняв; вимагати більше, ніж вимагав базовий.

**Погано.** У базовому класі `ServiceRequest` є метод `AddPart(part)` — додати запчастину. У нащадка «Діагностика» запчастин не буває, і автор пише реалізацію, яка кидає виняток «діагностика не використовує запчастин». Тепер будь-який цикл, що проходить списком заявок і додає запчастину, аварійно завершується, щойно натрапить на діагностику. Формально ієрархія правильна, практично — нащадок не підставляється замість базового.

**Краще.** Робота із запчастинами — не спільна властивість усіх заявок, а окреме вміння. Її виносять в інтерфейс `IUsesParts`, який реалізують гарантійний і платний ремонт, а діагностика — ні. Код, якому потрібні запчастини, працює з `IUsesParts` і просто не отримує діагностику у свій список.

Ознаки порушення, які легко помітити в чужому описі класу:

| Ознака в коді нащадка | Про що свідчить |
|---|---|
| перевизначений метод складається з кидання винятку | метод не належить базовому класу |
| перевизначений метод порожній, «щоб нічого не робив» | те саме |
| перед викликом методу доводиться перевіряти, який це насправді нащадок | базовий контракт описано неправильно |
| нащадок звужує допустимі вхідні дані | порушення в чистому вигляді |

#### 6.4. I — принцип розділення інтерфейсів

**Формулювання простою мовою:** краще кілька вузьких інтерфейсів, ніж один широкий. Клас не повинен бути змушений реалізовувати те, що йому не потрібно.

**Погано.** Один інтерфейс `IEntity` з членами: `Save`, `Load`, `Delete`, `Print`, `ExportToCsv`, `SendByEmail`, `Validate`. Клас «Клієнт» реалізує його й змушений написати `SendByEmail`, яка нічого не робить, бо клієнтам нічого не надсилають. Порожня реалізація — це брехня в контракті, і вона одразу тягне за собою порушення принципу Лісков.

**Краще.** Три вузькі контракти: `IPrintable` (`Print`), `ICsvSerializable` (`ToCsvLine`, `FromCsvLine`), `IValidatable` (`Validate`). Кожен клас реалізує тільки те, що справді вміє. Порожніх методів не залишається.

| Широкий інтерфейс | Набір вузьких |
|---|---|
| один клас змушений мати всі члени | клас бере рівно те, що потрібно |
| порожні реалізації «щоб компілювалося» | порожніх реалізацій немає |
| додавання члена ламає всі класи | ламає лише тих, кому справді потрібен новий член |
| незрозуміло, що обіцяє тип змінної | тип змінної одразу говорить про вміння |

Практичний орієнтир для навчального проєкту: інтерфейс на один-три члени — нормально; інтерфейс на сім членів — привід поділити.

#### 6.5. D — принцип інверсії залежностей

**Формулювання простою мовою:** код, який керує процесом, має залежати від контракту, а не від конкретної реалізації; і навпаки — реалізація має підлаштовуватися під контракт, а не контракт під реалізацію.

**Погано.** Клас меню всередині себе створює файлове сховище:

```csharp
// Фрагмент для аналізу: меню прив'язане і до файлів, і до шляху.
public class RequestMenu
{
    private FileRequestStorage storage = new FileRequestStorage("requests.csv");
    // ...
}
```

Наслідки: меню неможливо перевірити без диска; неможливо тимчасово підмінити сховище на пам'ять; перехід на базу даних означає правку меню.

**Краще.** Меню оголошує потребу в контракті й отримує готове сховище ззовні — через конструктор:

```csharp
// Фрагмент для аналізу. Меню не знає, яке саме сховище йому дали.
public class RequestMenu
{
    private readonly IRequestStorage storage;

    public RequestMenu(IRequestStorage storage)
    {
        this.storage = storage;
    }
}
```

Рішення, яке саме сховище створити, піднімається на один рівень вище — у точку входу програми. Передавання залежності через конструктор називають **впровадженням залежності**.

| Питання | Було: `new` усередині | Стало: параметр конструктора |
|---|---|---|
| Хто вирішує, яке сховище | сам клас меню | точка входу програми |
| Чи можна підставити сховище в пам'яті | ні | так, нічого не змінюючи в меню |
| Чи видно залежність із сигнатури | ні, вона схована | так, конструктор чесно її називає |
| Що правити при зміні сховища | клас меню | один рядок у точці входу |

Слово «інверсія» означає розворот напрямку: раніше верхній рівень залежав від нижнього, тепер обидва залежать від контракту, який належить верхньому рівню.

### 7. Чому в навчальному проєкті вистачає трьох принципів

П'ять принципів народилися у великих промислових системах. У проєкті на 500–800 рядків користь від них дуже різна.

| Принцип | Користь у вашому проєкті | Чому саме так |
|---|---|---|
| Єдина відповідальність | висока, застосовувати обов'язково | без нього все опиняється в одному файлі `Program.cs`, і робота стає некерованою вже на ЛР16 |
| Відкритість-закритість | висока, застосовувати обов'язково | ви будете додавати різновиди й звіти щотижня; перебір типів доведеться правити щоразу |
| Підстановка Лісков | середня, тримати в голові як перевірку | ієрархія у вас неглибока, порушення трапляються рідко, але шукати їх треба вміти |
| Розділення інтерфейсів | низька на цьому обсязі | у вас буде два-три інтерфейси на один-два члени; ділити просто нічого |
| Інверсія залежностей | висока, застосовувати обов'язково | саме вона робить можливими тестові дані, підміну сховища й захист проєкту на чужій машині |

Отже, на лабораторній роботі №15 від вас вимагатимуть свідомого застосування першого, другого й п'ятого принципів. Третій і четвертий треба вміти назвати, пояснити й розпізнати порушення в наведеному описі — це перевірятиметься на контрольних питаннях і на захисті.

## Приклад виконання

**Умова.** Сервісний центр обліковує заявки на ремонт ноутбуків. Заявка має номер, прізвище клієнта, модель пристрою, опис несправності, дату прийому й статус. Заявки бувають трьох родів: гарантійний ремонт (клієнт не платить, потрібен номер гарантійного талона), платний ремонт (вартість складається з вартості робіт і вартості запчастин), діагностика (фіксована вартість 250 грн, запчастини не використовуються). Для кожної заявки треба вміти порахувати підсумкову вартість і очікуваний термін виконання в днях. Заявки треба зберігати; на час розробки зберігання має працювати без файлів. Для журналу потрібен друк короткого рядка про заявку. Крім заявок, у програмі є клієнти, для яких теж потрібен друк короткого рядка в журналі.

Спроєктуйте абстракції: визначте, що стане абстрактним класом, що — інтерфейсом, що — звичайним класом. Обґрунтуйте кожне рішення й перевірте проєкт за трьома основними принципами SOLID.

### Крок 1. Виписати іменники й дієслова з умови

Перше, що роблять при проєктуванні, — розкладають умову на «що є» і «що вміє».

| Іменники (кандидати на класи) | Дієслова (кандидати на члени) |
|---|---|
| заявка, гарантійний ремонт, платний ремонт, діагностика, клієнт, сховище, журнал | порахувати вартість, порахувати термін, зберегти, завантажити, видалити, надрукувати рядок |

### Крок 2. Розділити спільне і власне

| Характеристика | Гарантійний | Платний | Діагностика | Висновок |
|---|---|---|---|---|
| номер, клієнт, модель, несправність, дата, статус | є | є | є | спільні поля — у базовий клас |
| номер гарантійного талона | є | немає | немає | власне поле нащадка |
| вартість робіт і запчастин | немає | є | немає | власні поля нащадка |
| формула вартості | нуль | роботи + запчастини | 250 | у всіх різна — абстрактний метод |
| термін виконання | 14 днів | 5 днів | 1 день | у всіх різний — абстрактний метод |

Спільних полів багато, формули різні, і «просто заявку» без роду в сервісному центрі не приймають. За списком ознак із підрозділу 2 отримуємо: базовий клас робимо абстрактним, обидві формули — абстрактними методами.

### Крок 3. Знайти вміння, які виходять за межі ієрархії

Друк короткого рядка потрібен і заявці, і клієнтові. Клієнт заявкою не є — спільного базового класу немає й бути не повинно. Між «Клієнт» і «друкувати рядок» ставиться слово «вміє», а не «є різновидом». Отже, це інтерфейс.

Так само зі сховищем: файлове сховище й сховище в пам'яті — різної природи, спільного коду в них немає, спільне лише вміння. Інтерфейс.

### Крок 4. Скласти підсумкову таблицю рішень

| Поняття | Рішення | Обґрунтування |
|---|---|---|
| `ServiceRequest` | абстрактний клас | усі заявки одної природи, є спільні поля й спільний код; заявки без роду не буває |
| `WarrantyRequest`, `PaidRequest`, `DiagnosticRequest` | звичайні класи-нащадки | кожен — реальний різновид заявки |
| `Customer` | звичайний клас | «просто клієнт» існує, різновидів умова не вимагає |
| `IJournalPrintable` | інтерфейс, один член `ToJournalLine()` | вміння, спільне для класів із різних ієрархій |
| `IRequestStorage` | інтерфейс: `Save`, `LoadAll`, `Delete`, `Count` | дві реалізації різної природи, спільного коду немає |
| `InMemoryRequestStorage` | звичайний клас | реалізація контракту на списку; умова вимагає роботи без файлів |
| `FileRequestStorage` | звичайний клас | друга реалізація того самого контракту, з'явиться пізніше |
| `RequestMenu` | звичайний клас | відповідає лише за діалог із користувачем |

### Крок 5. Записати контракти словами

Проєкт абстракцій не вважається готовим, поки кожна обіцянка не описана.

| Член | Обіцянка |
|---|---|
| `CalculateCost()` | повертає підсумкову вартість у гривнях; ніколи не повертає від'ємне число |
| `EstimatedDays` | повертає очікуваний термін у днях; завжди більший за нуль |
| `ToJournalLine()` | повертає один рядок без символів переходу на новий рядок; ніколи не повертає `null` |
| `Save(request)` | зберігає заявку; якщо номер уже є — замінює запис; `null` не приймає |
| `LoadAll()` | повертає список усіх заявок; якщо їх немає — порожній список, не `null` |

| `Count` | кількість заявок у сховищі; ніколи не від'ємна |

### Крок 7. Перевірити проєкт за принципами

| Принцип | Перевірка | Результат |
|---|---|---|
| Єдина відповідальність | опишіть кожен клас реченням без «і» | `ServiceRequest` — «зберігає дані заявки й рахує її вартість». Слово «й» є, але обидві дії стосуються тих самих даних і змінюються з однієї причини — правил обліку. Прийнятно. `RequestMenu` — «веде діалог із користувачем». Чисто. |
| Відкритість-закритість | що робити, щоб додати виїзний ремонт | додати один клас-нащадок; жоден наявний клас не змінюється. Виконано |
| Підстановка Лісков | чи є в нащадках методи-заглушки | немає: робота із запчастинами не піднята в базовий клас, вона живе в `PaidRequest`. Виконано |
| Розділення інтерфейсів | чи не змушений хтось реалізовувати зайве | `IJournalPrintable` має один член, `IRequestStorage` — чотири, усі потрібні обом реалізаціям. Виконано |
| Інверсія залежностей | чи створює `RequestMenu` сховище сам | ні, отримує `IRequestStorage` через конструктор; вибір реалізації — у точці входу. Виконано |

### Крок 8. Записати висновок

Проєкт складається з однієї ієрархії (абстрактний клас `ServiceRequest` і три нащадки), двох інтерфейсів (`IJournalPrintable`, `IRequestStorage`), двох реалізацій сховища й двох звичайних класів (`Customer`, `RequestMenu`). Найризикованіше місце — контракт `LoadAll()`: якщо хоча б одна реалізація поверне `null` замість порожнього списку, увесь код звітів доведеться обвішувати перевірками. Тому обіцянку записано в таблиці контрактів окремим рядком і на лабораторній №15 її треба перевірити на обох реалізаціях.

## Завдання для аудиторної роботи

### Завдання 1. Абстрактний клас чи інтерфейс

Умова: міська служба прокату спортивного спорядження обліковує видачі. Видаються велосипеди, самокати, комплекти для скандинавської ходьби й намети. Для кожної видачі треба порахувати вартість (у велосипедів і самокатів — погодинно, у комплектів і наметів — подобово) і суму застави. Велосипеди й самокати перед видачею проходять технічний огляд, а комплекти й намети — ні, натомість їх перевіряють на комплектність. Усе спорядження, а також працівники пункту прокату, мають з'являтися у звіті одним коротким рядком.
