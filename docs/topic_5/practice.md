# Самоперевірка та домашнє завдання

## Питання для самоперевірки

Питання згруповані за підрозділами теми. Відповідайте своїми словами — якщо не виходить,
поверніться до відповідного підрозділу.

### Основні поняття

1. Що таке система контролю версій? Назвіть щонайменше три можливості, які вона дає
   розробнику, і поясніть, як кожна з них рятує в реальній ситуації.
2. Git називають **розподіленою** системою. Що саме розподілене? Чому завдяки цьому
   більшість операцій (`git log`, `git commit`, `git branch`) працюють миттєво навіть
   без інтернету?
3. Назвіть три зони проєкту Git. Через які з них проходить файл на шляху від «я щойно
   його відредагував» до «він назавжди в історії»?
4. Що зберігається в прихованій папці `.git`? Що станеться з проєктом, якщо цю папку
   видалити, а всі інші файли залишити?
5. Із яких трьох частин складається коміт? Навіщо комітові посилання на батьківський
   коміт — хіба недостатньо дати й часу?
6. У лекції гілку названо «рухомою вказівкою на коміт». Чому саме **рухомою**?
   Що відбувається з цією вказівкою після кожного нового коміту?

### Взаємодія з Git

7. Git має три рівні конфігурації: системний, глобальний і локальний. Який із них
   переможе, якщо глобально задано `user.email` "me@gmail.com", а локально в поточному
   репозиторії — "me@company.com"? Під яким email вийде коміт?
8. Чим `git add .` відрізняється від `git commit -m "..."`? Чи потрапить у коміт файл,
   який ви змінили, але не додали до індексу?
9. Ви щойно виконали `git init` у папці, де лежить один файл `Program.cs`.
   Що покаже `git status`? А що він покаже після `git add Program.cs`?
10. Що робить прапорець `-u` у команді `git push -u origin main` і чому наступного разу
    вистачає просто `git push`?
11. Навіщо потрібен `.gitignore`? Чому папки `bin/` та `obj/` у проєкті .NET майже
    завжди туди вносять — вони ж є частиною програми?

### SSH та кілька акаунтів

12. Після `ssh-keygen -t ed25519` з'являються два файли. Який із них ви додаєте
    в налаштування GitHub, а який не показуєте нікому ніколи? Що станеться, якщо
    переплутати?
13. Що перевіряє команда `ssh -T git@github.com` і чому вона не відкриває жодного
    репозиторію?
14. У лекції є команда `git clone git@github-work:company/repo.git`. Хоста з іменем
    `github-work` не існує в інтернеті. Чому команда все одно спрацює?
15. Є два способи розділити робочий і особистий акаунти: через `git config user.email`
    і через окремі SSH-ключі у файлі `~/.ssh/config`. Який із них відповідає за питання
    «хто автор коміту», а який — за питання «чи пустить мене сервер»? Чому зазвичай
    потрібні обидва?

### Конвенції комітів

16. З яких частин складається повідомлення у форматі Conventional Commits? Яка з них
    необов'язкова?
17. Який тип коміту ви поставите, якщо: (а) оновили `.gitignore`; (б) перейменували
    змінні й розбили довгий метод на два, не змінивши поведінку; (в) прискорили запит
    до бази; (г) виправили друкарську помилку в README?
18. Що не так із повідомленням `feat(api): додавання нового ендпоінта`? Перепишіть його
    в імперативному стилі й поясніть правило своїми словами.
19. Що таке `BREAKING CHANGE`, де саме в повідомленні його пишуть і чому цього не можна
    просто написати у звичайному описі?
20. Конвенція комітів дозволяє інструментам автоматично збирати changelog і визначати
    номер версії. Поясніть, яка саме властивість формату робить це можливим —
    чому з повідомлення «fixed stuff» такого не витягнеш?

## Практичні міні-задачі

Короткі вправи на 5–10 хвилин кожна, для перевірки розуміння прямо після лекції.

1. **Три зони власноруч.** Створіть порожню папку, виконайте `git init`, додайте файл
   `hello.txt` і виконуйте `git status` після кожного кроку: після створення файлу,
   після `git add`, після `git commit`. Запишіть, як змінювався текст відповіді,
   і зіставте кожен стан із зоною Git.

2. **Хто автор.** У навчальному репозиторії задайте локально інше ім'я та email
   (`git config --local user.name "Test Student"`), зробіть коміт і подивіться
   `git log`. Потім виконайте `git config --list` і знайдіть, скільки разів у виводі
   зустрічається `user.email` та який рядок переміг.

3. **Гілка за дві хвилини.** Створіть гілку `feature/greeting`, змініть у ній файл,
   закомітьте, поверніться на `main`, злийте гілку і подивіться результат командою
   `git log --oneline --graph --all`. Намалюйте побачене на папері.

4. **Ігнорування в дії.** Додайте у репозиторій папку `bin` з будь-яким файлом
   усередині, виконайте `git status` — файл видно. Створіть `.gitignore` з рядком
   `bin/` і виконайте `git status` ще раз. Поясніть різницю.

5. **Перепишіть коміти.** Перед вами реальна історія студентського проєкту:
   `update`, `fixed stuff`, `final version`, `final version 2`, `works now`.
   Перепишіть усі п'ять повідомлень за Conventional Commits, вигадавши правдоподібний
   зміст змін.

6. **Свій ключ.** Згенеруйте SSH-ключ командою `ssh-keygen -t ed25519 -C "ваш@email"`,
   знайдіть обидва файли в папці `.ssh` і відкрийте публічний у текстовому редакторі.
   Не відкривайте приватний під час демонстрації екрана.

## Домашнє завдання

:::info[Що здавати]
Посилання на репозиторій на GitHub + скриншот історії комітів
(вивід `git log --oneline --graph --all` або вкладка Commits на GitHub).
Орієнтовний час виконання — 30–45 хвилин.
:::

### Завдання: «Мій репозиторій навчальних робіт»

До кінця семестру у вас накопичиться десяток консольних програм, і зараз найкращий
момент завести для них один акуратний репозиторій, а не папку «нове3_final_справжнє».
Ваше завдання — створити такий репозиторій, наповнити його маленькою програмою
і провести її через повний цикл роботи з Git: коміти, гілка, злиття, публікація.

Програма може бути найпростішою — консольне привітання, яке запитує ім'я. Головне тут
не код, а **історія комітів**: вона має читатися як розповідь про те, що відбувалося
з проєктом.

**Вимоги:**

- створити локальний репозиторій, налаштувати `user.name` та `user.email`;
- додати `.gitignore`, у якому ігноруються `bin/` та `obj/` (переконайтеся, що
  скомпільовані файли справді не потрапляють у коміти);
- зробити **щонайменше 5 комітів за Conventional Commits**, і серед них мають бути
  різні типи: хоча б один `feat`, один `fix`, один `docs` і один `chore`;
- створити гілку з осмисленою назвою, наприклад `feature/greeting`, зробити в ній
  1–2 коміти й **злити** її в `main` (гілку після злиття можна залишити);
- додати `README.md` з назвою проєкту, одним абзацом опису і командою для запуску;
- створити репозиторій на GitHub і надіслати туди все командою `git push -u origin main`.

**Приклад роботи:**

```
$ git log --oneline --graph --all
*   9c31f0a (HEAD -> main) Merge branch 'feature/greeting'
|\
| * 4ab77d2 (feature/greeting) feat(app): запам'ятовувати ім'я між запитаннями
| * 1e0b5c9 feat(app): додати персональне привітання за іменем
|/
* 7d2ae41 docs(readme): додати інструкцію із запуску проєкту
* b5590c3 fix(input): обробити порожнє введення імені
* a10c8ef chore(git): додати .gitignore для bin та obj
* 3f4d012 feat(app): створити базовий консольний проєкт

$ git push -u origin main
Enumerating objects: 24, done.
To https://github.com/student/opam-labs.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

:::tip[Підказка]
Якщо `git push` просить логін і пароль, а пароль не підходить — GitHub давно не приймає
звичайний пароль акаунта. Використайте посилання виду `git@github.com:...` і SSH-ключ
із підрозділу про SSH, або створіть у налаштуваннях GitHub персональний токен доступу.

Щоб `.gitignore` подіяв на файли, які вже потрапили в індекс, одного створення файлу
замало — спочатку приберіть їх з індексу: `git rm -r --cached bin obj`.

Гілку створюють і одразу перемикаються на неї однією командою: `git checkout -b ім'я`.
:::

**Додатково (за бажанням, на вищу оцінку):** зробіть у гілці зміну, яка **конфліктує**
з тим, що ви змінили в `main` (наприклад, обидві гілки правлять той самий рядок
привітання). Спробуйте злиття, отримайте конфлікт, розв'яжіть його вручну й завершіть
merge. У README опишіть двома реченнями, що ви побачили у файлі під час конфлікту.
