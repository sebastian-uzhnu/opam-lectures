# Гілки та злиття

Гілки — це та частина Git, заради якої його й обрали розробники всього світу.
Вони дозволяють вести кілька напрямків роботи одночасно, не заважаючи одне одному,
і потім акуратно звести результати докупи.

## Навіщо потрібні гілки

Уявіть, що ви робите лабораторну, і вона вже працює. Тепер треба додати нову
можливість, але ви не впевнені, що вийде. Без гілок є два поганих варіанти:
зіпсувати робочий код або копіювати папку в `лаба_v2_остаточна_ця_точно`.

Гілка розв'язує це елегантно: ви створюєте окрему лінію розробки, експериментуєте
скільки завгодно, і якщо не вийшло — просто видаляєте гілку. Робоча версія
весь цей час залишається недоторканою.

```
          ┌── feature/search ──●───●───┐
          │                            ▼
main ──●──●───────────●──────────────────●── (злито)
```

## Основні команди

### Переглянути гілки

```bash
git branch                  # список локальних гілок
git branch -a               # разом із віддаленими
```

Поточна гілка позначена зірочкою:

```
* main
  feature/search
```

### Створити гілку

```bash
git branch feature/search           # створити
git switch feature/search           # перейти на неї

git switch -c feature/search        # створити і перейти одразу ✅
```

:::note[`switch` чи `checkout`]
Історично для перемикання гілок використовували `git checkout`, і ви постійно
побачите цей варіант у статтях. Проблема в тому, що `checkout` робить занадто
багато різних речей (перемикає гілки, відновлює файли, відділяє HEAD), і це
плутало людей.

З Git 2.23 цю команду розділили на дві зрозуміліші:

| Завдання | Сучасна команда | Стара |
|----------|-----------------|-------|
| Перемкнути гілку | `git switch` | `git checkout` |
| Відновити файл | `git restore` | `git checkout --` |

Обидва варіанти працюють; у нових проєктах пишіть `switch` і `restore`.
:::

### Перейменувати й видалити

```bash
git branch -m нова-назва            # перейменувати поточну
git branch -d feature/search        # видалити (тільки якщо злита)
git branch -D feature/search        # видалити примусово ⚠️
```

:::warning
`-d` (маленька) відмовиться видаляти гілку, у якій є незлиті коміти — це захист.
`-D` (велика) видаляє попри все, і незлиті коміти стають недосяжними.
Використовуйте `-D` лише тоді, коли свідомо відмовляєтеся від роботи в гілці.
:::

## Як іменувати гілки

Назва гілки має пояснювати, що в ній робиться. Загальноприйнята схема —
`тип/короткий-опис`:

| Префікс | Призначення | Приклад |
|---------|-------------|---------|
| `feature/` | Нова можливість | `feature/user-login` |
| `fix/` | Виправлення помилки | `fix/division-by-zero` |
| `docs/` | Документація | `docs/readme-update` |
| `refactor/` | Переробка без зміни поведінки | `refactor/extract-methods` |

Слова розділяють дефісами, використовують латиницю й нижній регістр.

:::tip
Назви на кшталт `test`, `new`, `my-branch`, `fix2` через тиждень нічого не
скажуть навіть вам самим. Гілка живе кілька днів, але історія — роками.
:::

## Злиття (merge)

Коли робота в гілці завершена, її **зливають** в основну.

Порядок дій завжди однаковий: **перейти туди, куди зливаємо**, і злити те,
що зливаємо.

```bash
git switch main                 # 1. перейшли на main
git merge feature/search        # 2. влили в нього гілку
git branch -d feature/search    # 3. прибрали за собою
```

### Два види злиття

**Fast-forward** — якщо в `main` не було нових комітів, Git просто пересуває
вказівник уперед. Нового коміту не створюється.

```
До:    main ──●
                ╲
                 ●───● feature

Після: main ─────────● (просто пересунувся)
```

**Merge commit** — якщо в обох гілках були зміни, Git створює окремий коміт
злиття з двома батьками.

```
        ┌───●───● feature ──┐
main ──●────●───────────────●  ← коміт злиття
```

## Конфлікти злиття

**Конфлікт** виникає, коли в обох гілках змінили **той самий фрагмент того самого
файлу**. Git не може вирішити, чия версія правильна, і чесно передає рішення вам.

:::note
Конфлікт — не поломка й не ваша помилка. Це нормальна частина командної роботи.
Git зупиняється саме тому, що не хоче мовчки втратити чиюсь роботу.
:::

Виглядає це так:

```bash
git merge feature/search
```

```
Auto-merging Program.cs
CONFLICT (content): Merge conflict in Program.cs
Automatic merge failed; fix conflicts and then commit the result.
```

Відкривши файл, ви побачите маркери:

```csharp
<<<<<<< HEAD
Console.WriteLine("Вітаємо у системі!");
=======
Console.WriteLine("Ласкаво просимо!");
>>>>>>> feature/search
```

Що означає кожна частина:

| Маркер | Що це |
|--------|-------|
| `<<<<<<< HEAD` | Початок вашої версії (та гілка, де ви зараз) |
| `=======` | Межа між версіями |
| `>>>>>>> feature/search` | Кінець версії з гілки, яку зливаєте |

### Як розв'язати конфлікт

1. **Відкрити файл** і знайти маркери.
2. **Вирішити**, який варіант правильний — залишити один, обидва або написати новий.
3. **Видалити всі три маркери** (`<<<<<<<`, `=======`, `>>>>>>>`).
4. Зберегти файл, додати його в індекс і завершити злиття:

```bash
git add Program.cs
git commit                       # завершує злиття
```

Після виправлення файл має виглядати як звичайний робочий код:

```csharp
Console.WriteLine("Ласкаво просимо!");
```

:::warning[Найчастіша помилка]
Забути видалити маркери. Рядки `<<<<<<< HEAD` і `=======` — не коментарі,
це звичайний текст у файлі. Залишите їх — код не скомпілюється, а помилка
компілятора буде дуже дивною.

Перед комітом завжди перевіряйте:

```bash
git diff --check
```
:::

### Якщо все пішло не так

Злиття завжди можна скасувати й повернутися до стану до нього:

```bash
git merge --abort
```

Ця команда безпечна: вона відновлює робочу директорію такою, якою вона була
до початку злиття.

## Як уникати конфліктів

Конфлікти неможливо виключити повністю, але їх кількість сильно залежить
від дисципліни:

1. **Оновлюйтеся частіше.** Чим довше гілка живе окремо, тим більше розходження:

   ```bash
   git switch feature/search
   git merge main              # підтягнути свіжий main до себе
   ```

2. **Робіть короткі гілки.** Гілка на два дні конфліктує рідше, ніж на два місяці.

3. **Домовляйтеся в команді**, хто який файл редагує.

4. **Робіть маленькі коміти** — конфлікт у 5 рядках розв'язується за хвилину,
   у 500 рядках — за годину.

## Робота з віддаленими гілками

```bash
git push -u origin feature/search   # надіслати гілку на сервер (уперше)
git push                            # наступні рази

git fetch                           # завантажити зміни, не зливаючи
git pull                            # завантажити і злити одразу
```

:::tip[`fetch` проти `pull`]
`git pull` = `git fetch` + `git merge`. Якщо хочете спочатку **подивитися**,
що змінилося, і лише потім зливати — використовуйте `fetch`, перегляньте
зміни через `git log origin/main`, а потім зливайте свідомо.
:::

## Pull Request

У командній роботі гілки зазвичай зливають не локально, а через **Pull Request**
(на GitHub) або **Merge Request** (на GitLab).

Порядок такий:

1. Створюєте гілку й працюєте в ній.
2. Надсилаєте її на GitHub: `git push -u origin feature/search`.
3. На сайті створюєте Pull Request у `main`.
4. Колеги переглядають зміни, залишають зауваження.
5. Після схвалення гілку зливають кнопкою на сайті.

Сенс у тому, що зміни **проходять перегляд** до потрапляння в основну гілку.
Це і є той код-рев'ю, про який ви чутимете на будь-якій роботі.

:::note[Захищені гілки]
У серйозних проєктах пряма робота з `main` заборонена технічно: сервер
відхиляє `git push` у цю гілку. Єдиний шлях змін — через Pull Request.
Це не бюрократія, а захист від випадкового псування робочої версії.
:::

## Типовий цикл роботи

```bash
# 1. Оновилися
git switch main
git pull

# 2. Створили гілку під задачу
git switch -c feature/calculator

# 3. Попрацювали, зберегли
git add .
git commit -m "feat: додано калькулятор ІМТ"

# 4. Надіслали на сервер
git push -u origin feature/calculator

# 5. Створили Pull Request на GitHub, дочекалися злиття

# 6. Прибрали за собою
git switch main
git pull
git branch -d feature/calculator
```

## Висновок

- **Гілка** — окрема лінія розробки; дозволяє експериментувати, не псуючи
  робочу версію.
- `git switch -c назва` створює гілку й одразу на неї переходить;
  `switch` і `restore` — сучасна заміна перевантаженого `checkout`.
- Щоб злити, треба **перейти в цільову гілку** і виконати `git merge` з назвою
  тієї, яку вливаєте.
- **Конфлікт** виникає при зміні одного фрагмента в обох гілках; його розв'язують
  вручну, обов'язково **видаляючи маркери** `<<<<<<<`, `=======`, `>>>>>>>`.
- `git merge --abort` безпечно скасовує невдале злиття.
- Конфліктів менше, коли гілки **короткі** й часто синхронізуються з `main`.
- У командній роботі зміни потрапляють в основну гілку через **Pull Request**
  із переглядом коду.
