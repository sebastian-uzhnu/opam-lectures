# Методика пошуку помилок

Ви вже знаєте інструменти: точки зупинки, покрокове виконання, вікна Locals,
Watch і Call Stack. Але інструмент сам по собі нікого не рятує — молоток
не будує дім.

Найчастіша картина на лабораторній роботі виглядає так: студент ставить
брейкпойнт на перший рядок `Main`, тисне F10 сорок разів поспіль, дивиться
на числа у вікні Locals і за півгодини закриває Visual Studio з думкою «воно
просто не працює». Причина не в браку знань про дебагер, а в **браку методики**.

Цей підрозділ — саме про методику. Про те, як шукати помилку системно, а не
навмання.

## Три види помилок

| Вид | Коли виявляється | Хто повідомляє | Складність пошуку |
|---|---|---|---|
| **Синтаксична** | під час компіляції | компілятор | низька |
| **Часу виконання** (runtime) | під час роботи | виняток і стек-трейс | середня |
| **Логічна** | не виявляється сама | ніхто | висока |

### Синтаксичні помилки

**Синтаксична помилка** — порушення правил мови: забута крапка з комою,
незакрита дужка, друкарська помилка в назві методу.

```csharp
int count = 10
Console.WriteLine(cout);
```

Програма навіть не скомпілюється. Visual Studio підкреслить проблемні місця
червоним і покаже в вікні Error List: `CS1002: ; expected` і
`CS0103: The name 'cout' does not exist in the current context`.

Це **найкращий вид помилок**: компілятор показує файл, рядок і причину.
Виправлення зазвичай займає секунди.

### Помилки часу виконання

Код синтаксично правильний, компілюється, запускається — і падає.

```csharp
int[] marks = [10, 11, 9];
Console.WriteLine(marks[5]);          // IndexOutOfRangeException

int divisor = 0;
Console.WriteLine(100 / divisor);     // DivideByZeroException

string input = Console.ReadLine();
int number = int.Parse(input);        // FormatException, якщо ввели «абв»
```

Про такі помилки повідомляє **виняток** (exception): програма зупиняється,
Visual Studio показує тип винятку, повідомлення і стек викликів. Теж непогано:
принаймні відомо, **де** зламалося.

### Логічні помилки

Програма компілюється, працює, не падає — і видає **неправильний результат**.

```csharp
double average = 0;
foreach (int mark in marks)
{
    average += mark;
}
Console.WriteLine($"Середній бал: {average}");   // забули поділити на кількість
```

Ніхто не скаржиться. Програма впевнено повідомляє, що середній бал дорівнює 30.
Помилку побачить або уважний користувач, або ніхто.

Логічні помилки найважчі саме тому, що **система мовчить**. У перших двох
випадках хтось (компілятор або середовище виконання) уже зробив за вас
половину роботи — вказав місце. У третьому випадку немає ані місця, ані
підтвердження, що помилка взагалі є. Ви шукаєте чорну кішку в темній кімнаті,
не будучи впевненим, що вона там.

:::info Цікаво
Термін **баг** (bug — комаха) закріпився в 1947 році, коли в релейній
обчислювальній машині Harvard Mark II знайшли метелика, який замкнув контакти.
Оператор вклеїв його в журнал із підписом «перший випадок реального
знайденого бага». Втім, слово «баг» у значенні «дефект у механізмі» вживав
ще Томас Едісон у 1870-х.
:::

## Наукова методика налагодження

Пошук помилки — це маленьке наукове дослідження. У науці метод відомий:
спостереження, гіпотеза, експеримент, висновок. У налагодженні він працює
так само добре.

```
      ┌──────────────────────────────────────────────┐
      │                                              │
      ▼                                              │
 1. ВІДТВОРИТИ                                       │
    Знайти точні кроки, за яких помилка              │
    з'являється ЩОРАЗУ                               │
      │                                              │
      ▼                                              │
 2. ЛОКАЛІЗУВАТИ                                     │
    Звузити ділянку коду, де ховається помилка       │
    (метод половинного ділення)                      │
      │                                              │
      ▼                                              │
 3. ГІПОТЕЗА                                         │
    «Я думаю, що причина в тому, що ...»             │
      │                                              │
      ▼                                              │
 4. ПЕРЕВІРИТИ                          гіпотеза     │
    Брейкпойнт, Watch, лог —            хибна ───────┘
    гіпотеза підтвердилася?
      │ так
      ▼
 5. ВИПРАВИТИ
    Змінити код (одну річ за раз!)
      │
      ▼
 6. ПЕРЕКОНАТИСЯ
    Помилка зникла? Інше не зламалося?
```

Розберімо кожен крок.

### Крок 1. Відтворити

Помилка, яку не вдається відтворити, — це не помилка, а чутка. Перше, що
треба зробити, — знайти **точну послідовність дій**, після якої програма
щоразу поводиться неправильно.

Запишіть відповіді на питання:

- які саме дані вводилися;
- у якому порядку виконувалися дії;
- що очікувалося і що сталося насправді;
- чи повторюється це щоразу чи лише іноді.

Останнє питання найважливіше. Якщо помилка «плаваюча», підозрюйте: неініціалізовані
дані, залежність від часу або від порядку введення, роботу з випадковими
числами без фіксованого seed.

:::warning Обережно
«У мене видає якусь дурницю» — це не опис помилки. Опис помилки звучить так:
«якщо ввести 5 оцінок, серед яких є 0, програма виводить середній бал 12
замість 7,2». Поки ви не сформулювали проблему в такому вигляді, шукати ще
нема чого.
:::

### Крок 2. Локалізувати: метод половинного ділення

Найпотужніша техніка в налагодженні — **метод половинного ділення**
(бінарний пошук у коді). Ідея проста: замість того, щоб проходити 200 рядків
по одному, ставимо брейкпойнт **посередині** і питаємо: дані тут ще правильні?

```
Програма зі 200 рядків, десь помилка
│
├─ Брейкпойнт на рядку 100. Дані правильні?
│     ├── ТАК  ──▶ помилка в рядках 100–200
│     └── НІ   ──▶ помилка в рядках   1–100
│
├─ Брейкпойнт посередині залишку (рядок 150 або 50)
│
└─ Повторюємо, доки ділянка не звузиться до кількох рядків
```

Математика на нашому боці: кожна перевірка вдвічі зменшує зону пошуку.
Щоб знайти помилку серед 1024 рядків, вистачає **десяти** брейкпойнтів.
Проходити по одному рядку означало б до 1024 натискань F10.

Той самий принцип працює і з даними: якщо програма падає на файлі з 10 000
рядків, спробуйте перші 5000. Впало — ділимо далі. Не впало — причина в
другій половині.

:::tip Порада
Для кожної перевірки заздалегідь сформулюйте, **що саме має бути правильним**
у цій точці: «тут `total` має дорівнювати 57, а `count` — 6». Порівняння
з очікуванням дає відповідь за секунду. Просто дивитися на числа й думати
«ну, начебто нормально» — марна витрата часу.
:::

### Крок 3. Сформулювати гіпотезу

Гіпотеза — це **конкретне твердження, яке можна перевірити**.

| Погана гіпотеза | Хороша гіпотеза |
|---|---|
| «Щось не так з масивом» | «`Length` дорівнює 5, а цикл доходить до індексу 5» |
| «Метод не працює» | «`Parse` отримує рядок з пробілом і кидає виняток» |
| «Воно якось дивно рахує» | «`sum` не обнуляється між викликами методу» |

Хороша гіпотеза дає готовий план перевірки. З поганої почати нема з чого.

### Крок 4. Перевірити

Перевірка — це один брейкпойнт, один вираз у Watch або один рядок логу.
Не десять одразу: якщо перевіряти все підряд, ви не зрозумієте, що саме
дало результат.

Якщо гіпотеза не підтвердилася — **це теж результат**. Ви викреслили одну
можливість і звузили пошук. Повертайтеся до кроку 3.

### Крок 5. Виправити одну річ за раз

Найпоширеніша помилка новачка на цьому кроці — «підправлю відразу все, що
виглядає підозріло». Після цього програма починає працювати, але ніхто не
знає чому, а ще три зміни могли непомітно щось зламати.

Правило: **одна зміна — один запуск — одна перевірка**.

### Крок 6. Переконатися

Перевірте не лише той випадок, який падав, а й сусідні:

- порожній ввід;
- один елемент;
- граничні значення (нуль, від'ємні, максимальні);
- те, що працювало раніше.

Останній пункт важливий: виправлення, яке ламає щось інше, називається
**регресією**, і вона зазвичай виявляється в найгірший момент.

## Мінімальний відтворюваний приклад

Коли програма велика, а помилка незрозуміла, є прийом, що діє майже завжди:
**зменшуйте програму, доки помилка не зникне**.

Алгоритм:

1. Скопіюйте проєкт в окрему папку (щоб не зіпсувати оригінал).
2. Видаліть шматок коду, який, на вашу думку, до помилки не причетний.
3. Запустіть. Помилка залишилася?
   - **так** — чудово, видалений шматок ні до чого, видаляйте далі;
   - **ні** — поверніть шматок, видаляйте інший.
4. Повторюйте, доки лишиться 15–30 рядків, які все ще падають.

```
420 рядків, падає
  │ прибрали роботу з файлами
  ▼
280 рядків, падає
  │ прибрали меню і ввід користувача, дані вписали константами
  ▼
 95 рядків, падає
  │ прибрали два класи з трьох
  ▼
 18 рядків, падає  ◀── помилка вже видно неозброєним оком
```

Ефект тут подвійний. По-перше, у двадцяти рядках помилку часто видно просто
очима. По-друге — і це буває навіть частіше — **помилка знаходиться в процесі
скорочення**: викидаючи черговий шматок, ви нарешті уважно його читаєте.

:::tip Порада
Мінімальний приклад — це ще й єдиний правильний спосіб попросити допомоги.
Питання «у мене не працює курсова, подивіться» не має відповіді. Питання
«ось 15 рядків, я очікую 7,2, а отримую 12» отримає відповідь за хвилину —
і від викладача, і на форумі, і від будь-якого однокурсника.
:::

## Метод гумової качечки

**Rubber duck debugging** — техніка з книги «The Pragmatic Programmer»:
поставте на стіл іграшкову качку і **поясніть їй свій код уголос, рядок за
рядком**. Не «загалом що робить програма», а детально: що в цій змінній,
навіщо ця умова, що станеться на наступній ітерації.

Звучить як жарт, працює серйозно. Причини цілком раціональні:

- **Читання очима і промовляння вголос — різні режими мозку.** Читаючи мовчки,
  ви бачите те, що **хотіли** написати. Промовляючи, ви змушені вимовити те,
  що написано насправді.
- **Пояснення вимагає послідовності.** Не можна перескочити через незрозумілий
  рядок, сказавши «ну, тут усе ясно» — доводиться сформулювати, що саме ясно.
- **Слухач без контексту змушує пояснювати все.** Качка не знає вашого
  проєкту, тож не можна відмахнутися.

Момент, коли ви посеред фрази зупиняєтеся зі словами «стоп, а чому тут
плюс?» — і є мета вправи. Качка при цьому не сказала жодного слова.

Замість качки годиться будь-що: сусід по парті, порожня аудиторія, коментар,
який ви пишете до методу, або текст питання на форумі. До речі, значна
частина питань на форумах не публікується саме тому, що відповідь знаходиться
під час написання питання.

## Читання стек-трейсу

Коли програма падає, .NET друкує **стек-трейс** — ланцюжок викликів, який
привів до винятку. Це не страшний текст, який треба гортати, а карта з
адресою помилки.

```
Unhandled exception. System.FormatException: The input string 'дванадцять'
was not in a correct format.
   at System.Number.ThrowOverflowOrFormatException(...)
   at System.Number.ParseInt32(ReadOnlySpan`1 value, ...)
   at System.Int32.Parse(String s)
   at GradeBook.MarkParser.ParseMark(String raw) in C:\Projects\GradeBook\MarkParser.cs:line 23
   at GradeBook.Journal.LoadMarks(String[] lines) in C:\Projects\GradeBook\Journal.cs:line 41
   at GradeBook.Program.Main() in C:\Projects\GradeBook\Program.cs:line 12
```

Читаємо **згори вниз**:

1. **Перший рядок** — тип винятку і повідомлення. Тут одразу видно причину:
   рядок «дванадцять» не є числом.
2. **Верхні кадри** — це код бібліотеки .NET (`System.Number`, `System.Int32`).
   Там помилки майже напевно немає: `int.Parse` працює правильно вже двадцять
   років.
3. **Перший кадр із назвою вашого проєкту й номером рядка** — ось із чого
   треба починати. Тут це `MarkParser.cs:line 23`. Саме туди ставимо
   брейкпойнт.
4. **Нижні кадри** — хто це викликав: `Journal.LoadMarks`, а його — `Main`.
   Вони показують **контекст**: звідки прийшли погані дані.

```
   ▲ бібліотека .NET       ← сюди дивитися не треба
   │ System.Number...
   │ System.Int32.Parse
   ├───────────────────────────────────────────────
   │ MarkParser.ParseMark   MarkParser.cs:23   ◀── ТУТ ставимо брейкпойнт
   │ Journal.LoadMarks      Journal.cs:41      ◀── звідки прийшли дані
   ▼ Program.Main           Program.cs:12      ◀── початок ланцюжка
```

:::tip Порада
У Visual Studio увімкніть **Just My Code** (Tools → Options → Debugging →
Enable Just My Code). Тоді кадри бібліотек у вікні Call Stack згортаються,
і ваш код видно одразу. А ще: якщо в стек-трейсі немає номерів рядків,
перевірте, що збірка йде в конфігурації **Debug**, а не Release.
:::

Не забувайте про **внутрішній виняток** (`InnerException`). Повідомлення
«An error occurred while updating the entries» саме по собі марне — справжня
причина лежить рівнем нижче. У вікні винятку Visual Studio для цього є
посилання **View Details** і рядок `InnerException`.

## Умовні точки зупинки та точки за кількістю влучань

Уявіть цикл на 5000 ітерацій, який ламається десь ближче до кінця. Звичайний
брейкпойнт тут — катування: п'ять тисяч натискань F5.

### Умовна точка зупинки (Conditional Breakpoint)

Правий клік на кружечку брейкпойнта → **Conditions** → **Conditional
Expression** → **Is true**, і пишемо звичайний вираз C#:

```
students[i].Name == null
```

Програма летить на повній швидкості й зупиняється **лише тоді**, коли умова
істинна. Замість п'яти тисяч зупинок — одна, саме та, що потрібна.

Приклади корисних умов:

```
i == 4987                     // конкретна ітерація
balance < 0                   // момент, коли значення стало неправильним
order.Id == 1042              // конкретний об'єкт серед тисяч
name.Contains("Шевч")         // цікавий випадок у даних
```

### Кількість влучань (Hit Count)

Та сама менюшка **Conditions** → **Hit Count**. Варіанти: зупинитися на
конкретному влучанні (`= 4987`), на кожному сотому (`is a multiple of 100`)
або починаючи з певного (`is greater than or equal to 4900`).

Зручно, коли ви не знаєте умову, але знаєте приблизний номер ітерації:
поставте «is greater than or equal to 4900» і далі йдіть кроками.

### Фільтр і дії

- **Filter** — зупинятися лише в певному потоці чи процесі (знадобиться
  в темі про багатопотоковість).
- **Actions** — не зупинятися, а надрукувати повідомлення у вікно Output.
  Це вже знайомий вам **трейспойнт**: свого роду логування без зміни коду.

| Ситуація | Що використати |
|---|---|
| Знаю, за якої умови дані псуються | Conditional Expression |
| Знаю приблизний номер ітерації | Hit Count |
| Треба побачити всі значення, не зупиняючись | Actions (трейспойнт) |
| Треба зупинитися, коли поле об'єкта змінилося | брейкпойнт у сетері властивості |

:::warning Обережно
Умовний брейкпойнт сповільнює програму: середовище обчислює вираз на кожному
проходженні рядка. Для циклу на мільйон ітерацій із важкою умовою чекати
доведеться довго. У такому разі дешевше тимчасово вписати в код
`if (умова) System.Diagnostics.Debugger.Break();` — це зупинить дебагер
у потрібний момент без постійних обчислень.
:::

## Логування замість брейкпойнтів

Брейкпойнти чудові, коли помилка відтворюється тут і зараз. Але вони
безсилі, коли:

- помилка з'являється раз на сто запусків;
- зупинка ламає саму помилку (робота з часом, мережею, кількома потоками);
- програма вже здана і працює в іншого користувача.

У цих випадках потрібне **логування** — запис подій у журнал під час роботи.

### Debug.WriteLine

```csharp
using System.Diagnostics;

Debug.WriteLine($"ParseMark: вхід = '{raw}'");
Debug.WriteLine($"Оброблено {count} записів, сума = {total}");
```

Повідомлення потрапляють у вікно **Output** Visual Studio. Головна перевага:
у конфігурації **Release компілятор викидає ці виклики повністю** — вони не
сповільнюють готову програму й не показують користувачеві службову інформацію.

### Trace

`Trace` виглядає так само, але працює **і в Release**:

```csharp
Trace.WriteLine("Запуск імпорту журналу оцінок");
Trace.TraceWarning("Файл налаштувань не знайдено, використано типові значення");
Trace.TraceError("Не вдалося зберегти журнал");
```

| Клас | Debug-конфігурація | Release-конфігурація | Для чого |
|---|---|---|---|
| `Debug` | працює | вирізається | налагодження під час розробки |
| `Trace` | працює | працює | діагностика в готовій програмі |

### Debug.Assert

**Assert** — це перевірка припущення, яке **завжди** має бути істинним.
Якщо припущення порушено, Visual Studio негайно зупиняє програму і показує
вікно з повідомленням та стеком викликів.

```csharp
static double CalculateAverage(int[] marks)
{
    Debug.Assert(marks != null, "Масив оцінок не може бути null");
    Debug.Assert(marks.Length > 0, "Масив оцінок не може бути порожнім");

    int sum = 0;
    foreach (int mark in marks) sum += mark;

    double result = (double)sum / marks.Length;

    Debug.Assert(result >= 1 && result <= 12, $"Середній бал поза шкалою: {result}");
    return result;
}
```

Assert ловить помилку **в момент її виникнення**, а не через десять методів,
коли неправильне значення вже розповзлося по програмі. У Release всі
`Debug.Assert` зникають, тож вартість нульова.

:::warning Обережно
`Debug.Assert` — це перевірка **помилки програміста**, а не помилки
користувача. Те, що користувач може ввести текст замість числа, — нормальна
ситуація, її обробляють через `if` або `try-catch`. Assert призначений для
випадків «цього не може бути ніколи»: наприклад, кількість елементів стала
від'ємною.
:::

### Умовна компіляція

Директива `#if DEBUG` дозволяє включати цілі блоки коду лише в
Debug-конфігурації:

```csharp
#if DEBUG
    Console.WriteLine("=== Діагностика ===");
    Console.WriteLine($"Завантажено записів: {records.Count}");
    Console.WriteLine($"Час обробки: {stopwatch.ElapsedMilliseconds} мс");
#endif
```

Символ `DEBUG` Visual Studio визначає автоматично для Debug-конфігурації.
У Release цей код навіть не потрапить у скомпільований файл.

### Чому `Console.WriteLine` для налагодження — погана звичка

Спокуса зрозуміла: `Console.WriteLine($"i = {i}")` пишеться швидше, ніж
ставиться брейкпойнт. Але:

1. **Це залишається в готовій програмі.** Користувач бачить `i = 47` посеред
   таблиці оцінок і не розуміє, що відбувається.
2. **Це засмічує реальний вивід.** Корисні повідомлення губляться серед
   службових, і саму програму стає неможливо перевірити.
3. **Це доводиться прибирати руками.** А потім повертати, коли помилка
   повторилася. І знову прибирати. `Debug.WriteLine` не треба прибирати
   ніколи — він зникає сам.
4. **Це сповільнює програму.** Вивід у консоль — повільна операція. Виклик
   у циклі на мільйон ітерацій перетворює секунду на хвилини.
5. **У програмах без консолі це просто не працює.** У застосунках WPF,
   ASP.NET або мобільних консолі немає, а вікно Output є завжди.

Правило просте: **`Console.WriteLine` — для користувача, `Debug.WriteLine` —
для вас**.

## Розбір типових сценаріїв

### Сценарій 1. NullReferenceException

Найпоширеніший виняток у .NET. Повідомлення «Object reference not set to an
instance of an object» означає одне: ви звернулися до члена об'єкта, якого
насправді немає.

```csharp
Student best = students.FirstOrDefault(s => s.Average > 11);
Console.WriteLine(best.Name.ToUpper());   // де саме null?
```

У цьому рядку кандидатів на `null` троє: `best`, `best.Name` і сам `students`.
Як з'ясувати, хто винен:

1. **Прочитайте повідомлення .NET 8.** Сучасна версія часто дописує ім'я:
   `Object reference not set to an instance of an object. Object name: 'best'`.
   У багатьох випадках цього досить.
2. **Розберіть довгий рядок на частини.** Одна з причин, чому «ланцюжки»
   методів незручні при налагодженні:

   ```csharp
   Student best = students.FirstOrDefault(s => s.Average > 11);
   Debug.Assert(best != null, "Відмінників не знайдено");
   string name = best.Name;
   Debug.Assert(name != null, "У студента не заповнене ім'я");
   Console.WriteLine(name.ToUpper());
   ```

   Тепер виняток вкаже конкретний рядок, а Assert назве проблему словами.
3. **Наведіть курсор на кожну частину виразу** в режимі Break Mode —
   Data Tip покаже `null` біля винуватця.
4. **Увімкніть зупинку на кинутому винятку**: Debug → Windows → Exception
   Settings → галочка навпроти `System.NullReferenceException`. Тоді дебагер
   зупиниться **в момент виникнення**, з усіма живими локальними змінними,
   а не після падіння програми.

:::tip Порада
Найкраще — не ловити `NullReferenceException`, а не допускати його. Увімкніть
у файлі проєкту nullable reference types (`enable`), і компілятор попереджатиме
про потенційні `null` ще до запуску. Оператори `?.` і `??` теж допомагають:
`best?.Name ?? "невідомо"` не впаде ніколи.
:::

### Сценарій 2. Програма зависла

Програма запустилася і не реагує. Курсор блимає, вікно біле, нічого не
відбувається. Питання: вона рахує щось довге чи застрягла назавжди?

Порядок дій:

1. **Натисніть паузу** — Debug → Break All (Ctrl+Alt+Break). Дебагер зупинить
   програму там, де вона зараз.
2. **Подивіться, де ви опинилися.** Жовта стрілка покаже рядок. Дев'ять разів
   із десяти це буде цикл.
3. **Відкрийте Call Stack** — зрозумієте, як програма туди потрапила.
4. **Натисніть паузу ще раз через кілька секунд.** Якщо стрілка стоїть на
   тому самому місці й змінні не змінюються — це нескінченний цикл або
   очікування. Якщо змінні змінюються — програма працює, просто повільно.
5. **Перевірте змінні з умови циклу.** Найчастіше винен забутий інкремент або
   умова, яка ніколи не стане хибною (згадайте тему 7).
6. **Відкрийте вікно Threads** (Debug → Windows → Threads). Воно показує
   всі потоки програми. Якщо потоків кілька і кожен чогось чекає, можливе
   **взаємне блокування** (deadlock): перший потік тримає ресурс, потрібний
   другому, а другий — потрібний першому.

| Ознака | Ймовірна причина |
|---|---|
| Стрілка стоїть на місці, змінні не міняються | нескінченний цикл |
| Стрілка в `Console.ReadLine` | програма чекає вводу, а ви не помітили |
| Стрілка всередині мережевого виклику | немає відповіді від сервера чи бази |
| Кілька потоків у стані Waiting | можливий deadlock |
| Змінні змінюються, але дуже повільно | неефективний алгоритм, не баг |

### Сценарій 3. «А на моєму комп'ютері працює»

Класика жанру: у вас усе працює, у викладача програма падає. Причина майже
завжди в одному з чотирьох пунктів.

**Різні дані.** У вас файл із 3 рядками, у викладача — з 3000, причому один
порожній. Перевіряйте граничні випадки: порожній ввід, дуже великі значення,
несподівані символи.

**Різна культура (регіональні налаштування).** Це найпідступніший пункт для
України.

```csharp
double x = double.Parse("3.14");   // у системі з українською культурою — FormatException
```

В українській та більшості європейських культур десятковий роздільник —
**кома**, а в інваріантній та англійській — **крапка**. Програма, написана
на комп'ютері з англійською локаллю, падає на комп'ютері з українською, і
навпаки.

Ліки — задавати культуру явно там, де формат має значення:

```csharp
using System.Globalization;

// для читання та запису файлів і обміну даними — інваріантна культура
double value = double.Parse("3.14", CultureInfo.InvariantCulture);
string text = value.ToString(CultureInfo.InvariantCulture);

// для показу користувачеві — його рідна культура, це правильно
Console.WriteLine($"Ціна: {value:F2}");
```

**Різні шляхи до файлів.** Рядок `"C:\\Users\\Ivan\\Desktop\\data.txt"`
працює лише на вашому комп'ютері. Правильно — відносний шлях або складений:

```csharp
string path = Path.Combine(AppContext.BaseDirectory, "data.txt");
```

`Path.Combine` ще й сам ставить правильний роздільник — це знадобиться,
якщо програму колись запустять на Linux.

**Різне оточення.** Інша версія .NET, відсутній файл конфігурації, папка
`bin` з вашої машини, яку ви скопіювали разом із проєктом. Перевірка: зробіть
Build → Clean Solution, потім Rebuild і запустіть на чистій копії проєкту.

:::warning Обережно
Перед здачею роботи обов'язково зберіть її в конфігурації **Release** і
запустіть з папки. Дуже часто програма, яка чудово працює під дебагером,
у Release поводиться інакше — наприклад, через код, залишений у `#if DEBUG`,
або через те, що дебагер приховував неініціалізовані дані.
:::

## Hot Reload та Edit and Continue

:::tip Порада
У Visual Studio 2022 і .NET 8 працює **Hot Reload** — можливість змінювати
код **прямо під час виконання програми**, без перезапуску. Натисніть кнопку
з іконкою полум'я на панелі налагодження (або Alt+F10), і зміни застосуються
до запущеної програми.

Для чого це в навчальних задачах: ви зупинилися на брейкпойнті, побачили
помилку в рядку нижче, виправили, продовжили — і не треба проходити весь
шлях від початку програми заново. Особливо цінно, коли до помилки ведуть
десять кроків введення даних.

**Edit and Continue** — старша функція з тією ж ідеєю, яка працює саме в
режимі зупинки: правите код у Break Mode і тиснете F5.

Обмеження, про які варто знати: не можна змінювати сигнатуру методу
(параметри, тип повернення), додавати чи видаляти поля класу, змінювати тіло
методу, який зараз на вершині стека викликів, і редагувати код у
Release-конфігурації. Якщо зміна не підтримується, Visual Studio чесно
запропонує перезапустити програму.
:::

## Типові помилки

- **Починати з дебагера, не сформулювавши проблему.** Спершу — точний опис
  «очікував X, отримав Y за таких даних», потім інструменти. Інакше ви просто
  розглядаєте змінні без мети.
- **Проходити всю програму по F10 з першого рядка.** Використовуйте
  половинне ділення: один брейкпойнт посередині відповідає на більше питань,
  ніж сто натискань F10.
- **Виправляти кілька речей одночасно.** Якщо після цього запрацювало,
  ви не дізнаєтеся, що саме було причиною, — і наступного разу помилка
  повернеться.
- **Ігнорувати текст винятку і стек-трейс.** Там уже написано тип помилки,
  повідомлення, файл і номер рядка. Читайте згори вниз і шукайте перший кадр
  зі своїм проєктом.
- **Розкидати `Console.WriteLine` по коду і забувати їх прибрати.**
  Для діагностики існує `Debug.WriteLine`: він пише у вікно Output і повністю
  зникає в Release.
