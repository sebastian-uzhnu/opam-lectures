# Готові засоби .NET

Ми написали власні сортування й пошуки — і це було потрібно, щоб зрозуміти, як воно
влаштоване всередині. Але в реальному коді цикл сортування вручну ви писатимете хіба
що ніколи: у класі `Array` уже є набір готових, ретельно оптимізованих і перевірених
мільйонами програмістів методів. Правило просте: **свою реалізацію пишемо, щоб
навчитися; бібліотечну використовуємо, щоб працювати**.

## Огляд методів класу Array

| Метод | Що робить | Умова застосування |
|---|---|---|
| `Array.Sort` | сортує масив за зростанням | елементи мають бути порівнюваними |
| `Array.Reverse` | перевертає порядок елементів | будь-який масив |
| `Array.IndexOf` | лінійний пошук першого входження | будь-який масив |
| `Array.LastIndexOf` | лінійний пошук останнього входження | будь-який масив |
| `Array.BinarySearch` | бінарний пошук | масив **обов'язково** відсортований |
| `Array.Find` | перший елемент за умовою | будь-який масив |
| `Array.FindIndex` | індекс першого елемента за умовою | будь-який масив |
| `Array.FindAll` | усі елементи за умовою | будь-який масив |
| `Array.Exists` | чи є хоч один елемент за умовою | будь-який масив |
| `Array.Fill` | заповнює масив одним значенням | будь-який масив |

Зверніть увагу: усі ці методи **статичні**, тобто викликаються від імені класу
`Array`, а масив передається аргументом — `Array.Sort(numbers)`, а не `numbers.Sort()`.

## Array.Sort

Найпростіший випадок — відсортувати масив чисел або рядків за зростанням:

```csharp
int[] scores = [42, 7, 91, 15, 63, 7];
Array.Sort(scores);
Console.WriteLine(string.Join(", ", scores));

string[] nicknames = ["zeta", "alpha", "omega", "beta"];
Array.Sort(nicknames);
Console.WriteLine(string.Join(", ", nicknames));
```

Вивід:

```
7, 7, 15, 42, 63, 91
alpha, beta, omega, zeta
```

`Array.Sort` сортує **на місці**: він змінює переданий масив і нічого не повертає.
Якщо оригінал потрібно зберегти — робіть копію заздалегідь.

### Сортування частини масиву

```csharp
int[] data = [9, 8, 7, 100, 50, 75, 1];
Array.Sort(data, 3, 3);   // з індексу 3, три елементи
Console.WriteLine(string.Join(", ", data));
```

Вивід:

```
9, 8, 7, 50, 75, 100, 1
```

Перші три та останній елементи не зачеплено — відсортовано лише вказаний діапазон.

### Сортування двох паралельних масивів

Ось метод, який рятує в задачах на кшталт «рейтингу гравців». Є два масиви однакової
довжини: **ключі** (за чим сортуємо) та **значення** (що переставляємо разом із ключами).
`Array.Sort` уміє переставляти обидва синхронно:

```csharp
string[] players = ["Драйв", "Комета", "Барс", "Вихор"];
int[] points = [1450, 2100, 980, 1730];

Array.Sort(points, players);   // сортуємо ЗА points, players їдуть слідом

for (int i = 0; i < players.Length; i++)
{
    Console.WriteLine($"{players[i],-8} {points[i]}");
}
```

Вивід:

```
Барс     980
Драйв    1450
Вихор    1730
Комета   2100
```

Перший аргумент — масив ключів, другий — масив значень. Порядок переплутати легко,
а помилка тиха: програма відсортує за нікнеймами замість очок і нічого не скаже.

:::danger Часта помилка
`Array.Sort(players, points)` замість `Array.Sort(points, players)` — це сортування
за алфавітом нікнеймів, а не за очками. Компілятор не заперечить, бо обидва виклики
коректні за типами. Запам'ятайте: **першим іде те, ЗА чим сортуємо**.
:::

### Сортування за спаданням

Окремого методу для спадання немає. Найпростіший шлях — відсортувати за зростанням
і перевернути:

```csharp
int[] points = [1450, 2100, 980, 1730];
Array.Sort(points);
Array.Reverse(points);
Console.WriteLine(string.Join(", ", points));
```

Вивід:

```
2100, 1730, 1450, 980
```

`Array.Reverse` теж працює на місці й теж уміє перевертати лише частину масиву:
`Array.Reverse(arr, startIndex, length)`.

## Array.IndexOf та інші «швидкі» пошуки

`Array.IndexOf` — це той самий лінійний пошук, який ми писали власноруч, лише
готовий і на всі типи одразу:

```csharp
string[] players = ["Барс", "Драйв", "Вихор", "Комета", "Драйв"];

Console.WriteLine(Array.IndexOf(players, "Драйв"));      // 1
Console.WriteLine(Array.LastIndexOf(players, "Драйв"));  // 4
Console.WriteLine(Array.IndexOf(players, "Тінь"));       // -1
```

Угода про повернення -1 — та сама, що ми обговорювали в першому підрозділі теми.
Бібліотека дотримується її так само, як і ваш власний код.

## Array.BinarySearch

Бінарний пошук у стандартній реалізації. Працює швидко, але має жорстку умову:

```csharp
int[] scores = [7, 15, 42, 63, 91];   // ВІДСОРТОВАНО за зростанням

int index = Array.BinarySearch(scores, 42);
Console.WriteLine($"42 знайдено на позиції {index}");
```

Вивід:

```
42 знайдено на позиції 2
```

:::warning Обережно
`Array.BinarySearch` на **невідсортованому** масиві не викидає жодного винятку
і не попереджає про проблему. Він просто повертає **сміття**: інколи -1, інколи
випадкове від'ємне число, інколи «правильний» індекс випадково. Виглядає це так,
ніби програма працює, і саме тому баг знаходять пізно й важко.

Правило залізобетонне: перед `Array.BinarySearch` масив **має бути** відсортований
тим самим порядком, у якому шукаємо. Сумніваєтеся — викличте `Array.Sort` перед
пошуком або скористайтеся `Array.IndexOf`.
:::

Продемонструємо саме цю пастку:

```csharp
int[] unsorted = [91, 7, 63, 15, 42];

Console.WriteLine(Array.IndexOf(unsorted, 15));        // лінійний пошук — правильно
Console.WriteLine(Array.BinarySearch(unsorted, 15));   // бінарний — сміття
```

Вивід:

```
3
-1
```

Число 15 стоїть на позиції 3, воно в масиві є — а бінарний пошук стверджує, що його
немає. Жодної помилки, жодного попередження.

### Що означає від'ємний результат

Тут `Array.BinarySearch` поводиться цікавіше за наш саморобний метод: якщо елемента
немає, він повертає не просто -1, а **побітове доповнення індексу**, куди цей елемент
слід було б вставити. Розгортається воно оператором `~` (тильда):

```csharp
int[] scores = [7, 15, 42, 63, 91];

int result = Array.BinarySearch(scores, 50);

if (result >= 0)
{
    Console.WriteLine($"Знайдено на позиції {result}");
}
else
{
    int insertAt = ~result;   // ~ перетворює -4 на 3
    Console.WriteLine($"Не знайдено. Місце для вставки: {insertAt}");
    Console.WriteLine($"50 мало б стояти між {scores[insertAt - 1]} і {scores[insertAt]}");
}
```

Вивід:

```
Не знайдено. Місце для вставки: 3
50 мало б стояти між 42 і 63
```

```
індекси:   0    1    2    3    4
значення:  7   15   42   63   91
                       ^
                       сюди слід вставити 50, отже insertAt = 3
                       метод повернув ~3, тобто -4
```

Це зручно для задач на кшталт «знайти найближче значення» або «вставити в упорядкований
масив, не порушивши порядок».

:::tip Порада
Просте правило читання результату: **результат `>= 0` — знайдено, індекс перед вами;
результат менший за нуль — не знайдено, а `~результат` каже, куди вставляти**.
:::

## Пошук за умовою: Find, FindAll, Exists

`IndexOf` шукає **конкретне значення**. Але частіше треба знайти елемент, який
задовольняє **умову**: перший від'ємний, усі оцінки вище 90, нікнейм довший за
8 символів. Для цього є методи `Find`, `FindIndex`, `FindAll`, `FindLast`, `Exists`,
`TrueForAll` — і всім їм умову передають у вигляді **лямбди**.

### Лямбда за одну хвилину

**Лямбда** — це коротка форма запису умови або обчислення прямо в місці виклику.
Читається так: `параметр => вираз`, а стрілка `=>` читається як «переходить у» або
просто «дає».

```csharp
score => score > 90          // "візьми score і скажи, чи він більший за 90"
name => name.Length > 8      // "візьми name і скажи, чи довший він за 8 символів"
x => x * 2                   // "візьми x і поверни його подвоєним"
```

Тип параметра писати не треба — компілятор виведе його з масиву, до якого метод
застосовано. Якщо масив `int[]`, то `score` буде `int`.

Для перших чотирьох методів у списку лямбда має повертати `bool` — тобто бути **умовою**.
Такі лямбди називають **предикатами**.

:::note
Під капотом лямбда — це компактний запис невеличкого методу, який передається
іншому методу як аргумент. Механізм цього (делегати) ви розбиратимете пізніше.
Поки що цілком достатньо ставитися до лямбди як до «умови у вигляді виразу».
:::

### Приклади

```csharp
int[] points = [1450, 2100, 980, 1730, 640, 2050];

int firstHigh = Array.Find(points, p => p > 2000);
Console.WriteLine($"Перший результат вище 2000: {firstHigh}");

int firstHighIndex = Array.FindIndex(points, p => p > 2000);
Console.WriteLine($"Його індекс: {firstHighIndex}");

int[] allHigh = Array.FindAll(points, p => p > 1500);
Console.WriteLine($"Усі вище 1500: {string.Join(", ", allHigh)}");

bool anyLow = Array.Exists(points, p => p < 700);
Console.WriteLine($"Чи є хтось нижче 700: {anyLow}");

bool allPositive = Array.TrueForAll(points, p => p > 0);
Console.WriteLine($"Усі результати додатні: {allPositive}");
```

Вивід:

```
Перший результат вище 2000: 2100
Його індекс: 1
Усі вище 1500: 2100, 1730, 2050
Чи є хтось нижче 700: 640
Усі результати додатні: True
```

:::danger Часта помилка
`Array.Find` повертає **значення за замовчуванням**, якщо нічого не знайдено:
для `int` це 0, для `string` — `null`. Тобто результат 0 може означати як
«знайдено елемент зі значенням 0», так і «не знайдено нічого». Коли ця різниця
важлива, беріть `Array.FindIndex` — він чесно повертає -1.
:::

## Як .NET розуміє, що «більше», а що «менше»

Виникає питання, повз яке легко проскочити: звідки `Array.Sort` знає, що 7 менше
за 42, а «alpha» стоїть раніше за «beta»? Ми ж не передавали жодного правила.

Відповідь: **типи `int`, `double`, `string`, `DateTime` та інші вбудовані типи
вміють порівнювати самі себе**. У кожного з них є метод `CompareTo`:

```csharp
Console.WriteLine(7.CompareTo(42));            // від'ємне: 7 менше
Console.WriteLine(42.CompareTo(7));            // додатне: 42 більше
Console.WriteLine(42.CompareTo(42));           // 0: рівні
Console.WriteLine("alpha".CompareTo("beta"));  // від'ємне: alpha раніше
```

Вивід:

```
-1
1
0
-1
```

Домовленість про результат `CompareTo` така, і вона однакова в усьому .NET:

| Результат | Означає |
|---|---|
| від'ємне число | поточний елемент має стояти **раніше** |
| нуль | елементи рівні за порядком |
| додатне число | поточний елемент має стояти **пізніше** |

Точні значення (-1 чи -37) значення не мають — важливий лише знак.

### IComparable: «я вмію порівнювати себе»

Формально ця здатність описана **інтерфейсом** `IComparable`. Інтерфейс — це просто
**домовленість**, список того, що тип зобов'язується вміти. `IComparable` містить
рівно один пункт: «маю метод `CompareTo`».

`Array.Sort(arr)` без додаткових аргументів працює лише з типами, які цю домовленість
виконують. Спробуйте відсортувати масив власної структури без `IComparable` — отримаєте
виняток `InvalidOperationException` під час виконання.

Навчити свій тип порівнюватися нескладно:

```csharp
struct Player : IComparable<Player>
{
    public string Nick;
    public int Score;

    // "порівняй мене з іншим гравцем": порівнюємо за очками
    public int CompareTo(Player other) => Score.CompareTo(other.Score);
}

Player[] roster =
[
    new Player { Nick = "Драйв", Score = 1450 },
    new Player { Nick = "Комета", Score = 2100 },
    new Player { Nick = "Барс", Score = 980 }
];

Array.Sort(roster);   // працює, бо Player реалізує IComparable

foreach (Player p in roster)
{
    Console.WriteLine($"{p.Nick,-8} {p.Score}");
}
```

Вивід:

```
Барс     980
Драйв    1450
Комета   2100
```

Зверніть увагу: усередині `CompareTo` ми не пишемо власної логіки порівняння — ми
делегуємо роботу вже наявному `CompareTo` для `int`. Так роблять майже завжди.

### IComparer: «окремий суддя»

`IComparable` вбудовує в тип **один-єдиний** спосіб порівняння. А що робити, коли
той самий масив потрібно сортувати то за очками, то за нікнеймом, то за спаданням?

Для цього існує `IComparer` — **окремий об'єкт-правило**, який передають у `Array.Sort`
другим аргументом. Тип при цьому не змінюється взагалі: правил може бути скільки завгодно.

Найпростіший спосіб створити таке правило — метод `Comparer.Create` з лямбдою:

```csharp
// за очками, від більших до менших
Array.Sort(roster, Comparer<Player>.Create((a, b) => b.Score.CompareTo(a.Score)));

// за нікнеймом за алфавітом
Array.Sort(roster, Comparer<Player>.Create((a, b) => a.Nick.CompareTo(b.Nick)));

// за довжиною нікнейма, а за однакової довжини — за алфавітом
Array.Sort(roster, Comparer<Player>.Create((a, b) =>
{
    int byLength = a.Nick.Length.CompareTo(b.Nick.Length);
    return byLength != 0 ? byLength : a.Nick.CompareTo(b.Nick);
}));
```

Лямбда тут приймає **два** параметри і повертає число за тією ж домовленістю:
від'ємне — `a` раніше, нуль — однаково, додатне — `a` пізніше.

Прийом «поміняти `a` і `b` місцями, щоб отримати спадання» варто запам'ятати. А останній
приклад показує **сортування за двома критеріями в одному правилі**: якщо перше
порівняння дало нуль (елементи рівні), переходимо до другого.

| Що вибрати | Коли | Коли не варто |
|---|---|---|
| `IComparable` (метод `CompareTo` у типі) | є один природний порядок «за замовчуванням» | критеріїв кілька і всі рівноправні |
| `IComparer` (`Comparer.Create`) | критеріїв кілька або порядок залежить від ситуації | тип і так має єдиний очевидний порядок |
| `Array.Sort(keys, items)` | дані лежать у паралельних масивах | дані вже зібрані в один тип |

## Який алгоритм усередині Array.Sort

:::info Цікаво
`Array.Sort` використовує **інтроспективне сортування (introsort)** — гібрид одразу
з трьох алгоритмів, які ми розібрали:

1. Починає зі **швидкого сортування** — воно найшвидше в типовому випадку.
2. Коли підмасив стає коротким (близько 16 елементів), перемикається на **сортування
   вставками** — на малих обсягах воно виграє за рахунок мінімальних накладних витрат.
3. Якщо глибина рекурсії перевищує приблизно `2 log₂ n` (ознака, що дані «невдалі»
   й швидке сортування деградує), перемикається на **пірамідальне сортування (heapsort)**
   з гарантованим `O(n log n)`.

Тобто бібліотека бере найкраще від кожного алгоритму й підстраховується від найгіршого
випадку. Саме тому ваша власна реалізація швидкого сортування майже напевно програє
`Array.Sort` — не через ідею, а через десятки таких деталей.
:::

:::warning Обережно
Одна важлива властивість випливає безпосередньо з цього: `Array.Sort` **не є стійким**.
Швидке та пірамідальне сортування стійкості не забезпечують. Якщо порядок рівних
елементів для вас важливий (пригадайте приклад зі студентами з попереднього підрозділу),
`Array.Sort` не підходить — потрібне сортування злиттям або `OrderBy` з LINQ,
який ви вивчатимете пізніше.
:::

## Порівняння рядків: маленька пастка

`Array.Sort` для масиву рядків за замовчуванням використовує порівняння **з урахуванням
культури** — тобто правил мови, налаштованої в системі. Для української це те, що треба:
літери йдуть у правильному алфавітному порядку.

Але якщо потрібне передбачуване порівняння «за кодами символів», незалежне від
налаштувань комп'ютера, вказують `StringComparison.Ordinal`:

```csharp
string[] words = ["яблуко", "Ананас", "банан"];

Array.Sort(words);
Console.WriteLine(string.Join(", ", words));

Array.Sort(words, (a, b) => string.Compare(a, b, StringComparison.Ordinal));
Console.WriteLine(string.Join(", ", words));
```

Вивід:

```
Ананас, банан, яблуко
Ананас, банан, яблуко
```

Тут результати збіглися, але для змішаних регістрів і різних алфавітів можуть і не
збігтися. Порада проста: сортуєте для показу людині — залишайте культурне порівняння;
для внутрішньої логіки й бінарного пошуку — `Ordinal`.

:::danger Часта помилка
Відсортувати масив одним правилом, а шукати `Array.BinarySearch` за іншим. Наприклад,
відсортували за спаданням, а шукаєте стандартним бінарним пошуком, який очікує
зростання. Результат — те саме тихе сміття. Порядок сортування і порядок пошуку
мають збігатися.
:::

## Типові помилки

- **`Array.Sort` не повертає масив.** `int[] sorted = Array.Sort(arr);` не скомпілюється:
  метод сортує на місці й повертає `void`.
- **Забути, що оригінал зіпсовано.** Після `Array.Sort(arr)` початкового порядку більше
  немає. Потрібен — робіть `(int[])arr.Clone()` до сортування.
- **`Array.BinarySearch` на невідсортованому масиві.** Мовчазне сміття замість помилки.
- **Плутати порядок аргументів у `Array.Sort(keys, items)`.** Першим іде масив, ЗА яким
  сортуємо.
- **Перевіряти результат `Array.Find` на 0 замість використання `FindIndex`.**
  Нуль — це і «не знайдено», і цілком легальне значення елемента.
