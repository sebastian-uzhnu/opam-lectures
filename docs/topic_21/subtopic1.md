# Мова XAML

У попередньому підрозділі ми написали перше вікно й побачили дивний файл
із кутовими дужками, який чомусь перетворюється на C#. Настав час розібратися
з ним як слід: що це за мова, за якими правилами вона працює і чому ми взагалі
описуємо інтерфейс не звичайним кодом.

## XAML — це опис дерева об'єктів

**XAML** (eXtensible Application Markup Language, читається «зáмл») — мова
розмітки на основі XML, призначена для того, щоб **створювати об'єкти
і встановлювати їхні властивості декларативно**.

Слово «декларативно» тут ключове. Порівняйте два способи сказати одне й те саме.

**Імперативно** (наказово) — ви перелічуєте кроки:

> створи кнопку; постав їй текст «Зберегти»; постав ширину 100;
> візьми панель; поклади кнопку в панель

**Декларативно** (описово) — ви описуєте бажаний результат:

> у панелі є кнопка шириною 100 з текстом «Зберегти»

Обидва описи дають однакове дерево об'єктів. Але друге читається як картинка,
а перше — як інструкція.

Найважливіше, що варто зрозуміти: **XAML не робить нічого такого, чого не можна
зробити на C#**. Це не «інша технологія» — це інший запис тих самих дій.
Доведімо це, написавши одне й те саме вікно двома способами.

## Одне вікно, два записи

Ось інтерфейс: заголовок, поле введення й кнопка, складені у вертикальну
панель.

**Варіант перший — XAML:**

```xml
<Window x:Class="XamlDemo.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="Реєстрація" Height="200" Width="320">

    <StackPanel Margin="16">
        <TextBlock Text="Логін:" FontSize="14"/>
        <TextBox x:Name="LoginTextBox" Margin="0,4,0,0"/>
        <Button x:Name="SubmitButton"
                Content="Увійти"
                Margin="0,12,0,0"
                Padding="8,4"/>
    </StackPanel>
</Window>
```

**Варіант другий — той самий інтерфейс на чистому C#**, без жодного XAML:

```csharp
using System.Windows;
using System.Windows.Controls;

namespace XamlDemo;

public class MainWindowInCode : Window
{
    public MainWindowInCode()
    {
        Title = "Реєстрація";
        Height = 200;
        Width = 320;

        var panel = new StackPanel
        {
            Margin = new Thickness(16)
        };

        var label = new TextBlock
        {
            Text = "Логін:",
            FontSize = 14
        };
        panel.Children.Add(label);

        var loginTextBox = new TextBox
        {
            Margin = new Thickness(0, 4, 0, 0)
        };
        panel.Children.Add(loginTextBox);

        var submitButton = new Button
        {
            Content = "Увійти",
            Margin = new Thickness(0, 12, 0, 0),
            Padding = new Thickness(8, 4, 8, 4)
        };
        panel.Children.Add(submitButton);

        Content = panel;   // вміст вікна — наша панель
    }
}
```

Результат ідентичний до пікселя. Але порівняйте самі файли:

| | XAML | C# |
|---|---|---|
| Рядків на цей інтерфейс | 9 | 35 |
| Видно структуру «хто в кому» | одразу, за відступами | треба читати `Add` і шукати змінні |
| Додати елемент у середину | вставити рядок | створити змінну + знайти правильне місце для `Add` |
| Попередній перегляд у Visual Studio | так | ні |
| Дизайнер може редагувати | так | ні |

І це інтерфейс із трьох елементів. У реальному вікні їх тридцять, і різниця
з лінійної стає катастрофічною.

:::info[Цікаво]
Те, що XAML — лише інший запис створення об'єктів, має несподіваний наслідок:
XAML не прив'язаний до інтерфейсу як такого. Ним можна описати будь-який
об'єктний граф — і його справді використовують не тільки у WPF: у .NET MAUI,
Avalonia, Windows App SDK та навіть у описах робочих процесів. Мова та сама,
набір класів різний.
:::

## Основне правило: тег — це клас, атрибут — це властивість

Запам'ятайте одне речення, і половина синтаксису XAML стане очевидною:

> **Кожен елемент розмітки — це виклик конструктора класу без параметрів.
> Кожен атрибут — це присвоєння однойменної властивості.**

```
XAML                                    C#
─────────────────────────────────       ────────────────────────────────
<Button                             ──▶ var b = new Button();
    Content="Зберегти"              ──▶ b.Content = "Зберегти";
    Width="120"                     ──▶ b.Width = 120;
    FontSize="14"/>                 ──▶ b.FontSize = 14;
```

Звідси одразу випливають правила, яких ніде окремо не пишуть, але які
діють завжди:

- **Імена чутливі до регістру.** `<button>` не існує, є `<Button>`. `content`
  не існує, є `Content`. Це не XML з HTML-поблажками, це рівно імена класів
  і властивостей .NET.
- **Клас має мати конструктор без параметрів.** Саме тому в XAML не буває
  тегів для класів, які без аргументів створити неможливо.
- **Написати можна тільки те, що існує.** Якщо у класу `Button` немає
  властивості `Color`, рядок `Color="Red"` не скомпілюється. Список
  доступних властивостей підказує IntelliSense — користуйтеся ним.

Значення атрибутів у XAML завжди записані в лапках як рядок — навіть числа
й логічні значення. Перетворення рядка на потрібний тип виконує платформа
через **конвертери типів**: рядок `"120"` стає `double`, `"True"` стає `bool`,
`"DarkGreen"` стає `SolidColorBrush`, `"16,8,16,8"` стає структурою `Thickness`.

## Вкладеність: хто в кому

Друге правило таке ж просте:

> **Вкладений тег — це вміст зовнішнього об'єкта.**

```xml
<StackPanel>
    <TextBlock Text="Перший"/>
    <TextBlock Text="Другий"/>
</StackPanel>
```

перетворюється на додавання обох написів у колекцію `Children` панелі.

Тут ховається важлива відмінність, яку студенти часто не помічають:

- **Панелі** (`StackPanel`, `Grid`, `DockPanel`…) мають властивість `Children`
  і можуть містити **скільки завгодно** дочірніх елементів.
- **Вікно** (`Window`) і більшість елементів керування (`Button`, `Border`)
  мають властивість `Content` і можуть містити **рівно один** елемент.

```
Window
  └── Content: рівно один елемент
        │
        └── StackPanel
              └── Children: скільки завгодно
                    ├── TextBlock
                    ├── TextBox
                    └── Button
```

:::danger[Часта помилка]
Покласти у вікно два елементи підряд:

```xml
<Window ...>
    <TextBlock Text="Перший"/>
    <Button Content="Друга"/>
</Window>
```

Помилка збірки: `The property 'Content' is set more than once`. Вікно вміщує
один елемент. Розв'язання завжди одне: спочатку покласти у вікно **панель**,
а вже в неї — усе решта. Саме тому шаблон Visual Studio одразу створює
порожній `Grid` усередині `Window`.
:::

Цікаво, що `Content` — не обов'язково елемент інтерфейсу. У кнопку можна
покласти що завгодно, зокрема іншу панель:

```xml
<Button Padding="10">
    <StackPanel>
        <TextBlock Text="Зберегти" FontWeight="Bold"/>
        <TextBlock Text="Ctrl+S" FontSize="10" Foreground="Gray"/>
    </StackPanel>
</Button>
```

Це кнопка з двома рядками тексту різного розміру. У растрових технологіях
таке потребувало б малювання вручну; тут це три рядки розмітки. Ось що мають
на увазі, коли кажуть, що WPF «складається» з елементів.

## Шапка вікна: розбираємо кожен рядок

Тепер повернімося до того страхітливого початку файлу й розберемо його
рядок за рядком.

```xml
<Window x:Class="XamlDemo.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
        xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
        xmlns:local="clr-namespace:XamlDemo"
        mc:Ignorable="d"
        Title="Реєстрація" Height="200" Width="320">
```

**`x:Class="XamlDemo.MainWindow"`**

Зв'язок розмітки з кодом. Каже компілятору: «згенеруй другу половину
`partial`-класу `XamlDemo.MainWindow`». Ім'я має точно збігатися з простором
імен і класом у файлі code-behind. Якщо ви перейменували клас у C#,
а тут не виправили — збірка впаде.

**`xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"`**

**Простір імен XML за замовчуванням.** Незважаючи на вигляд, це не адреса
в інтернеті: браузер за нею нічого не покаже, і працює все офлайн. Це просто
унікальний рядок-ідентифікатор, за яким компілятор розуміє, у яких просторах
імен .NET шукати класи.

Саме цей рядок означає: «усі теги без префікса — це елементи WPF». Завдяки
йому `<Button>` знаходиться в `System.Windows.Controls`, `<Window>` —
в `System.Windows`, `<SolidColorBrush>` — в `System.Windows.Media`, і вам
не треба писати жодного `using`.

**`xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"`**

Другий простір імен, із префіксом `x`. У ньому не елементи інтерфейсу,
а **службові конструкції самої мови XAML**: `x:Class`, `x:Name`, `x:Key`,
`x:Static`, `x:Type`. Правило запам'ятовується так: **усе, що починається
з `x:` — це вказівка компілятору, а не властивість елемента**.

**`xmlns:d=...` та `xmlns:mc=...`**

Простори імен для **дизайнера**. Вони дозволяють задавати властивості, які
діють лише в режимі попереднього перегляду у Visual Studio і зникають
у зібраній програмі, — наприклад, підставні дані, щоб порожній список
у дизайнері не виглядав порожнім.

Атрибут **`mc:Ignorable="d"`** каже: «усе з префіксом `d` під час виконання
ігнорувати». Ці два рядки можна спокійно видалити, якщо ви ними не
користуєтеся, — нічого не зламається. Але й залишити їх не шкідливо.

**`xmlns:local="clr-namespace:XamlDemo"`**

Ось це вже цікаво: простір імен, що вказує на **ваш власний код**.
`clr-namespace:XamlDemo` означає «простір імен `XamlDemo` у цій самій збірці».
Завдяки цьому рядку ви можете використовувати в розмітці свої класи:

```xml
<local:ColorPickerControl Width="200"/>
```

Префікс `local` — не ключове слово, це просто ім'я, яке обрав шаблон.
Могло бути `my`, `app`, `ui` — байдуже, аби послідовно.

**`Title`, `Height`, `Width`**

А оце вже звичайні властивості класу `Window`, без жодної магії.

| Атрибут | Що це насправді |
|---|---|
| `x:Class` | інструкція компілятору: з яким класом пов'язана розмітка |
| `xmlns` | де шукати класи для тегів без префікса |
| `xmlns:x` | службові конструкції мови XAML |
| `xmlns:d`, `xmlns:mc` | тільки для дизайнера, у програмі не діють |
| `xmlns:local` | ваші власні класи з цього проєкту |
| `Title`, `Width`, … | звичайні властивості об'єкта |

:::tip[Порада]
Шапку вікна не набирають руками й не запам'ятовують напам'ять. Її генерує
шаблон, і за півроку роботи вона просто перестає привертати увагу. Але один
раз розібратися варто — бо коли компілятор скаже
`The type 'local:Foo' was not found`, ви знатимете, куди дивитися.
:::

## Властивості-елементи

Атрибут — це рядок у лапках. А що робити, коли значення властивості —
не рядок, а цілий об'єкт із власними властивостями?

Наприклад, ми хочемо залити кнопку не суцільним кольором, а градієнтом.
Градієнт описується класом `LinearGradientBrush`, у якого є колекція
опорних точок. У рядок таке не запишеш.

Для цього існує **синтаксис властивості-елемента**: властивість записують
не атрибутом, а вкладеним тегом у форматі `ІмʼяКласу.ІмʼяВластивості`.

```xml
<Button Content="Градієнтна" Width="160" Height="48">
    <Button.Background>
        <LinearGradientBrush StartPoint="0,0" EndPoint="0,1">
            <GradientStop Color="#FF7BB2F0" Offset="0"/>
            <GradientStop Color="#FF1E5AA8" Offset="1"/>
        </LinearGradientBrush>
    </Button.Background>
</Button>
```

Читається так: «у кнопки властивість `Background` дорівнює ось цьому
об'єкту `LinearGradientBrush`, а в нього всередині дві опорні точки».

Ось той самий запис на C#, щоб остаточно зникла магія:

```csharp
var brush = new LinearGradientBrush
{
    StartPoint = new Point(0, 0),
    EndPoint = new Point(0, 1)
};
brush.GradientStops.Add(new GradientStop(Color.FromRgb(0x7B, 0xB2, 0xF0), 0));
brush.GradientStops.Add(new GradientStop(Color.FromRgb(0x1E, 0x5A, 0xA8), 1));

SaveButton.Background = brush;
```

**Коли без властивості-елемента не обійтися:**

1. Значення — складний об'єкт (пензель, шаблон, стиль, анімація).
2. Значення — колекція. Наприклад, рядки таблиці `Grid`:

```xml
<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto"/>
        <RowDefinition Height="*"/>
    </Grid.RowDefinitions>
    <!-- далі елементи -->
</Grid>
```

3. Значення — багаторядковий текст, у якому є переноси.

Зверніть увагу на важливу деталь: `<Grid.RowDefinitions>` — **не дочірній
елемент** сітки. Це її властивість, просто записана тегом. Тому вона
не займає місця на екрані й не вважається одним із елементів, розкладених
по комірках.

:::warning[Обережно]
У назві властивості-елемента крапка відокремлює **клас**, якому належить
властивість, від імені властивості. `<Grid.RowDefinitions>` — правильно,
`<RowDefinitions>` — помилка «тип не знайдено». І цей тег має бути
безпосередньо всередині того самого `<Grid>`, властивістю якого він є.
:::

## Розширення розмітки

Іноді значення атрибута не можна записати ані текстом, ані вкладеним тегом —
бо його ще немає на момент написання розмітки. Наприклад: «візьми колір
із ресурсів застосунку» або «показуй тут поточне значення властивості
об'єкта, і оновлюй, коли воно змінюється».

Для таких випадків у XAML є **розширення розмітки** (markup extensions).
Зовні вони виглядають як текст у фігурних дужках усередині лапок:

```xml
<TextBlock Text="{Binding UserName}"/>
<Button Background="{StaticResource AccentBrush}"/>
<TextBlock Text="{x:Static local:AppInfo.Version}"/>
```

Що там усередині — це не рядок, а команда компілятору: «не присвоюй текст,
а створи спеціальний об'єкт, який сам обчислить значення».

Три найпоширеніші розширення:

| Розширення | Що робить | Коли вивчаємо |
|---|---|---|
| `StaticResource` | підставляє ресурс (колір, стиль, шрифт) за ключем | тема 22 |
| `Binding` | прив'язує властивість до даних і стежить за змінами | тема 24 |
| `x:Static` | підставляє значення статичного поля або властивості з C# | за потреби |

Зараз просто впізнавайте цей запис і не лякайтеся його в чужому коді.
Найважливіше з них — `Binding` — стане окремою великою темою, і саме воно
перетворить ваші вікна з «розмальованих кнопок» на справжні застосунки.

:::note
Якщо вам справді потрібно вивести текст, що починається з фігурної дужки
(наприклад, фрагмент JSON), платформа сприйме його як розширення розмітки
і видасть помилку. Рятує спеціальна екранувальна послідовність: перед таким
текстом ставлять порожню пару фігурних дужок — `Text="{}{ось текст}"`.
Трапляється рідко, але знати варто.
:::

## Приєднані властивості

Ось конструкція, яка вперше виглядає нелогічно:

```xml
<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto"/>
        <RowDefinition Height="Auto"/>
    </Grid.RowDefinitions>

    <TextBlock Grid.Row="0" Text="Логін"/>
    <TextBox   Grid.Row="1"/>
</Grid>
```

Питання: чому на `TextBlock` написано `Grid.Row`? Адже `Grid` — це клас
сітки, а не напису. У класі `TextBlock` немає властивості `Row` — можете
перевірити в документації, її там справді немає.

І це не помилка. Це **приєднана властивість** (attached property) — механізм,
який дозволяє одному класу «чіпляти» додаткові дані на чужі об'єкти.

Логіка така. Номер рядка — це не характеристика напису. Напис не знає
і не має знати, що він живе в сітці: покладіть його в `StackPanel`, і жодного
рядка не буде. Номер рядка — це характеристика **відносин** між написом
і його батьківською сіткою. Володіє цією інформацією сітка, а стосується
вона дитини.

```
   Кому належить властивість         На кому записана
 ┌──────────────────────────┐     ┌──────────────────────────┐
 │  клас Grid               │     │  конкретний TextBlock    │
 │  визначає правила:       │     │                          │
 │  "у якому рядку          │────▶│  Grid.Row = 0            │
 │   розташувати дитину"    │     │  Grid.Column = 1         │
 └──────────────────────────┘     └──────────────────────────┘
        визначає                      зберігає значення
```

Запис `Grid.Row="0"` читається як «властивість `Row`, яку визначив клас
`Grid`, для цього елемента дорівнює нулю». Коли сітка розкладатиме дітей,
вона в кожної спитає це значення — і поставить, куди сказано.

У коді на C# приєднані властивості встановлюють статичним методом:

```csharp
var box = new TextBox();
Grid.SetRow(box, 1);       // те саме, що Grid.Row="1" у XAML
Grid.SetColumn(box, 0);
MainGrid.Children.Add(box);
```

Приєднаних властивостей у WPF багато, і майже кожна панель компонування
має власні:

| Властивість | Чия | Що задає |
|---|---|---|
| `Grid.Row`, `Grid.Column` | `Grid` | у якій комірці розташувати елемент |
| `Grid.RowSpan`, `Grid.ColumnSpan` | `Grid` | на скільки комірок розтягнути |
| `DockPanel.Dock` | `DockPanel` | до якого краю притиснути |
| `Canvas.Left`, `Canvas.Top` | `Canvas` | координати елемента |
| `Panel.ZIndex` | `Panel` | хто поверх кого, якщо елементи перекриваються |

:::warning[Обережно]
Приєднана властивість діє, лише коли елемент справді лежить у відповідній
панелі. `Grid.Row="3"` на елементі всередині `StackPanel` не викличе помилки —
значення просто збережеться і ніхто його не прочитає. Це підступно: помилки
немає, а елемент не там, де ви його чекаєте. Якщо `Grid.Row` «не працює» —
перша підозра саме така: подивіться, в якій панелі лежить елемент.
:::

## x:Name: як елемент стає полем класу

Ми вже бачили `x:Name` у першому вікні. Тепер зрозуміло, чому в нього
префікс `x:`: це не властивість елемента, а вказівка компілятору.

```xml
<TextBox x:Name="LoginTextBox" Width="200"/>
```

Що робить компілятор, побачивши цей рядок:

1. Оголошує у згенерованій половині класу поле
   `internal System.Windows.Controls.TextBox LoginTextBox;`
2. У методі `InitializeComponent` після створення дерева елементів
   присвоює цьому полю посилання на створений `TextBox`.

Після цього в code-behind ви пишете `LoginTextBox.Text` — і це звичайне
звернення до поля, без жодного пошуку елементів за іменем під час роботи.
Саме тому IntelliSense знає про цей елемент і підказує його властивості.

**Правила іменування:**

- Ім'я має бути коректним ідентифікатором C#: літери, цифри, підкреслення,
  не починається з цифри.
- Ім'я має бути унікальним у межах вікна.
- Ім'я потрібне **тільки тим елементам**, до яких ви звертаєтеся з коду.
  Заголовки, рамки й декоративні написи іменувати не треба — зайві імена
  засмічують клас.
- Називайте осмислено: `LoginTextBox`, `SubmitButton`, `ResultTextBlock`,
  а не `textBox1`, `button2`.

:::tip[Порада]
Зручна угода: `ІменникТипЕлемента` — `AmountTextBox`, `CalculateButton`,
`TotalTextBlock`. Читаючи код, ви одразу знаєте і призначення елемента,
і його тип, і не плутаєте `TextBox` (поле введення) з `TextBlock` (напис).
Ці два імені схожі, і плутають їх постійно.
:::

:::note
У XAML трапляється також атрибут `Name` без префікса — у елементів, які
успадковують `FrameworkElement`, така властивість справді є. Практична
різниця мінімальна; пишіть `x:Name`, він працює завжди й скрізь.
:::

## Коментарі

Коментарі в XAML — як у HTML: відкривна послідовність із знаком оклику
й два дефіси, закривна з двома дефісами.

```xml
<StackPanel>
    <!-- Верхня частина: введення даних -->
    <TextBox x:Name="AmountTextBox"/>

    <!--
        Кнопку тимчасово прибрано, поки не готовий обробник.
        Повернути після завершення розрахунку.
    -->
    <!-- <Button Content="Порахувати"/> -->
</StackPanel>
```

Дві особливості, які створюють несподівані проблеми:

- **Коментарі не можна вкладати один в одного.** Якщо всередині
  закоментованого блоку вже був коментар, розмітка зламається.
- **Коментар не можна поставити всередині тега**, між атрибутами. Тільки
  між елементами.

## Типові синтаксичні помилки та що каже Visual Studio

XAML суворіший за HTML: браузер прощає незакритий тег, компілятор XAML —
ніколи. Ось найчастіші помилки та повідомлення, якими вони супроводжуються.

**Незакритий тег.**

```xml
<StackPanel>
    <TextBlock Text="Привіт">
</StackPanel>
```

Visual Studio: `The 'TextBlock' start tag on line 5 does not match the end
tag of 'StackPanel'`. Елемент без вмісту закривають скісною рискою перед
кутовою дужкою: `<TextBlock Text="Привіт"/>`.

**Помилка в регістрі.**

```xml
<Button content="Ok"/>
```

Visual Studio: `The property 'content' was not found in type 'Button'`.
Властивості починаються з великої літери.

**Двічі встановлений вміст.**

```xml
<Button Content="Ok">
    <TextBlock Text="Скасувати"/>
</Button>
```

Visual Studio: `The property 'Content' is set more than once`. Вкладений
елемент — це теж `Content`, тому атрибут із ним конфліктує.

**Невідповідність `x:Class` і коду.**

Visual Studio: `Partial declarations of 'MainWindow' must not specify
different base classes` або `The name 'InitializeComponent' does not exist
in the current context`. Перевірте, що простір імен і клас у розмітці
точно збігаються з файлом code-behind.

**Обробник, якого немає в коді.**

```xml
<Button Click="SaveButton_Click"/>
```

Якщо метод не написаний: `The name 'SaveButton_Click' does not exist in the
current context`. Подвійне клацання по імені обробника в розмітці з підказкою
Visual Studio створює метод автоматично.

**Некоректне значення властивості.**

```xml
<TextBox Width="широкий"/>
```

Visual Studio: `Cannot convert the string 'широкий' in attribute 'Width'
to object of type 'System.Double'`. Спрацював конвертер типів — і не зміг.

:::tip[Порада]
Помилки XAML Visual Studio показує у вікні **Error List**, і подвійне клацання
по рядку помилки перекидає точно в потрібне місце розмітки. Іще корисніше:
якщо вікно дизайнера показує жовту смугу з текстом помилки — не ігноруйте її,
розгорніть. Там зазвичай написано рівно те, що зламалося.
:::

## Типові помилки

**Плутають `TextBox` і `TextBlock`.** `TextBox` — поле, куди користувач
вводить текст. `TextBlock` — напис, який лише показує текст. Обидва мають
властивість `Text`, тому код компілюється — і потім ви дивуєтеся, чому
«напис» можна редагувати.

**Пишуть `Text` у кнопки.** У `Button` вміст задається властивістю `Content`,
а не `Text`. Помилка: `The property 'Text' was not found in type 'Button'`.

**Кладуть два елементи безпосередньо у `Window`.** Вікно вміщує рівно один
елемент. Потрібна панель-контейнер.

**Забувають `x:` перед `Name` або `Class`.** `Class="..."` без префікса —
помилка «властивість не знайдено», бо у `Window` немає властивості `Class`.

**Ставлять `Grid.Row` на елемент, що лежить не в `Grid`.** Помилки немає,
результату теж немає. Перевірте батьківську панель.
