# Життєвий цикл програм та етапи розв'язання задачі

Написання коду — це приблизно 20% роботи над програмою. Решта 80% — з'ясувати, що саме
треба зробити, продумати рішення, перевірити його, впровадити й підтримувати роками.
Студенти зазвичай дізнаються про це на третьому курсі, коли виявляється, що курсова
робота «вже написана», але не працює ні в кого, крім автора.

Тому тему алгоритмів завершимо ширшим поглядом: як виглядає повний шлях програми
від ідеї до виведення з експлуатації, і де в цьому шляху лежить та частина, якою
ми займалися в попередніх підрозділах.

## Життєвий цикл програмного забезпечення

**Життєвий цикл ПЗ** (Software Development Life Cycle, SDLC) — увесь період існування
програмного продукту від задуму до припинення використання.

| Етап | Зміст | Результат етапу |
|------|-------|-----------------|
| 1. **Аналіз вимог** | З'ясувати, що саме потрібно замовнику й користувачам | Технічне завдання |
| 2. **Проєктування** | Продумати архітектуру, структури даних, алгоритми | Проєктна документація, схеми |
| 3. **Реалізація** | Написання коду | Вихідний код |
| 4. **Тестування** | Пошук і виправлення помилок | Звіт про тестування, виправлений код |
| 5. **Впровадження** | Розгортання в робочому середовищі, навчання користувачів | Працююча система |
| 6. **Супровід** | Виправлення помилок, оновлення, підтримка | Нові версії |
| 7. **Виведення з експлуатації** | Припинення підтримки, міграція даних | Архів даних |

### Скільки коштує помилка

Ключова причина, чому етапи йдуть саме в такому порядку — **вартість виправлення
помилки зростає на порядок з кожним етапом**.

| Де знайдено помилку | Відносна вартість виправлення |
|---------------------|-------------------------------|
| На етапі вимог | 1 |
| На етапі проєктування | ~5 |
| На етапі кодування | ~10 |
| На етапі тестування | ~50 |
| Після випуску | ~150 і більше |

Помилка у вимогах — це виправлений абзац у документі. Та сама помилка, виявлена
після випуску — це переписаний модуль, повторне тестування, розсилка оновлення
тисячам користувачів і зіпсована репутація.

:::warning
Саме звідси випливає головна порада всього курсу: **не починайте писати код, доки
не зрозуміли задачу**. Година, витрачена на постановку задачі й алгоритм, економить
день налагодження.
:::

## Моделі життєвого циклу

Етапи однакові, а от порядок їх проходження може бути різним. Це і називають
**моделлю життєвого циклу**.

### Каскадна модель (Waterfall)

Етапи виконуються строго послідовно: наступний починається після повного завершення
попереднього.

```
Вимоги → Проєктування → Реалізація → Тестування → Впровадження → Супровід
```

**Переваги:** зрозуміле планування, чітка документація, легко оцінити терміни.

**Недоліки:** повернутися назад майже неможливо. Якщо на етапі тестування виявилося,
що вимоги були неправильні — переробляти доведеться все.

**Де застосовують:** там, де вимоги точно відомі й не змінюються — авіоніка, медичне
обладнання, державні системи.

### Ітеративна модель

Продукт створюється за кілька проходів. На кожній ітерації проходять усі етапи, але
для невеликої частини функціональності.

```
Ітерація 1: вимоги → проєкт → код → тест   (базова функція)
Ітерація 2: вимоги → проєкт → код → тест   (+ нова функція)
Ітерація 3: ...
```

**Переваги:** робочий продукт з'являється рано, вимоги можна уточнювати по ходу.

**Недоліки:** складніше оцінити загальні терміни й бюджет.

### Гнучкі методології (Agile, Scrum)

Розвиток ітеративного підходу: короткі цикли по 1–4 тижні (**спринти**), постійний
зворотний зв'язок від замовника, готовність міняти вимоги на будь-якому етапі.

**Де застосовують:** більшість сучасної комерційної розробки — вебсервіси, мобільні
застосунки, продуктові команди.

:::info
У навчальних задачах ви фактично працюєте за каскадною моделлю в мініатюрі: прочитали
умову, склали алгоритм, написали код, перевірили. У реальній роботі вас майже напевно
чекає Scrum.
:::

## Етапи розв'язання задачі на комп'ютері

Якщо життєвий цикл — це погляд на проєкт зверху, то **етапи розв'язання задачі** —
це те, що відбувається всередині, коли розв'язують одну конкретну задачу.

### 1. Постановка задачі

З'ясувати, що дано, що знайти і який між ними зв'язок. Визначити діапазони вхідних
даних і поведінку в особливих випадках.

> **Приклад.** Дано: температура в градусах Цельсія, дійсне число від −90 до +60.
> Знайти: температуру у Фаренгейтах. Зв'язок: `F = C · 9/5 + 32`.

### 2. Побудова математичної моделі

Перекласти задачу мовою формул і відношень: які величини є, якими рівняннями вони
пов'язані, які обмеження діють.

Це етап, який студенти пропускають найчастіше — і саме на ньому виявляється, що
задача насправді не має розв'язку або має їх безліч.

### 3. Розробка алгоритму

Скласти послідовність дій — псевдокодом або блок-схемою. Саме цим ми займалися
в попередніх підрозділах.

### 4. Кодування

Записати алгоритм мовою програмування. Якщо етап 3 виконано добре, цей етап
механічний.

### 5. Налагодження й тестування

Знайти й виправити помилки. Розрізняють три види:

| Вид помилки | Коли виявляється | Приклад |
|-------------|------------------|---------|
| **Синтаксична** | Під час компіляції | Пропущена крапка з комою, помилка в назві методу |
| **Помилка виконання** (runtime) | Під час роботи програми | Ділення на нуль, вихід за межі масиву |
| **Логічна** | Не виявляється сама — тільки перевіркою результатів | Програма рахує середнє, а ділить на неправильну кількість |

Синтаксичні помилки нешкідливі — компілятор сам їх покаже. Помилки виконання
помітні, бо програма падає. **Найнебезпечніші — логічні:** програма працює, нічого
не повідомляє, а результат неправильний.

:::tip[Як тестувати свою програму]
Перевіряйте не тільки «нормальні» дані, а й **граничні**:

- нуль і від'ємні числа, якщо вони допустимі;
- найменше і найбільше допустиме значення;
- порожній ввід, ввід тексту замість числа;
- однакові значення там, де очікуються різні.

Більшість помилок ховається саме на межах діапазонів, а не в середині.
:::

### 6. Аналіз результатів

Перевірити, чи розв'язана задача насправді: чи має результат фізичний сенс, чи
збігається з ручним розрахунком на контрольному прикладі.

### 7. Супровід

Виправлення виявлених згодом помилок, доопрацювання під нові вимоги.

## Як пов'язані життєвий цикл і етапи розв'язання задачі

Етапи розв'язання задачі **вкладені** в життєвий цикл:

| Етап життєвого циклу | Які етапи розв'язання задачі туди входять |
|----------------------|-------------------------------------------|
| Аналіз вимог | Постановка задачі |
| Проєктування | Математична модель, розробка алгоритму |
| Реалізація | Кодування |
| Тестування | Налагодження, тестування, аналіз результатів |
| Супровід | Супровід |

Життєвий цикл — це **каркас усього проєкту**, а розв'язання задачі — **зміст кожного
етапу**. Велика програма містить сотні окремих задач, і цикл «постановка → алгоритм →
код → перевірка» проходиться для кожної з них окремо, усередині відповідної стадії
життєвого циклу.

## Приклад наскрізь: від задачі до готової програми

Простежимо всі етапи на одній маленькій задачі.

**Задача від «замовника»:** «Треба щось, щоб рахувати оцінки студентів».

**Етап 1 — постановка.** Після уточнень формулювання стає таким:

> Дано: кількість студентів `n` (ціле, від 1 до 100) і `n` оцінок (цілі числа
> від 1 до 12). Знайти: середній бал (дійсне число, два знаки після коми) і
> кількість студентів, що мають менше ніж 4 бали. Особливий випадок: якщо `n = 0`,
> вивести повідомлення і не рахувати.

**Етап 2 — модель.** Середнє = сума оцінок / кількість. Кількість незадовільних —
лічильник значень, менших за 4.

**Етап 3 — алгоритм:**

```
початок
    ввести n
    якщо n <= 0 то
        вивести "Немає студентів"
        кінець
    sum = 0
    k = 0
    для i від 1 до n
        ввести оцінку
        sum = sum + оцінка
        якщо оцінка < 4 то
            k = k + 1
    середнє = sum / n
    вивести середнє
    вивести k
кінець
```

**Етап 4 — кодування:**

```csharp
int n = int.Parse(Console.ReadLine());

if (n <= 0)
{
    Console.WriteLine("Немає студентів");
    return;
}

int sum = 0;
int k = 0;

for (int i = 1; i <= n; i++)
{
    int mark = int.Parse(Console.ReadLine());
    sum = sum + mark;

    if (mark < 4)
    {
        k++;
    }
}

double average = (double)sum / n;

Console.WriteLine($"Середній бал: {average:F2}");
Console.WriteLine($"Незадовільних: {k}");
```

**Етап 5 — тестування.** Перевіряємо на контрольних наборах:

| Вхідні дані | Очікуваний результат | Що перевіряємо |
|-------------|---------------------|----------------|
| n = 3; 10, 8, 12 | 10.00; 0 | Звичайний випадок |
| n = 0 | «Немає студентів» | Захисна умова |
| n = 2; 3, 3 | 3.00; 2 | Усі незадовільні |
| n = 1; 12 | 12.00; 0 | Мінімальна кількість |

:::note[Чому `(double)sum / n`, а не `sum / n`]
Якщо обидва операнди цілі, C# виконує **цілочисельне** ділення: `7 / 2` дає `3`,
а не `3.5`. Приведення `(double)` змушує виконати ділення з дробовою частиною.
Це рівно та логічна помилка, яку компілятор не побачить, а тести — побачать.
:::

**Етап 6 — аналіз.** Середнє з 10, 8, 12 дорівнює 10 — збігається з ручним
розрахунком. Задача розв'язана.

## Висновок

- **Життєвий цикл ПЗ** — сім етапів від аналізу вимог до виведення з експлуатації.
- Вартість виправлення помилки зростає приблизно вдесятеро з кожним пройденим
  етапом — тому час на постановку задачі й алгоритм завжди окупається.
- **Моделі життєвого циклу** різняться порядком проходження етапів: каскадна
  (строго послідовно), ітеративна та гнучка (циклічно, малими порціями).
- **Етапи розв'язання задачі** — постановка, модель, алгоритм, кодування, тестування,
  аналіз, супровід — вкладені всередину етапів життєвого циклу.
- Помилки бувають **синтаксичні, виконання й логічні**; найнебезпечніші — логічні,
  бо програма при них продовжує працювати.
