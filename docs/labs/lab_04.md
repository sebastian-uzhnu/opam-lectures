# Лабораторна робота №4

## Тема
Система контролю версій Git. Робота з локальним та віддаленим репозиторієм

## Мета
Навчитися створювати локальний репозиторій Git та фіксувати в ньому стани проєкту.
Закріпити розуміння трьох областей Git — робочого каталогу, індексу та репозиторію —
і навчитися свідомо переміщувати зміни між ними. Набути навичок роботи з віддаленим
репозиторієм, створення гілок, злиття та розв'язання конфліктів. Сформувати звичку
писати зрозумілі повідомлення до комітів.

## Тривалість
2 академічні години.

## Обладнання та програмне забезпечення
Персональний комп'ютер, .NET 8 SDK, будь-яке середовище розробки або текстовий редактор
і термінал, встановлений Git (перевірка: команда `git --version`), обліковий запис
на будь-якому сервісі розміщення репозиторіїв, доступ до мережі.

## Теоретичні відомості

### 1. Навіщо потрібна система контролю версій

Уявіть ситуацію, знайому кожному: ви пишете курсову роботу. Спочатку є файл
`kursova.docx`, потім `kursova_нова.docx`, `kursova_нова2.docx`, `kursova_фінал.docx`,
`kursova_фінал_виправлено.docx`. Через тиждень ви не пам'ятаєте, у якому з них правильний
розділ 2, а в якому — правильний список літератури. З програмами ця проблема гостріша:
кожна зміна може щось зламати, а ніде не записано, **чому** її внесено.

**Система контролю версій** (Version Control System, VCS) — це програма, яка зберігає
історію змін файлів проєкту: хто, коли, що саме і навіщо змінив, — і дає змогу
повернутися до будь-якого збереженого стану.

Що дає контроль версій:

| Потреба | Без VCS | З VCS |
|---|---|---|
| Повернутися до вчорашнього стану | Копія папки, якщо здогадалися зробити | `git checkout` до потрібного коміту |
| Дізнатися, коли з'явилася помилка | Здогадки | `git log` показує кожну зміну з датою й автором |
| Працювати вдвох над одним проєктом | Пересилання архівів | Спільний віддалений репозиторій |
| Спробувати ризиковану ідею | Копія «про всяк випадок» | Окрема гілка, яку не шкода видалити |
| Пояснити, навіщо зміна | Ніде | Повідомлення до коміту |

**Git** — найпоширеніша сьогодні система контролю версій. Вона **розподілена**: у кожного
учасника є повна копія історії проєкту, а не лише остання версія. Тому більшість
операцій Git виконує локально, без мережі, і працює миттєво.

### 2. Репозиторій і три області Git

**Репозиторій** (repository, скорочено repo) — це папка проєкту разом із прихованою
підпапкою `.git`, у якій Git зберігає всю історію. Видалите `.git` — залишиться
звичайна папка з файлами без історії.

Git оперує трьома областями — це найважливіше поняття всієї роботи.

```text
  ┌────────────────────┐   git add    ┌──────────────┐  git commit  ┌──────────────────┐
  │  Робочий каталог   │ ───────────▶ │    Індекс    │ ───────────▶ │   Репозиторій    │
  │ (working directory)│              │   (staging   │              │  (.git, історія  │
  │   файли на диску   │ ◀─────────── │     area)    │ ◀─────────── │     комітів)     │
  └────────────────────┘  git restore └──────────────┘ git restore  └──────────────────┘
                                                        --staged
```

- **Робочий каталог** — те, що ви бачите у файловому менеджері й редагуєте.
- **Індекс** (*staging area*, «область підготовки») — чернетка майбутнього коміту. Сюди
  ви складаєте саме ті зміни, які хочете зафіксувати разом: завдяки індексу можна
  з п'яти змінених файлів закомітити тільки три.
- **Репозиторій** — послідовність **комітів**. **Коміт** (commit) — це знімок стану всіх
  відстежуваних файлів плюс автор, дата, повідомлення й посилання на попередній коміт.

Аналогія: робочий каталог — робочий стіл, індекс — конверт, у який ви складаєте документи
для відправлення, коміт — заклеєний і підписаний конверт, покладений в архів.

### 3. Початкове налаштування

Git підписує кожен коміт іменем та поштою автора. Налаштувати їх треба один раз на
комп'ютері (ключ `--global` означає «для всіх моїх репозиторіїв»):

```bash
git config --global user.name "Прізвище Ім'я"
git config --global user.email "student@example.com"
git config --global init.defaultBranch main
```

Третя команда задає назву головної гілки `main` для нових репозиторіїв. Перевірити
налаштування: `git config --list`.

### 4. Створення репозиторію: `git init`

```bash
dotnet new console -n Lab04
cd Lab04
git init      # Initialized empty Git repository in /home/student/Lab04/.git/
```

Репозиторій створено, але він порожній: жодного коміту ще немає, хоча файли вже лежать
у папці. Git ніколи не бере файли «сам» — ви щоразу вказуєте, що саме фіксувати.

### 5. `git status` — головна команда початківця

`git status` відповідає на три питання: у якій ви гілці, які файли змінені, що
підготовлено до коміту. Виконуйте її після кожної дії, доки не звикнете.

```bash
git status
```

**Вивід:**

```
On branch main
No commits yet
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        Lab04.csproj
        Program.cs
        bin/
        obj/
nothing added to commit but untracked files present (use "git add" to track)
```

**Невідстежуваний файл** (untracked) — файл, про який Git знає, що він є, але не стежить
за його змінами, бо його жодного разу не додавали до індексу.

Зверніть увагу на `bin/` та `obj/` — про них далі.

### 6. `.gitignore` — що не потрапляє в репозиторій

Під час збирання .NET створює папки `bin` (готові виконувані файли) та `obj` (проміжні
файли компіляції). Зберігати їх в історії не можна: вони відновлюються однією командою
`dotnet build`, тобто це не вихідний код; вони важать багато й змінюються за кожного
запуску, засмічуючи історію; вони різні на різних комп'ютерах і спричиняють безглузді
конфлікти.

**`.gitignore`** — текстовий файл у корені репозиторію з переліком шаблонів імен, які
Git має ігнорувати. Створіть його вручну або командою:

```bash
dotnet new gitignore
```

Мінімальний власний варіант для .NET-проєкту:

```text
# Результати збирання
bin/
obj/

# Налаштування середовищ розробки і тимчасові файли
.vs/
.idea/
*.user
*.log
```

Правила запису: `bin/` — папка з такою назвою на будь-якому рівні; `*.log` — усі файли
з таким розширенням; рядок, що починається з `#`, — коментар. Сам файл `.gitignore`
обов'язково комітять — він частина проєкту й має бути однаковим у всіх учасників.

Важливо: `.gitignore` діє лише на невідстежувані файли. Якщо файл уже потрапив у коміт,
додавання його до `.gitignore` нічого не змінить — доведеться прибрати його з індексу
командою `git rm --cached ім'я_файлу`.

### 7. `git add` і `git commit`

```bash
git add .gitignore Program.cs Lab04.csproj
git status
```

**Вивід:**

```
On branch main
No commits yet
Changes to be committed:
        new file:   .gitignore
        new file:   Lab04.csproj
        new file:   Program.cs
```

Папок `bin` та `obj` у переліку більше немає — `.gitignore` спрацював.

Варіанти команди `git add`:

| Команда | Дія |
|---|---|
| `git add Program.cs` | додати в індекс один файл |
| `git add Program.cs Lab04.csproj` | додати кілька файлів |
| `git add .` | додати всі зміни в поточній папці та підпапках |
| `git add -A` | додати всі зміни в репозиторії, зокрема видалення файлів |
| `git restore --staged Program.cs` | прибрати файл з індексу, зміни лишаються на диску |

Тепер фіксуємо стан:

```bash
git commit -m "Створено каркас проєкту Lab04 і додано .gitignore"
```

**Вивід:**

```
[main (root-commit) a1b2c3d] Створено каркас проєкту Lab04 і додано .gitignore
 3 files changed, 22 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 Lab04.csproj
 create mode 100644 Program.cs
```

`a1b2c3d` — скорочений **хеш коміту**, унікальний ідентифікатор із 40 шістнадцяткових
цифр, за яким на цей коміт можна послатися. Ключ `-m` задає повідомлення прямо в команді;
без нього Git відкриє текстовий редактор.

### 8. `git log` — перегляд історії

Команда `git log` виводить коміти від найновішого до найстарішого, для кожного — повний
хеш, автора, дату й повідомлення:

```
commit a1b2c3d4e5f60718293a4b5c6d7e8f9012345678 (HEAD -> main)
Author: Прізвище Ім'я <student@example.com>
Date:   Mon Sep 8 10:14:22 2025 +0300

    Створено каркас проєкту Lab04 і додано .gitignore
```

**HEAD** — вказівник на коміт, який ви зараз бачите в робочому каталозі; зазвичай це
останній коміт поточної гілки. Корисні варіанти перегляду:

| Команда | Що показує |
|---|---|
| `git log --oneline` | по одному рядку на коміт: хеш і повідомлення |
| `git log --oneline --graph --all` | історію всіх гілок у вигляді схеми |
| `git log -3` | три останні коміти |
| `git log --stat` | які файли й на скільки рядків змінилися |
| `git show a1b2c3d` | повний вміст конкретного коміту |
| `git diff` | зміни в робочому каталозі, ще не додані в індекс |
| `git diff --staged` | зміни, підготовлені в індексі |

### 9. Правила хороших повідомлень до комітів

Повідомлення пишуть не для Git, а для людини — часто для себе самого через півроку.
Правила: перший рядок — короткий підсумок до 50–72 символів без крапки в кінці;
віддієслівний іменник або наказовий спосіб («Додано перевірку введення», а не «додав»,
«правки», «фікс»); відповідати на питання **що** і **навіщо**, а не **як** — «як» видно
з коду; один коміт — одна закінчена зміна; якщо потрібні подробиці, залишають порожній
рядок після заголовка й далі пишуть пояснення.

| Погано | Чому погано | Добре |
|---|---|---|
| `fix` | що саме виправлено? | `Виправлено формулу переведення хвилин у години` |
| `робота за 8 вересня` | невідомо, що змінилося | `Додано виведення вартості з двома знаками після коми` |
| `.` | нічого не повідомляє | `Додано .gitignore для папок bin і obj` |
| `Змінив рядок 17 у Program.cs` | «як» замість «що» | `Замінено Convert.ToDouble на double.TryParse` |
| `Додано введення даних, перейменовано змінні, оновлено README` | три зміни в одному коміті | три окремі коміти |

### 10. Віддалений репозиторій

**Віддалений репозиторій** (remote) — копія репозиторію на сервері. Вона потрібна, щоб
код не зник разом із комп'ютером, щоб працювати з кількох машин і щоб здавати роботу
викладачеві.

Створіть **порожній** репозиторій на обраному сервісі (без README, без ліцензії —
інакше історії розійдуться) і зв'яжіть його з локальним:

```bash
git remote add origin https://example.com/user/lab04.git
git remote -v                 # перевірити, що адресу записано
git push -u origin main
```

**Вивід `git push`:**

```
Writing objects: 100% (5/5), 612 bytes, done.
To https://example.com/user/lab04.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

`origin` — загальноприйнята коротка назва основного віддаленого репозиторію. Ключ `-u`
запам'ятовує зв'язок гілок, тож надалі достатньо просто `git push`.

| Команда | Дія |
|---|---|
| `git remote add origin URL` | прив'язати віддалений репозиторій |
| `git push` | відправити свої коміти на сервер |
| `git pull` | забрати зміни з сервера й влити у свою гілку |
| `git fetch` | забрати зміни, але не зливати (подивитися, що нового) |
| `git clone URL` | завантажити репозиторій разом з історією на новий комп'ютер |

`git clone` створює папку з іменем репозиторію, налаштовує `origin` і одразу робить
робочу копію — окремо викликати `git init` не потрібно. Типовий робочий цикл одного дня:
`git pull` → правки в коді → `git add` → `git commit -m "..."` → `git push`.

### 11. Гілки

**Гілка** (branch) — рухомий вказівник на коміт. Створення гілки не копіює файли: Git
лише запам'ятовує, від якого коміту вона відгалужується. Тому гілки в Git дешеві,
і їх створюють навіть заради невеликої правки.

Навіщо: у гілці `main` лежить робоча версія, яку не соромно показати. Нову можливість
роблять у окремій гілці; якщо вона не вдалася — гілку видаляють, і `main` не постраждав.

```bash
git branch                    # перелік гілок, зірочка біля поточної
git branch feature-tax        # створити гілку від поточного коміту
git switch feature-tax        # перейти в гілку
git switch -c feature-tax     # створити і одразу перейти (те саме за один крок)
git switch main               # повернутися
git merge feature-tax         # влити гілку feature-tax у поточну
git branch -d feature-tax     # видалити злиту гілку
```

Схема: до злиття у `main` є коміти A і B, у `feature-tax` — C і D. Якщо в `main` після
відгалуження нічого не додавали, Git просто пересуває вказівник уперед — це
**перемотування** (fast-forward). Якщо ж у `main` з'явився власний коміт E, Git створює
**коміт злиття** M із двома батьками:

```text
  ДО ЗЛИТТЯ                  ПЕРЕМОТУВАННЯ (fast-forward)
        C ──── D                   A ──── B ──── C ──── D
       /        ↑ feature-tax                           ↑ main, feature-tax
  A ──── B
         ↑ main              КОМІТ ЗЛИТТЯ
                                   C ──── D
                                  /        \
                             A ──── B       M   ← main
                                     \     /
                                      E ───
```

### 12. Конфлікт злиття і його розв'язання

**Конфлікт** виникає, коли в обох гілках змінили **ті самі рядки** того самого файлу.
Git не вирішує за вас, чия версія правильна, — він зупиняється й просить допомоги.

```bash
git merge feature-price
```

**Вивід:**

```
Auto-merging Program.cs
CONFLICT (content): Merge conflict in Program.cs
Automatic merge failed; fix conflicts and then commit the result.
```

Відкрийте файл. Git позначив спірне місце:

```csharp
Console.WriteLine("Розрахунок вартості друку");
<<<<<<< HEAD
double pricePerPage = 2.50;
=======
double pricePerPage = 3.00;
>>>>>>> feature-price
Console.WriteLine($"Ціна сторінки: {pricePerPage} грн");
```

Читати так: між `<<<<<<< HEAD` і `=======` — версія поточної гілки (тієї, у яку зливаєте),
між `=======` і `>>>>>>> feature-price` — версія гілки, яку зливаєте. Порядок дій:

1. Вирішіть, який варіант правильний: залишити свій, узяти чужий або скласти новий.
2. Відредагуйте файл так, щоб він був коректним кодом. **Усі три рядки-маркери
   (`<<<<<<<`, `=======`, `>>>>>>>`) мають зникнути.**
3. `git add Program.cs` — так ви повідомляєте Git, що конфлікт розв'язано.
4. `git commit` — Git запропонує готове повідомлення про злиття, його можна доповнити.

Після правки фрагмент має виглядати, наприклад, так:

```csharp
Console.WriteLine("Розрахунок вартості друку");
double pricePerPage = 3.00;   // нова ціна з гілки feature-price
Console.WriteLine($"Ціна сторінки: {pricePerPage} грн");
```

Якщо ви заплуталися, з незавершеного злиття завжди можна вийти: `git merge --abort`
повертає репозиторій у стан до `git merge`.

Як зменшити кількість конфліктів: частіше робити `git pull`, тримати коміти невеликими,
не форматувати весь файл разом зі змістовною правкою, домовлятися в команді, хто що
редагує.

## Приклад виконання

**Умова.** Створити репозиторій із програмою, що обчислює вартість друку документа:
користувач вводить кількість сторінок і ціну однієї сторінки, програма виводить
загальну вартість. Зробити три коміти (каркас, введення даних, обчислення), потім
у гілці `feature-discount` додати знижку 10 %, злити гілку в `main` і відправити
результат на сервер.

### Крок 1. Проєкт і перший коміт

```bash
dotnet new console -n PrintCost
cd PrintCost
dotnet new gitignore
git init
git add .
git commit -m "Створено каркас консольного проєкту PrintCost"
```

Файл `Program.cs` на цей момент містить згенерований шаблон.

потрапили. Робоча версія програми є і на комп'ютері, і на сервері.

## Хід роботи

1. Перевірте, що Git встановлено: `git --version`. Задайте своє ім'я та пошту командами
   `git config --global user.name` і `git config --global user.email`.
2. Створіть проєкт `dotnet new console -n Lab04` і перейдіть у його папку. Виконайте
   `git init` та `git status`; запишіть у звіт, які файли Git вважає невідстежуваними.
3. Додайте файл `.gitignore` з правилами для `bin/` та `obj/`. Ще раз виконайте
   `git status` і переконайтеся, що ці папки зникли з переліку. Зробіть перший коміт
   із каркасом проєкту.
4. Напишіть у `Program.cs` програму свого варіанта з таблиці індивідуальних завдань,
   виконуючи послідовність комітів, зазначену в стовпці «Коміти»: після кожного етапу —
   `git add` і `git commit -m` з власним осмисленим повідомленням.
5. Перегляньте історію командами `git log` та `git log --oneline`. Збережіть вивід
   для звіту.
6. Створіть гілку з назвою зі свого варіанта (`git switch -c ...`), внесіть у ній
   доробку, зазначену в стовпці «Доробка у гілці», і зробіть у гілці щонайменше
   один коміт.
7. Поверніться в `main` і виконайте дію, зазначену в стовпці «Сценарій». Злийте гілку
   командою `git merge`. Якщо виникне конфлікт — розв'яжіть його, приберіть маркери
   `<<<<<<<`, `=======`, `>>>>>>>`, виконайте `git add` і `git commit`. Опишіть у звіті,
   через що виник конфлікт і як ви його розв'язали.
8. Перегляньте підсумкову структуру історії: `git log --oneline --graph --all`.
   Збережіть схему для звіту.
9. Створіть порожній віддалений репозиторій, прив'яжіть його командою `git remote add`
   і відправте роботу: `git push -u origin main`. Переконайтеся, що на сервері немає
   папок `bin` та `obj`.
10. Склонуйте свій репозиторій в іншу папку (`git clone`), запустіть програму командою
    `dotnet run` і переконайтеся, що вона працює. Це перевірка, що в репозиторій
    потрапило все потрібне.

## Індивідуальне завдання

Створіть репозиторій із консольною програмою свого варіанта (програма лінійна,
без розгалужень), виконайте задану послідовність комітів, створіть гілку з доробкою
і злийте її в `main`. Результат відправте у віддалений репозиторій.

У стовпці «Коміти» через стрілку вказано етапи; кожен етап — окремий коміт із власним
повідомленням. У стовпці «Сценарій» описано, що зробити перед злиттям гілки:
FF означає злиття перемотуванням (у `main` нічого не змінюємо), КЗ — злиття з комітом
злиття (у `main` змінюємо **інший** рядок або файл), КОНФЛІКТ — навмисний конфлікт
(у `main` змінюємо **той самий** рядок, що й у гілці).

| № | Програма (лінійна) | Коміти | Гілка та доробка | Сценарій |
|---|---|---|---|---|
| 1 | Вартість поїздки таксі: подача + кілометраж × тариф | каркас → введення → обчислення | `feature-night-rate`: нічний тариф +20 % | КОНФЛІКТ: у `main` змінити ціну кілометра в тому самому рядку |
| 2 | Площа й периметр прямокутної ділянки в сотках | каркас → введення сторін → площа → периметр | `feature-fence`: вартість паркану за периметром | FF |
| 3 | Переведення часу в секундах у години, хвилини, секунди | каркас → введення → обчислення → форматований вивід | `feature-days`: додати ще й дні | КЗ: у `main` додати рядок-заголовок програми |
| 4 | Вартість заправки авто: літри × ціна, залишок від купюри | каркас → введення → обчислення | `feature-liters-per-100`: витрата на 100 км | КОНФЛІКТ: у `main` змінити той самий рядок виведення підсумку |
| 5 | Підсумкова оцінка як середнє трьох складників з вагами | каркас → введення оцінок → середнє | `feature-weights`: винести ваги в окремі змінні й вивести їх | КЗ: у `main` додати коментар-шапку з автором |
| 6 | Комунальний платіж за електроенергію за показниками лічильника | каркас → введення показників → різниця → сума | `feature-subsidy`: врахувати знижку 15 % | FF |
| 7 | Довжина кола й площа круга за радіусом | каркас → введення → довжина → площа | `feature-sphere`: об'єм кулі того самого радіуса | КОНФЛІКТ: у `main` змінити той самий рядок із числом π |
| 8 | Вартість піци: основа + ціна за см² додаткової начинки | каркас → введення → обчислення | `feature-delivery`: додати вартість доставки | КЗ: у `main` змінити текст привітання |
| 9 | Переведення температури з Цельсія у Фаренгейти й Кельвіни | каркас → введення → Фаренгейти → Кельвіни | `feature-format`: вивід з одним знаком після коми | КОНФЛІКТ: у `main` змінити той самий рядок виведення |
| 10 | Розрахунок відрядних: дні × добові + проїзд | каркас → введення → обчислення | `feature-hotel`: додати вартість готелю | FF |
| 11 | Маса й вартість партії цукру за мішками | каркас → введення → маса → вартість | `feature-discount`: оптова знижка 7 % від 50 мішків | КЗ: у `main` додати виведення дати розрахунку |
| 12 | Час у дорозі: відстань ÷ швидкість, у годинах і хвилинах | каркас → введення → час → розклад по хвилинах | `feature-stops`: додати час на зупинки | КОНФЛІКТ: у `main` змінити той самий рядок із формулою |
| 13 | Вартість фотодруку: кількість × ціна формату + рамка | каркас → введення → обчислення | `feature-vat`: додати ПДВ 20 % | КЗ: у `main` змінити назву програми у заголовку |
| 14 | Обсяг і вартість бетону для фундаменту (a × b × h) | каркас → введення розмірів → об'єм → вартість | `feature-truck`: кількість міксерів по 5 м³ | FF |
| 15 | Розрахунок зарплати: ставка × години − податок 18 % | каркас → введення → нарахування → податок | `feature-military-tax`: додати військовий збір 1,5 % | КОНФЛІКТ: у `main` змінити той самий рядок із податком |
| 16 | Переведення відстані з миль у кілометри й навпаки | каркас → введення → милі в км → км у милі | `feature-feet`: додати фути й дюйми | КЗ: у `main` додати виведення коефіцієнта переведення |
| 17 | Вартість інтернет-тарифу: абонплата + перевищення трафіку | каркас → введення → перевищення → сума | `feature-router`: додати оренду обладнання | FF |
| 18 | Периметр і площа трикутника за трьома сторонами (формула Герона) | каркас → введення сторін → півпериметр → площа | `feature-height`: висота до найбільшої сторони | КОНФЛІКТ: у `main` змінити той самий рядок обчислення площі |
| 19 | Кількість рулонів шпалер для кімнати | каркас → введення розмірів → площа стін → рулони | `feature-doors`: відняти площу вікон і дверей | КЗ: у `main` додати виведення висоти рулону |
| 20 | Вартість квитків у театр: дорослі + дитячі (пів ціни) | каркас → введення → обчислення | `feature-group`: групова знижка 10 % | КОНФЛІКТ: у `main` змінити той самий рядок із підсумком |

Вимоги до всіх варіантів: репозиторій містить `.gitignore` з `bin/` та `obj/` (цих папок
в історії немає); щонайменше **чотири** коміти в `main` і **один** у гілці; повідомлення
до комітів українською, осмислені, за правилами з розділу 9 теорії; гілку злито в `main`,
і після злиття `main` містить робочу програму; роботу відправлено у віддалений репозиторій.

## Контрольні питання

1. Що таке система контролю версій і які три задачі вона розв'язує, з якими не
   справляється копіювання папки проєкту?
2. Назвіть три області Git і поясніть, яка команда переміщує зміни між кожною парою
   сусідніх областей.
3. Навіщо потрібен індекс? Чому не можна було б одразу комітити все, що змінилося
   в робочому каталозі?
4. Що саме зберігається в коміті? Чи можна змінити вже створений коміт так, щоб цього
   ніхто не помітив?
5. Чому папки `bin` та `obj` не додають у репозиторій? Що станеться, якщо їх усе ж
   закомітити й над проєктом працюватимуть двоє?
6. Ви додали файл до `.gitignore`, але Git усе одно показує його зміни. Чому так сталося
   і як це виправити?
7. Чим `git init` відрізняється від `git clone`? У якій ситуації застосовують кожну
   з команд?
8. Що таке гілка і чому її створення відбувається миттєво навіть у великому проєкті?
9. У якому випадку злиття відбувається перемотуванням, а в якому Git створює окремий
   коміт злиття? Намалюйте схему для обох випадків.
10. Через що виникає конфлікт злиття? Опишіть послідовність дій для його розв'язання
    та поясніть, що означають рядки `<<<<<<<`, `=======`, `>>>>>>>`.
