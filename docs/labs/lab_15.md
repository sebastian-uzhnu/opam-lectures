# Лабораторна робота №15

## Тема
Абстрактні класи та інтерфейси. Реалізація IComparable

## Мета
Навчитися відділяти опис спільної поведінки від її реалізації: оголошувати абстрактні класи й абстрактні методи там, де базовий тип не має самостійного сенсу. Закріпити поняття контракту через інтерфейси, навчитися реалізовувати кілька інтерфейсів одним класом. Набути навичок упорядкування власних об'єктів засобами `IComparable<T>` та `IComparer<T>`. Спроєктувати власний узагальнений інтерфейс сховища `IRepository<T>` і реалізувати його поверх CSV-файлу, щоб дані проєкту вперше пережили закриття програми.

## Тривалість
2 академічні години.

## Обладнання та програмне забезпечення
Персональний комп'ютер, .NET 8 SDK, будь-яке середовище розробки або текстовий редактор і термінал, система контролю версій Git.

## Що було на попередньому кроці

Це четвертий крок наскрізного проєкту. На виході з лабораторної роботи №14 ваш застосунок мав такий вигляд.

- Є **базовий клас** головної сутності з властивостями, перевіркою значень у сеттерах, однією обчислюваною властивістю й перевизначеним `ToString()`.
- Від базового класу успадковано **два-три нащадки**, у кожного — власні додаткові поля.
- У базовому класі оголошено метод, позначений `virtual`, а в кожному нащадку — його `override`. Саме на ньому ви побачили **поліморфізм**: один виклик через посилання базового типу виконує різний код залежно від фактичного типу об'єкта.
- Усі записи зберігаються в одній колекції `List<БазовийКлас>`, працює консольне меню: додати, показати всі, знайти, видалити.
- **Дані живуть тільки в пам'яті.** Після виходу з програми все зникає — при кожному запуску список порожній.

У демонстраційній темі викладача «Облік ноутбуків у сервісному центрі» головна сутність — **заявка на ремонт**, клас `RepairOrder` з властивостями `Id`, `OwnerName`, `Brand`, `Model`, `ReceivedDate`, `RepairCost`, `IsDone`, обчислюваною властивістю `DaysInService` і трьома нащадками: `WarrantyRepair` (поле `WarrantyUntil`), `PaidRepair` (поля `PartsCost`, `LaborCost`), `Diagnostics` (поле `FixedFee`). Спільний метод — `public virtual decimal GetTotal()`.

## Що змінюємо

Нічого не переписуємо з нуля. Цього тижня в проєкті відбуваються чотири зміни.

1. **Базовий клас стає абстрактним.** Створити «заявку взагалі», яка не є ні гарантійною, ні платною, ні діагностикою, неможливо в реальному сервісному центрі — отже, це має бути неможливим і в програмі. Слово `abstract` перед `class` цю можливість прибирає.
2. **Метод `GetTotal()` із `virtual` стає `abstract`.** У базовому класі він більше не має тіла: базовий клас не знає й не може знати, скільки коштує ремонт. Тепер компілятор **змусить** кожного нащадка написати свій `override`, а не мовчки успадкувати безглузду реалізацію.
3. **Клас реалізує два інтерфейси** — стандартний `IComparable<T>` (щоб `Sort()` умів упорядковувати заявки) і власний `IHasId` (щоб сховище вміло знаходити запис за номером).
4. **З'являється сховище.** Ви оголошуєте власний узагальнений інтерфейс `IRepository<T>` з операціями `Add`, `GetAll`, `GetById`, `Remove`, `Save`, `Load` і пишете його реалізацію `CsvRepository`, яка читає й пише CSV-файл — рівно те, що ви робили в лабораторній роботі №11. Список `List<...>` більше не лежить у `Program`: він захований усередині сховища. Після цієї роботи ваш застосунок уперше **запам'ятовує дані між запусками**.

## Теоретичні відомості

### 1. Абстрактний клас і абстрактний метод

Погляньте на ієрархію після ЛР14. У колекції лежать гарантійні ремонти, платні ремонти й діагностики. А чи може там лежати просто `RepairOrder`? Що це за заявка, у якої немає жодного різновиду, і скільки вона коштує? Рядок `var order = new RepairOrder();` синтаксично можливий, але змістовно беззмістовний. Ситуація, коли базовий клас потрібен як **спільний знаменник**, але сам по собі не описує жодного реального об'єкта, трапляється постійно: `Фігура` (а яка саме?), `Транспортний засіб`, `Працівник`, `Платіж`. Для таких класів у C# є спеціальне позначення.

**Абстрактний клас** — клас, позначений модифікатором `abstract`, екземпляр якого створити не можна. Він існує тільки для того, щоб від нього успадковувалися.

**Абстрактний метод** — метод, позначений `abstract`, який оголошено без тіла: після списку параметрів ставиться крапка з комою. Нащадок **зобов'язаний** його перевизначити, інакше програма не скомпілюється.

```csharp
public abstract class Figure
{
    public string Name { get; set; } = "фігура";

    // абстрактний: тіла немає, кожен нащадок рахує площу по-своєму
    public abstract double Area();

    // звичайний метод: реалізація спільна для всіх нащадків
    public void Print() => Console.WriteLine($"{Name}: площа = {Area():F2}");
}

public class Circle : Figure
{
    public double R { get; set; }
    public override double Area() => Math.PI * R * R;
}

public class Rectangle : Figure
{
    public double W { get; set; }
    public double H { get; set; }
    public override double Area() => W * H;
}

// var f = new Figure();   // помилка компіляції: екземпляр абстрактного класу створити не можна
Figure a = new Circle { Name = "коло", R = 2 };
Figure b = new Rectangle { Name = "прямокутник", W = 3, H = 4 };
a.Print();          // коло: площа = 12,57
b.Print();          // прямокутник: площа = 12,00
```

Зверніть увагу на три важливі речі. Абстрактний клас цілком може мати **звичайні** поля, властивості, конструктори й методи з тілом (`Name`, `Print`) — абстрактним є не весь клас, а лише позначені `abstract` члени. Змінна типу `Figure` існує й працює: заборонено не оголошувати змінну абстрактного типу, а виконувати `new` цього типу. І нарешті: якщо клас має хоча б один абстрактний член, сам клас **обов'язково** позначається `abstract`; зворотне не обов'язкове — абстрактний клас без абстрактних членів просто забороняє створювати себе напряму.

### 2. Чим абстрактний метод відрізняється від віртуального

Обидва дозволяють нащадкові підмінити поведінку. Різниця — в тому, чи є в базового класу розумна поведінка за замовчуванням.

| Ознака | `virtual` | `abstract` |
|---|---|---|
| Тіло методу в базовому класі | є | немає |
| Чи зобов'язаний нащадок перевизначати | ні, може успадкувати | так, інакше помилка компіляції |
| Чи можна створити екземпляр базового класу | так | ні (клас теж `abstract`) |
| Коли обирати | базова поведінка розумна, нащадок її уточнює | базовий клас не знає, що робити |
| Виклик `base.Метод()` у нащадкові | можливий і часто доречний | неможливий: тіла немає |

Найпоширеніша помилка початківця — залишати `virtual` там, де тіла нема чим наповнити: `public virtual decimal GetTotal() => 0;`, де нуль є вигадкою, а не значенням. Такий метод небезпечний: нащадок, автор якого забув написати `override`, мовчки поверне нуль, і помилка виявиться не під час компіляції, а в бухгалтерії. Абстрактний метод цю помилку робить неможливою.

### 3. Інтерфейс

**Інтерфейс** — іменований перелік членів (методів, властивостей, індексаторів, подій), які клас зобов'язується надати. Це **контракт**: інтерфейс описує, *що* об'єкт уміє, і нічого не каже про те, *як* він це робить і які має поля.

Оголошення й реалізація (через двокрапку, як і наслідування, але клас інтерфейс **реалізує**, а не успадковує):

```csharp
public interface IPrintable
{
    // модифікатори доступу не пишуть: усі члени інтерфейсу публічні
    void Print();
    string Caption { get; }
}

public class Invoice : IPrintable
{
    public int Number { get; set; }
    public decimal Sum { get; set; }

    public string Caption => $"Рахунок №{Number}";
    public void Print() => Console.WriteLine($"{Caption}: {Sum:F2} грн");
}

// змінна типу інтерфейсу приймає будь-який об'єкт, що його реалізує
var list = new List<IPrintable> { new Invoice { Number = 7, Sum = 1250 } };
foreach (var item in list)
    item.Print();                   // Рахунок №7: 1250,00 грн
```

Члени, які реалізують інтерфейс, обов'язково `public` і **без** слова `override` — інтерфейс не є базовим класом, тут нема чого перевизначати.

Це той самий поліморфізм, що й у ЛР14, але побудований не на спільному предкові, а на спільному вмінні: класи `Invoice` і `Report` можуть не мати жодного спільного предка, крім `object`, і все одно потрапити в один список — бо обидва вміють друкуватися.

### 4. Множинна, явна й типова реалізація інтерфейсів

C# не має множинного наслідування класів: у класу рівно один базовий клас. Але інтерфейсів клас може реалізувати **скільки завгодно** — саме тому вони й потрібні.

```csharp
public interface IHasId { int Id { get; } }
public interface IArchivable { void Archive(); }

public class Document : IPrintable, IHasId, IArchivable   // три контракти одночасно
{
    public int Id { get; set; }
    public string Caption => $"Документ №{Id}";
    public void Print() => Console.WriteLine(Caption);
    public void Archive() => Console.WriteLine($"{Caption} перенесено в архів");
}
```

Один об'єкт `Document` можна покласти в `List<IPrintable>`, у `List<IHasId>` і в `List<IArchivable>` — залежно від того, яке саме його вміння цікавить конкретний фрагмент коду. Ім'я інтерфейсу з `I` на початку — усталене правило іменування в .NET, дотримуйтеся його.

**Явна реалізація (коротко).** Якщо два інтерфейси вимагають методу з однаковою сигнатурою, але різним змістом, метод реалізують **явно** — указавши перед іменем назву інтерфейсу. Такий член не має модифікатора доступу й доступний лише через змінну типу інтерфейсу.

```csharp
public class Guide : IUkrainian, IEnglish     // обидва оголошують string Greet();
{
    string IUkrainian.Greet() => "Вітаю!";
    string IEnglish.Greet() => "Welcome!";
}

var guide = new Guide();                           // guide.Greet() — помилка компіляції
Console.WriteLine(((IUkrainian)guide).Greet());    // Вітаю!
Console.WriteLine(((IEnglish)guide).Greet());      // Welcome!
```

У навчальному проєкті явна реалізація знадобиться рідко, але ви натрапите на неї в бібліотеках .NET: наприклад, `List<T>` явно реалізує кілька старих не узагальнених інтерфейсів, щоб не засмічувати ними підказку середовища.

**Реалізація за замовчуванням (C# 8+) — згадка.** Починаючи з C# 8, інтерфейс може містити **тіло** методу; клас, що реалізує інтерфейс, може такий метод не писати.

```csharp
public interface ILogger
{
    void Log(string message);
    void LogError(string message) => Log($"ПОМИЛКА: {message}");   // тіло в інтерфейсі
}
```

Механізм додали передусім для того, щоб автори бібліотек могли дописати метод в інтерфейс, не зламавши тисячі вже написаних класів. У навчальному проєкті **не користуйтеся** ним: якщо у вашому «інтерфейсі» з'явилася реалізація, ви майже напевно хотіли абстрактний клас.

### 5. Абстрактний клас проти інтерфейсу: що коли обирати

| Питання | Абстрактний клас | Інтерфейс |
|---|---|---|
| Смислове відношення | «є різновидом» (заявка на гарантійний ремонт **є** заявкою) | «уміє» (заявку **можна** порівняти, зберегти, надрукувати) |
| Скільки їх може бути в класу | один | скільки завгодно |
| Може містити поля й стан | так | ні (лише властивості без поля-сховища) |
| Може містити код методів | так, будь-який | лише реалізацію за замовчуванням, і краще без неї |
| Може мати конструктор | так | ні |
| Може містити `private`/`protected` члени | так | ні, усе публічне |
| Що дає нащадкові | готовий код і стан | тільки зобов'язання |
| Типова роль у проєкті | спільна основа однієї родини класів | спільне вміння класів із різних родин |

Практичне правило: **спільні дані й спільний код — в абстрактний клас, спільні вміння — в інтерфейси**. У вашому проєкті вони працюють разом: абстрактний клас записів реалізує кілька інтерфейсів.

### 6. Інтерфейс `IComparable<T>` і метод `CompareTo`

Щоб відсортувати `List<int>`, достатньо викликати `Sort()`. Для `List<RepairOrder>` той самий виклик закінчиться винятком під час виконання: середовище не знає, яка заявка «менша».

**`IComparable<T>`** — стандартний інтерфейс з одним-єдиним методом `int CompareTo(T? other)`. Контракт методу простий і його треба запам'ятати. Виклик `a.CompareTo(b)` повертає:

| Значення | Означає |
|---|---|
| від'ємне число | `a` передує `b` (умовно «менше») |
| нуль | `a` і `b` рівноцінні щодо порядку |
| додатне число | `a` йде після `b` («більше») |

Конкретна величина значення не має: `-1` і `-17000` для сортування однакові. Тому реалізацію майже ніколи не пишуть вручну — її делегують тому полю, за яким упорядковують:

```csharp
public class Student : IComparable<Student>
{
    public string LastName { get; set; } = "";
    public double Average { get; set; }

    // основний порядок: за середнім балом, від меншого до більшого
    public int CompareTo(Student? other)
    {
        if (other is null) return 1;                 // будь-який об'єкт «більший» за null
        return Average.CompareTo(other.Average);     // хай порівнює double
    }
}

var students = new List<Student>
{
    new Student { LastName = "Мельник", Average = 88.5 },
    new Student { LastName = "Іванчук", Average = 74.0 },
    new Student { LastName = "Кравець", Average = 95.2 },
};
students.Sort();                                     // тепер Sort() працює
foreach (var s in students)
    Console.WriteLine($"{s.LastName,-10} {s.Average:F1}");
```

**Вивід:**

```
Іванчук    74,0
Мельник    88,5
Кравець    95,2
```

Щоб отримати спадний порядок, достатньо поміняти місцями операнди: `other.Average.CompareTo(Average)`. Щоб упорядкувати за двома полями — спочатку порівняти перше, і лише якщо результат нуль, порівняти друге (саме так зроблено в демонстраційному проєкті: за датою, а за однакової дати — за номером).

**Як `List.Sort()` цим користується.** Метод `Sort()` без параметрів бере елементи по два й питає в першого: «ти більший чи менший за другого?» — тобто викликає `CompareTo`. На підставі відповіді він переставляє елементи. Сам алгоритм (у .NET це інтроспективне сортування — гібрид швидкого, пірамідального й сортування вставками) вас не обходить: ви відповідаєте лише за правило порівняння. Те саме правило використовують `Array.Sort`, `List.BinarySearch` і сортовані колекції.

### 7. `IComparer<T>` — альтернативний порядок

`IComparable<T>` задає **один** порядок — «природний» для цього типу. А якщо в меню треба сортувати то за датою, то за сумою, то за прізвищем?

Для цього є другий інтерфейс — **`IComparer<T>`**. Його реалізує не сам клас записів, а окремий маленький клас-порівнювач:

```csharp
public class ByLastName : IComparer<Student>
{
    public int Compare(Student? a, Student? b)
    {
        if (a is null || b is null) return a is null && b is null ? 0 : (a is null ? 1 : -1);
        return string.Compare(a.LastName, b.LastName, StringComparison.CurrentCulture);
    }
}

students.Sort(new ByLastName());          // порівнювач передається у Sort параметром
// тепер порядок буде Іванчук, Кравець, Мельник — за алфавітом, а не за балом
```

Різниця в одному реченні: `IComparable` — «я вмію порівнювати себе з собі подібними», `IComparer` — «я стороння річ, яка вміє порівнювати двох інших». Скільки потрібно порядків — стільки й класів-порівнювачів; природний порядок при цьому лишається недоторканим.

### 8. Власний узагальнений інтерфейс сховища

У ЛР12–14 список записів лежав просто в `Program` і всі методи меню длубалися в ньому напряму. Це працює, доки застосунок маленький. Щойно з'являється збереження у файл, виникає питання: де саме має бути код читання й запису?

Правильна відповідь — в окремому класі, який відповідає **тільки** за зберігання. А щоб `Program` не залежав від того, куди саме пишуться дані (у CSV-файл, у текстовий файл іншого формату, у пам'ять під час тестування), між ними ставлять інтерфейс.

```csharp
// «у мене є числовий ідентифікатор»: потрібно, щоб сховище вміло шукати за номером
public interface IHasId { int Id { get; } }

// узагальнений контракт сховища будь-яких записів з ідентифікатором
public interface IRepository<T> where T : class, IHasId
{
    void Add(T item);          // додати запис
    List<T> GetAll();          // отримати всі записи
    T? GetById(int id);        // знайти за номером; null, якщо немає
    bool Remove(int id);       // видалити; false, якщо не знайдено
    void Save();               // вивантажити у файл
    void Load();               // завантажити з файлу
}
```

Запис `where T : class, IHasId` — це **обмеження узагальненого параметра**: «підставляти замість `T` можна лише посилальні типи, що реалізують `IHasId`». Обмеження потрібні з двох причин: по-перше, без `IHasId` компілятор не дозволив би звертатися до `item.Id` усередині реалізації; по-друге, без `class` не можна було б повернути `null` із `GetById`.

**Repository** (від англ. *repository* — сховище) — усталена назва такого класу. Перевага: `Program` оголошує змінну типу `IRepository<RepairOrder>`, а який саме клас за нею стоїть, вирішується в одному рядку. Замінити CSV на будь-що інше — це написати новий клас і змінити цей один рядок; решта програми не змінюється жодним символом.

### 9. Реалізація сховища поверх CSV і обробка помилок

Читання й запис CSV ви робили в ЛР11, тож нового тут лише те, що код заховано в клас. Три правила, про які варто нагадати.

**Кодування.** Записуйте й читайте з явним `Encoding.UTF8`, інакше кирилиця в файлі перетвориться на «кракозябри». **Культура при перетворенні чисел і дат.** Число `1450.75` в українській культурі записується як `1450,75` — із комою, яка в CSV є роздільником полів. Тому в файл числа й дати пишуть у **інваріантній культурі**:

```csharp
var ci = CultureInfo.InvariantCulture;                             // System.Globalization
string s = 1450.75m.ToString(ci);                                  // "1450.75"
string d = new DateTime(2025, 9, 1).ToString("yyyy-MM-dd", ci);    // "2025-09-01"
decimal back = decimal.Parse(s, ci);
```

**Помилки.** Файлові операції зривають виняток за десятком причин: файлу немає, немає прав, файл зайнято іншим процесом. Жодна з них не має завершувати застосунок. Тому кожен вхід у файлову систему обгортають у `try/catch` з окремими блоками для `UnauthorizedAccessException` та `IOException`, а рядок із зіпсованими даними пропускають із повідомленням про його номер, не втрачаючи решту файлу.

**Файл `RepairOrder.cs`** — абстрактний базовий клас.

```csharp
using System.Globalization;

namespace ServiceCenter;

// Клас абстрактний: «заявки взагалі» не буває, буває гарантійна, платна або діагностика.
public abstract class RepairOrder : IComparable<RepairOrder>, IHasId
{
    // --- З ЛР13 без жодної зміни: поля-сховища й властивості з перевіркою у сеттерах ---
    // Id, OwnerName, Brand, Model, ReceivedDate, RepairCost (попередня оцінка, названа
    // клієнтові при прийомі), IsDone, а також обчислювана властивість:
    public int DaysInService => (DateTime.Today - ReceivedDate).Days;

    // --- НОВЕ: абстрактні члени, які зобов'язаний надати кожен нащадок ---
    public abstract string Kind { get; }          // назва різновиду, вона ж перший стовпець CSV
    public abstract decimal GetTotal();           // сума до сплати; базовий клас її не знає
    protected abstract string ExtraToCsv();       // додаткові поля нащадка у вигляді частини рядка

    // --- спільна реалізація для всіх нащадків ---

    // Складання повного рядка CSV. Числа й дати — в інваріантній культурі,
    // щоб десяткова кома не сплуталася з роздільником полів.
    public string ToCsv()
    {
        var ci = CultureInfo.InvariantCulture;
        return string.Join(';', Kind, Id.ToString(ci), OwnerName, Brand, Model,
            ReceivedDate.ToString("yyyy-MM-dd", ci), RepairCost.ToString(ci),
            IsDone ? "1" : "0", ExtraToCsv());
    }

    // Природний порядок заявок — за датою прийому, від найдавнішої.
    public int CompareTo(RepairOrder? other)
    {
        if (other is null) return 1;              // будь-яка заявка «більша» за ніщо
        int byDate = ReceivedDate.CompareTo(other.ReceivedDate);
        return byDate != 0 ? byDate : Id.CompareTo(other.Id);   // далі — за номером
    }

    public override string ToString()
    {
        string status = IsDone ? "виконано" : "у роботі";
        return $"№{Id,-3} {Kind,-12} {OwnerName,-16} {Brand} {Model,-12} " +
               $"прийнято {ReceivedDate:dd.MM.yyyy} ({DaysInService,2} дн.) " +
               $"до сплати {GetTotal(),8:F2} грн  [{status}]";
    }
}
```

```csharp
using System.Globalization;

namespace ServiceCenter;

// Гарантійний ремонт: клієнт не платить нічого.
public class WarrantyRepair : RepairOrder
{
    public DateTime WarrantyUntil { get; set; }
    public bool IsWarrantyValid => ReceivedDate <= WarrantyUntil;   // чинна на момент прийому

    public override string Kind => "Гарантійний";
    public override decimal GetTotal() => 0m;

    protected override string ExtraToCsv() =>
        WarrantyUntil.ToString("yyyy-MM-dd", CultureInfo.InvariantCulture);
}

// Платний ремонт: запчастини плюс робота.
public class PaidRepair : RepairOrder
{
    public decimal PartsCost { get; set; }
    public decimal LaborCost { get; set; }

    public override string Kind => "Платний";
    public override decimal GetTotal() => PartsCost + LaborCost;

    protected override string ExtraToCsv()
    {
        var ci = CultureInfo.InvariantCulture;
        return string.Join(';', PartsCost.ToString(ci), LaborCost.ToString(ci));
    }
}

// Діагностика: фіксована плата за огляд. Kind => "Діагностика",
// GetTotal() => FixedFee, ExtraToCsv() => FixedFee.ToString(ci).
public class Diagnostics : RepairOrder { public decimal FixedFee { get; set; } /* ... */ }

// Порівнювач для альтернативного порядку: за сумою до сплати, від більшої до меншої.
public class CostDescendingComparer : IComparer<RepairOrder>
{
    public int Compare(RepairOrder? a, RepairOrder? b)
    {
        if (a is null && b is null) return 0;
        if (a is null) return 1;
        if (b is null) return -1;
        return b.GetTotal().CompareTo(a.GetTotal());   // операнди навмисно переставлено
    }
}
```

**Файл `CsvRepository.cs`** — реалізація сховища.

```csharp
using System.Globalization;
using System.Text;

namespace ServiceCenter;

public class CsvRepository : IRepository<RepairOrder>
{
    private const string Header = "Тип;Id;Власник;Марка;Модель;Прийнято;Оцінка;Виконано;Додатково";

    private readonly List<RepairOrder> items = new();
    private readonly string path;

    public CsvRepository(string fileName)
    {
        string folder = Path.Combine(Directory.GetCurrentDirectory(), "data");
        Directory.CreateDirectory(folder);            // якщо папки немає — створити
        path = Path.Combine(folder, fileName);
    }

    public void Add(RepairOrder item)
    {
        if (item is null)
            throw new ArgumentNullException(nameof(item), "Не можна додати порожнє посилання.");
        if (item.Id <= 0) item.Id = NextId();
        items.Add(item);
    }

    // Повертаємо копію списку: зовнішній код не має змоги
    // додати чи видалити запис в обхід сховища.
    public List<RepairOrder> GetAll() => new List<RepairOrder>(items);

    public RepairOrder? GetById(int id)
    {
        foreach (var order in items)
            if (order.Id == id) return order;
        return null;
    }

    public bool Remove(int id)
    {
        var found = GetById(id);
        if (found is null) return false;
        items.Remove(found);
        return true;
    }

    // Наступний вільний номер: на одиницю більший за найбільший наявний.
    private int NextId()
    {
        int max = 0;
        foreach (var order in items)
            if (order.Id > max) max = order.Id;
        return max + 1;
    }

    public void Save()
    {
        try
        {
            var lines = new List<string> { Header };
            foreach (var order in items)
                lines.Add(order.ToCsv());
            File.WriteAllLines(path, lines, Encoding.UTF8);
            Console.WriteLine($"Збережено записів: {items.Count}. Файл: {path}");
        }
        catch (UnauthorizedAccessException)
        { Console.WriteLine("Немає прав на запис у файл даних. Зміни не збережено."); }
        catch (IOException ex)
        { Console.WriteLine($"Помилка запису: {ex.Message}"); }
    }

    public void Load()
    {
        items.Clear();
        if (!File.Exists(path))
        {
            Console.WriteLine("Файл даних не знайдено — починаємо з порожнього журналу.");
            return;
        }

        try
        {
            string[] lines = File.ReadAllLines(path, Encoding.UTF8);
            for (int i = 1; i < lines.Length; i++)          // рядок 0 — заголовок
            {
                if (string.IsNullOrWhiteSpace(lines[i])) continue;
                var order = Parse(lines[i], i + 1);
                if (order is not null) items.Add(order);
            }
            Console.WriteLine($"Завантажено записів: {items.Count}.");
        }
        catch (IOException ex)
        { Console.WriteLine($"Помилка читання: {ex.Message}. Журнал порожній."); }
    }

    // Розбір одного рядка. Зіпсований рядок не валить програму:
    // метод повідомляє про нього й повертає null.
    private static RepairOrder? Parse(string line, int lineNumber)
    {
        var ci = CultureInfo.InvariantCulture;
        string[] p = line.Split(';');

        try
        {
            if (p.Length < 9) throw new FormatException("замало стовпців");

            // Перший стовпець вирішує, який саме клас-нащадок відтворити.
            RepairOrder order = p[0] switch
            {
                "Гарантійний" => new WarrantyRepair
                    { WarrantyUntil = DateTime.ParseExact(p[8], "yyyy-MM-dd", ci) },
                "Платний" => new PaidRepair
                    { PartsCost = decimal.Parse(p[8], ci), LaborCost = decimal.Parse(p[9], ci) },
                "Діагностика" => new Diagnostics
                    { FixedFee = decimal.Parse(p[8], ci) },
                _ => throw new FormatException($"невідомий тип «{p[0]}»")
            };

            order.Id = int.Parse(p[1], ci);
            order.OwnerName = p[2];
            order.Brand = p[3];
            order.Model = p[4];
            order.ReceivedDate = DateTime.ParseExact(p[5], "yyyy-MM-dd", ci);
            order.RepairCost = decimal.Parse(p[6], ci);
            order.IsDone = p[7] == "1";
            return order;
        }
        catch (Exception ex) when (ex is FormatException or IndexOutOfRangeException or ArgumentException)
        {
            Console.WriteLine($"Рядок {lineNumber} пропущено: {ex.Message}");
            return null;
        }
    }
}
```

## Хід роботи

1. Відкрийте папку свого проєкту з ЛР14 і переконайтеся, що він збирається командою `dotnet build` без помилок. Створіть гілку або просто зробіть коміт поточного стану, щоб мати куди відкотитися.
2. Додайте модифікатор `abstract` до оголошення базового класу й перетворіть `virtual`-метод на `abstract`: приберіть тіло, поставте крапку з комою. Зберіть проєкт. Компілятор покаже всі місця, де залишився `new БазовийКлас(...)` і де нащадок не має `override`, — виправте їх.
3. Додайте в базовий клас абстрактну властивість `Kind` (назва різновиду рядком) і реалізуйте її в кожному нащадкові. Використайте її в `ToString()` замість жорстко вписаних назв.
4. Оголосіть у базовому класі реалізацію `IComparable<ВашКлас>`: додайте інтерфейс у список після двокрапки й напишіть `CompareTo`. Оберіть змістовний природний порядок (за датою, за номером, за назвою) і поясніть вибір у звіті. Перевірте роботу `Sort()` без параметрів.
5. Створіть окремий клас-порівнювач, що реалізує `IComparer<ВашКлас>` і задає **інший** порядок — за числовим полем, за спаданням. Додайте в меню два окремі пункти сортування.
6. Створіть файл `Contracts.cs`: оголосіть інтерфейс `IHasId` і узагальнений `IRepository<T>` з обмеженням `where T : class, IHasId` та шістьма членами (`Add`, `GetAll`, `GetById`, `Remove`, `Save`, `Load`). Додайте `IHasId` до списку інтерфейсів базового класу.
7. Реалізуйте клас `CsvRepository`, який тримає `List<ВашКлас>` у приватному полі, будує шлях через `Path.Combine` до папки `data` і вміє зберігати та завантажувати записи в UTF-8. Числа й дати перетворюйте з `CultureInfo.InvariantCulture`. Кожну файлову операцію обгорніть у `try/catch`, а зіпсований рядок пропускайте з повідомленням про його номер.
8. Перепишіть `Program`: приберіть звідти список, оголосіть поле типу `IRepository<ВашКлас>`, викличте `Load()` на початку й `Save()` перед виходом. Переконайтеся, що жоден метод меню більше не звертається до `List` напряму.
9. Перевірте роботу застосунку на трьох сценаріях: файлу немає; файл коректний; у файл вручну вписано зіпсований рядок і рядок з невідомим типом запису. Зафіксуйте вивід кожного сценарію для звіту.
10. Створіть `.gitignore` (`dotnet new gitignore`) і зробіть коміт із повідомленням `Лабораторна 15: абстрактний клас, IComparable, збереження у CSV`. Файл із даними додайте до репозиторію, папки `bin` і `obj` — ні.

## Завдання за вашою темою

Доопрацюйте свій наскрізний проєкт (тема — за номером у списку групи) так, щоб він відповідав усім наведеним нижче вимогам. Приклад виконання зроблено на демонстраційній темі викладача, у вашій темі змінюються назви класів, полів і зміст обчислень — структура лишається тією самою.

1. **Базовий клас вашої сутності оголошено `abstract`.** У звіті одним абзацом поясніть, чому створити «запис узагалі» у вашій предметній області безглуздо.
2. **Щонайменше один метод базового класу оголошено `abstract`** і перевизначено в усіх нащадках. Це має бути метод, значення якого справді залежить від різновиду запису (сума, тривалість, підсумковий бал, обсяг, вартість зберігання).
3. **Додано абстрактну властивість-ознаку різновиду** (рядок або окремий метод), яка використовується у виводі й у файлі даних.
4. **Реалізовано `IComparable<T>`** з осмисленим природним порядком. Для тем із датою природним порядком беріть дату; для тем із рейтингом або оцінкою — відповідне число; для довідникових тем — назву за алфавітом. Обов'язково опрацюйте випадок `other is null`.
5. **Реалізовано окремий клас-порівнювач `IComparer<T>`** для альтернативного порядку (за іншим полем і в протилежному напрямку).
6. **Оголошено власні інтерфейси `IHasId` та `IRepository<T>`** рівно з тими шістьма членами, що в прикладі. Інтерфейс має лежати в окремому файлі.
7. **Написано клас-реалізацію `CsvRepository`**, яка зберігає всі записи у файл `data/*.csv` і читає їх під час запуску. Формат рядка має містити ознаку різновиду, щоб під час читання можна було відтворити правильний клас-нащадок.
8. **`Program` працює лише через змінну типу інтерфейсу.** Рядок `IRepository<ВашКлас> repo = new CsvRepository("...");` має бути єдиним місцем у програмі, де згадано конкретний клас сховища.
9. **Меню доповнено двома пунктами сортування** — за природним порядком і за порівнювачем; застосунок не падає за відсутності файлу, за порожнього файлу, за зіпсованого рядка й за невідомого типу запису.

Мінімальний обсяг даних для демонстрації — **вісім записів**, серед яких є всі різновиди з вашої ієрархії.

## Додаткове завдання (на вищу оцінку)

Додайте до проєкту **другу реалізацію того самого інтерфейсу** — клас `MemoryRepository`, який тримає записи лише в пам'яті та нічого не пише на диск (методи `Save` і `Load` виводять повідомлення й нічого більше не роблять).

Доповніть застосунок ключем командного рядка: якщо програму запущено як `dotnet run -- --memory`, використовується `MemoryRepository`, інакше — `CsvRepository`. Аргументи командного рядка приходять у параметр `args` методу `Main`:

```csharp
bool useMemory = args.Length > 0 && args[0] == "--memory";
IRepository<RepairOrder> repo = useMemory ? new MemoryRepository()
                                          : new CsvRepository("orders.csv");
// ... решта коду не змінюється жодним символом
```

У звіті поясніть, скільки рядків коду довелося змінити поза класом сховища, і сформулюйте, який саме виграш дало те, що `Program` залежав від інтерфейсу, а не від класу. Додатково реалізуйте в `CsvRepository` створення резервної копії: перед записом файл, якщо він існує, копіюється в `orders_backup.csv` методом `File.Copy` з параметром перезапису.

## Контрольні питання

1. Що таке абстрактний клас і чим він відрізняється від звичайного? Чи може абстрактний клас мати конструктор, і якщо так, то хто його викликає?
2. Чим абстрактний метод відрізняється від віртуального? Наведіть із власного проєкту приклад методу, для якого доречний саме `abstract`, і приклад, для якого доречний `virtual`.
3. Що станеться під час компіляції, якщо нащадок не перевизначить абстрактний метод? А якщо не перевизначить віртуальний? Що робить `List.Sort()` без параметрів, якщо елементи не реалізують `IComparable<T>`, і коли ви це помітите?
4. Що таке інтерфейс? Чому його члени не мають модифікаторів доступу й тіл?
5. Чому в C# клас може мати лише один базовий клас, але скільки завгодно інтерфейсів? Яку задачу це вирішує?
6. Коли слід обирати абстрактний клас, а коли інтерфейс? Дайте відповідь у термінах «є різновидом» і «уміє».
7. Який контракт методу `CompareTo`: що означають від'ємне значення, нуль і додатне? Як переписати `CompareTo`, щоб отримати зворотний порядок?
8. Чим `IComparable<T>` відрізняється від `IComparer<T>`? Навіщо потрібен другий, якщо є перший?
9. Навіщо `Program` оголошує змінну типу `IRepository<T>`, а не типу `CsvRepository`? Що саме стало простішим завдяки цьому в додатковому завданні?
