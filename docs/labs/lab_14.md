# Лабораторна робота №14

## Тема
Побудова ієрархії класів. Наслідування та поліморфізм

## Мета
Навчитися будувати ієрархію класів: виділяти спільну частину в базовий клас і описувати відмінності в похідних. Закріпити роботу з модифікаторами `virtual`, `override`, `sealed` і конструкторами нащадків. Зрозуміти механізм поліморфізму й пізнього зв'язування та навчитися зберігати різні різновиди записів в одній колекції базового типу. Виконати третій крок наскрізного проєкту.

## Тривалість
2 академічні години.

## Обладнання та програмне забезпечення
Персональний комп'ютер, .NET 8 SDK, будь-яке середовище розробки або текстовий редактор і термінал, система контролю версій Git.

## Що було на попередньому кроці

Після лабораторної роботи №13 проєкт працює на власному класі: перелік записів зберігається у `List<ВашКлас>`, поля описано властивостями з валідацією у сеттерах, номер роздає статичний лічильник, є обчислювана властивість і перевизначений `ToString()`. Меню з чотирьох дій — додати, показати всі, знайти, видалити — лишилося таким самим, як у ЛР12.

У демонстраційній темі «Облік ноутбуків у сервісному центрі» це клас `RepairOrder` із властивостями `Id`, `OwnerName`, `Brand`, `Model`, `ReceivedDate`, `RepairCost`, `IsDone`, обчислюваною властивістю `DaysInService`, двома конструкторами й колекцією `List<RepairOrder>`.

## Що змінюємо

Реальні записи однієї предметної області рідко бувають однаковими. Заявка на гарантійний ремонт, платний ремонт і проста діагностика мають спільне (власник, бренд, модель, дата), але рахуються по-різному: гарантійний ремонт для клієнта безкоштовний, платний складається з вартості запчастин і роботи, діагностика коштує фіксовану суму.

Перше, що спадає на думку, — додати в клас поле «тип заявки» і всюди писати `if` або `switch`. Так робити не варто: щойно з'явиться четвертий тип, доведеться шукати ці розгалуження по всій програмі й нічого не забути. Правильне рішення — **ієрархія класів**: спільне залишається в базовому класі, відмінне описується в нащадках, а спосіб обчислення оголошується **віртуальним методом**, який кожен нащадок перевизначає по-своєму.

Цього тижня клас із ЛР13 стає **базовим**; від нього успадковуються **три нащадки** з власними полями; у базовому класі з'являється `public virtual decimal GetTotal()`, а в кожного нащадка — `override`; колекція лишається **однією** (`List<RepairOrder>` зберігає об'єкти всіх трьох типів одночасно); меню й далі не переписується — додається лише вибір різновиду при створенні запису та звіт за різновидами. Для демонстраційної теми ієрархія така:

```
                    RepairOrder  (базовий клас)
                    Id · OwnerName · Brand · Model
                    ReceivedDate · RepairCost · IsDone
                    virtual decimal GetTotal()
                              ▲
              ┌───────────────┼────────────────┐
              │               │                │
     WarrantyRepair      PaidRepair       Diagnostics
     + WarrantyUntil     + PartsCost      + FixedFee
                         + LaborCost
     ремонт            запчастини        фіксована
     безкоштовний      + робота          сума
```

## Теоретичні відомості

### 1. Наслідування: базовий і похідний клас

**Наслідування** — механізм, за яким новий клас отримує всі члени наявного й додає власні. Клас, від якого успадковують, називають **базовим** (батьківським), клас, який успадковує, — **похідним** (нащадком). Записується двокрапкою:

```csharp
class Employee                       // базовий клас
{
    public string Name { get; set; } = "";
    public decimal Salary { get; set; }

    public void Print() => Console.WriteLine($"{Name}: {Salary:F2} грн");
}

class Manager : Employee             // похідний клас
{
    public int TeamSize { get; set; }      // власне поле нащадка
}

var m = new Manager { Name = "Коваль", Salary = 25000m, TeamSize = 6 };
m.Print();                                  // метод дістався у спадок
Console.WriteLine($"Підлеглих: {m.TeamSize}");
```

**Вивід:**

```
Коваль: 25000,00 грн
Підлеглих: 6
```

Відношення нащадка й предка читається як «є різновидом»: менеджер **є** працівником, гарантійний ремонт **є** заявкою. Якщо таке речення звучить безглуздо («двигун є автомобілем»), наслідування тут не підходить — там потрібне не наслідування, а поле («в автомобіля **є** двигун»).

C# підтримує **одиничне наслідування**: у класу рівно один безпосередній базовий клас; ланцюжок при цьому може бути будь-якої довжини, а от «успадкувати від двох класів одразу» не можна.

### 2. Що успадковується, а що ні

| Член базового класу | Чи дістається нащадку |
|---|---|
| `public` і `protected` поля, властивості, методи | так, і видно всередині нащадка |
| `private` члени | існують в об'єкті, але **не видно** з коду нащадка |
| статичні члени | так, вони спільні на всю ієрархію |
| **конструктори** | **ні** — нащадок пише власні |
| перевизначені методи (`override`) | так, разом із новою поведінкою |

Найважливіший рядок цієї таблиці — про конструктори. Нащадок не успадковує конструктори базового класу, зате **зобов'язаний** якийсь із них викликати: без цього не буде з чого скласти успадковану частину об'єкта.

### 3. Модифікатор protected і виклик base(...)

**`protected`** — доступ «для себе й для нащадків»: ззовні член не видно, а всередині похідних класів — видно. Це компроміс між `private` (нащадок нічого не бачить) і `public` (бачать усі). Виклик конструктора базового класу записується після двокрапки словом **`base`**:

```csharp
class Employee
{
    public string Name { get; }
    public decimal Salary { get; }
    protected string Department;      // видно нащадкам, не видно ззовні

    public Employee(string name, decimal salary)
    {
        Name = name;
        Salary = salary;
        Department = "Загальний";
    }
}

class Manager : Employee
{
    public int TeamSize { get; }

    // спершу виконається конструктор Employee, потім тіло цього конструктора
    public Manager(string name, decimal salary, int teamSize) : base(name, salary)
    {
        TeamSize = teamSize;
        Department = "Управління";    // protected-поле доступне
    }

    // звертання до базової реалізації через base.
    public override string ToString() => base.ToString() + $", підлеглих: {TeamSize}";
}
```

Порядок виконання: спочатку конструктор базового класу, потім конструктор нащадка. Це логічно — не можна добудовувати другий поверх, доки немає першого. Якщо `base(...)` не написати, компілятор мовчки підставить `: base()`, тобто виклик конструктора базового класу **без параметрів**; коли такого конструктора немає, програма не скомпілюється — це найчастіша помилка при першому знайомстві з наслідуванням.

### 4. virtual, override і sealed

Щоб нащадок міг **замінити** поведінку методу, базовий клас має це дозволити — оголосити метод **віртуальним**:

| Модифікатор | Де пишеться | Що означає |
|---|---|---|
| `virtual` | у базовому класі | метод дозволено перевизначати |
| `override` | у нащадку | метод замінює базову реалізацію |
| `sealed override` | у нащадку | перевизначення далі по ланцюжку заборонено |
| `sealed class` | перед класом | від класу не можна успадковувати |

```csharp
class Payment
{
    public decimal Amount { get; set; }

    public virtual decimal GetFee() => Amount * 0.02m;         // 2% за замовчуванням
}

class CardPayment : Payment
{
    public override decimal GetFee() => Amount * 0.015m;       // картка дешевша
}

sealed class CashPayment : Payment
{
    public override decimal GetFee() => 0m;                    // готівка без комісії
}
```

Перевизначати можна методи, властивості й індексатори — усе, що позначене `virtual`; сигнатура (ім'я, типи параметрів, тип результату) при перевизначенні має збігатися точно. `sealed` застосовують, коли подальші зміни поведінки були б помилкою: «готівкова оплата безкоштовна, і жоден нащадок не має права це змінити».

### 5. Ключове слово new: приховування замість перевизначення

Якщо в нащадку оголосити метод із тим самим іменем, але **без** `override`, компілятор видасть попередження й запропонує `new` — **приховування** базового члена. Виглядає схоже, працює принципово інакше:

```csharp
class Base
{
    public virtual string Who() => "Base";
    public string Info() => "інформація з Base";
}

class Correct : Base
{
    public override string Who() => "Correct";         // перевизначення
}

class Wrong : Base
{
    public new string Info() => "інформація з Wrong";  // приховування
}

Base a = new Correct();
Base b = new Wrong();
Console.WriteLine(a.Who());     // Correct — виклик пішов у нащадка
Console.WriteLine(b.Info());    // інформація з Base — виклик лишився в базовому класі!
Console.WriteLine(((Wrong)b).Info());   // інформація з Wrong
```

**Вивід:**

```
Correct
інформація з Base
інформація з Wrong
```

Різниця в тому, **за чим обирається метод**. При `override` — за реальним типом об'єкта, при `new` — за типом змінної. Через це той самий об'єкт поводиться по-різному залежно від того, у змінну якого типу його поклали. Це джерело помилок, які важко знайти, тому `new` для приховування в навчальних і робочих проєктах не застосовують. Якщо він знадобився — майже завжди це означає, що ієрархію спроєктовано неправильно.

### 6. Поліморфізм і пізнє зв'язування

**Поліморфізм** — здатність змінної базового типу посилатися на об'єкт будь-якого нащадка, а виклику віртуального методу — потрапляти в реалізацію того нащадка, який насправді лежить у пам'яті.

Змінній базового типу можна присвоїти об'єкт похідного — це **висхідне перетворення**, воно завжди безпечне: `Payment p = new CardPayment { Amount = 1000m };`, і виклик `p.GetFee()` дасть 15,0, бо спрацював метод `CardPayment`. Компілятор на етапі компіляції не знає, який саме метод виконається: змінна оголошена як `Payment`, а об'єкт може бути будь-яким нащадком. Рішення ухвалюється **під час виконання** за реальним типом об'єкта. Це й називають **пізнім (динамічним) зв'язуванням**.

```
  Payment p = new CardPayment { Amount = 1000m };
  p.GetFee();
       │
       │  тип ЗМІННОЇ — Payment, тому компілятор лише перевіряє,
       │  що в Payment є віртуальний метод GetFee()
       ▼
  ┌───────────────────────────────┐
  │ об'єкт у купі: CardPayment    │
  │ ┌───────────────────────────┐ │
  │ │ таблиця віртуальних       │ │
  │ │ методів об'єкта:          │ │
  │ │   GetFee ──▶ CardPayment  │ │   ← під час виконання
  │ └───────────────────────────┘ │      беруть адресу звідси
  │   Amount = 1000               │
  └───────────────────────────────┘
       │
       ▼
  виконується CardPayment.GetFee()  →  15,0
```

Практичний наслідок — головна ідея цієї роботи: **один список базового типу зберігає об'єкти всіх нащадків, і код працює з ними однаково**.

```csharp
var payments = new List<Payment>
{
    new Payment { Amount = 500m },
    new CardPayment { Amount = 1000m },
    new CashPayment { Amount = 2000m }
};

decimal totalFee = 0;
foreach (Payment p in payments)      // тип змінної — базовий
    totalFee += p.GetFee();          // виконується метод реального типу

Console.WriteLine($"Комісія загалом: {totalFee:F2}");
```

**Вивід:**

```
Комісія загалом: 25,00
```

У циклі немає жодного `if` про тип платежу. Коли з'явиться четвертий різновид, цей цикл **не зміниться взагалі** — саме заради цього й будують ієрархію.

### 7. Клас object — корінь ієрархії

Кожен тип у .NET прямо чи опосередковано успадковує від класу **`object`**, тому будь-який об'єкт має методи `ToString()`, `Equals()`, `GetHashCode()`, `GetType()`. Метод `GetType()` повертає **реальний** тип об'єкта — той, який створювали, а не той, у яку змінну його поклали:

```csharp
object o = new CardPayment { Amount = 100m };
Console.WriteLine(o.GetType().Name);      // CardPayment
Console.WriteLine(o);                     // працює ToString()
```

### 8. Перевірка типу: is, as і зіставлення зі зразком

Іноді потрібно дізнатися, який саме нащадок лежить у змінній базового типу, — наприклад, щоб вивести його особливе поле у звіті. Оператор **`is`** перевіряє тип і повертає `bool`; сучасна форма одразу оголошує змінну потрібного типу:

```csharp
foreach (Payment p in payments)
    if (p is CardPayment card)          // перевірка типу та оголошення змінної разом
        Console.WriteLine($"Картковий платіж на {card.Amount} грн");
```

Оператор **`as`** намагається перетворити тип і повертає `null`, якщо не вдалося (пряме приведення `(CardPayment)p` у такому разі кине виняток): `CardPayment? card = p as CardPayment;` — і далі перевірка `if (card != null)`. **Зіставлення зі зразком за типом** у `switch`-виразі зручне, коли різновидів кілька:

```csharp
string kind = p switch
{
    CardPayment => "картка",
    CashPayment => "готівка",
    _ => "інший спосіб"
};
```

Важливе застереження: перевірка типу — **не заміна** віртуальним методам. Якщо в коді з'явився ланцюжок `if (x is A) … else if (x is B) …`, який обчислює те саме різними способами, це ознака того, що потрібен віртуальний метод. Перевірку типу застосовують тоді, коли потрібне саме **особливе** поле нащадка, якого немає в базовому класі.

### 9. Коротко про перевизначення Equals

За замовчуванням `Equals` для класів порівнює **посилання**: два різні об'єкти з однаковим вмістом вважаються нерівними. Якщо для вашого типу рівність означає збіг ідентифікатора, `Equals` перевизначають:

```csharp
public override bool Equals(object? obj) => obj is RepairOrder other && other.Id == Id;
public override int GetHashCode() => Id.GetHashCode();
```

Правило: перевизначили `Equals` — обов'язково перевизначте й `GetHashCode()`, інакше об'єкт поводитиметься неправильно у `Dictionary` і `HashSet`; метод `Contains` у `List` після цього шукатиме за вашим правилом рівності, а не за посиланням.

## Приклад виконання

**Умова.** Перебудувати застосунок «Облік ноутбуків у сервісному центрі» на ієрархію класів. Клас `RepairOrder` стає базовим. Нащадки: `WarrantyRepair` (гарантійний ремонт, додаткове поле — дата закінчення гарантії, для клієнта безкоштовний), `PaidRepair` (платний ремонт, поля — вартість запчастин і вартість роботи), `Diagnostics` (діагностика, поле — фіксована плата). У базовому класі оголосити `public virtual decimal GetTotal()` — скільки клієнт платить фактично; у кожного нащадка перевизначити. Колекція лишається одна: `List<RepairOrder>`. Додати звіт за різновидами заявок.

**Аналіз.**

Спільне для всіх заявок — власник, бренд, модель, дата прийому, оголошена вартість і стан виконання. Це базовий клас, він лишається таким, як у ЛР13, плюс віртуальний метод.

`RepairCost` у базовому класі — це **оголошена (орієнтовна) вартість**, її називає приймальник. `GetTotal()` — **сума до сплати**, і вона рахується по-різному: у базовому класі повертає оголошену вартість, у гарантійного ремонту — нуль, у платного — сума запчастин і роботи, у діагностики — фіксована плата. Саме через цю різницю метод і робиться віртуальним.

Кожен нащадок викликає конструктор базового класу через `: base(...)`, передаючи спільні поля, і далі заповнює власні. Для платного ремонту в `base(...)` передається сума запчастин і роботи — так оголошена вартість одразу відповідає дійсності.

Щоб нащадки могли зібрати свій рядок виведення, у базовому класі з'являється `protected string ShortInfo()` — спільна частина опису. Ззовні вона не потрібна, тому не `public`.

Різновид заявки показує віртуальна властивість `Kind`. Вона потрібна для звіту і для таблиці, а `GetTotal()` — для грошей. Клас `Diagnostics` робимо `sealed`: діагностика — остаточний різновид, від неї успадковувати нічого.

Меню лишається тим самим. Додається лише вибір різновиду в дії «додати» і п'ятий пункт — звіт за різновидами, у якому задіяно зіставлення зі зразком за типом.

**Код (файл `RepairOrder.cs`, додане й змінене).** Усі властивості, валідація та конструктори лишаються з ЛР13 без змін; нижче наведено те, що додається до класу, і новий `ToString()`.

```csharp
class RepairOrder
{
    // ... поля, властивості, валідація й обидва конструктори — без змін із ЛР13 ...

    // Різновид заявки. Віртуальна властивість: кожен нащадок називає себе сам
    public virtual string Kind => "Заявка";

    // Скільки клієнт платить фактично. Нащадки рахують це по-своєму
    public virtual decimal GetTotal() => RepairCost;

    // Спільна частина опису: потрібна нащадкам, не потрібна зовнішньому коду
    protected string ShortInfo() =>
        $"{Id,3} | {OwnerName,-12} | {Brand,-7} | {Model,-12} | " +
        $"{ReceivedDate:dd.MM.yyyy} | {DaysInService,4}";

    // ToString() тепер спирається на віртуальні члени: рядок формується
    // однаково, а значення в ньому дає реальний тип об'єкта
    public override string ToString() =>
        $"{ShortInfo()} | {Kind,-12} | {GetTotal(),9:F2} | " +
        (IsDone ? "готово" : "в роботі");

    // Дві заявки вважаємо однаковими, якщо збігаються їхні номери
    public override bool Equals(object? obj) => obj is RepairOrder other && other.Id == Id;
    public override int GetHashCode() => Id.GetHashCode();
}
```

```csharp
// --- Гарантійний ремонт: клієнт не платить нічого ---
class WarrantyRepair : RepairOrder
{
    public DateTime WarrantyUntil { get; init; }

    public override string Kind => "гарантійний";

    public WarrantyRepair(string ownerName, string brand, string model,
                          DateTime receivedDate, decimal repairCost,
                          DateTime warrantyUntil)
        : base(ownerName, brand, model, receivedDate, repairCost)
    {
        if (warrantyUntil < receivedDate)
            throw new ArgumentException("Гарантія закінчилася раніше за прийом техніки.",
                                        nameof(warrantyUntil));
        WarrantyUntil = warrantyUntil;
    }

    // Роботи виконує виробник, тому клієнт платить 0
    public override decimal GetTotal() => 0m;

    public override string ToString() =>
        base.ToString() + $" | гарантія до {WarrantyUntil:dd.MM.yyyy}";
}

// --- Платний ремонт: запчастини плюс робота ---
class PaidRepair : RepairOrder
{
    public decimal PartsCost { get; set; }
    public decimal LaborCost { get; set; }

    public override string Kind => "платний";

    public PaidRepair(string ownerName, string brand, string model,
                      DateTime receivedDate, decimal partsCost, decimal laborCost)
        : base(ownerName, brand, model, receivedDate, partsCost + laborCost)
    {
        if (partsCost < 0 || laborCost < 0)
            throw new ArgumentException("Складники вартості не можуть бути від'ємними.");
        PartsCost = partsCost;
        LaborCost = laborCost;
    }

    public override decimal GetTotal() => PartsCost + LaborCost;

    public override string ToString() =>
        base.ToString() + $" | запчастини {PartsCost:F2} + робота {LaborCost:F2}";
}

// --- Діагностика: фіксована плата. sealed: далі успадковувати нічого ---
sealed class Diagnostics : RepairOrder
{
    public decimal FixedFee { get; init; }

    public override string Kind => "діагностика";

    public Diagnostics(string ownerName, string brand, string model,
                       DateTime receivedDate, decimal fixedFee)
        : base(ownerName, brand, model, receivedDate, fixedFee)
    {
        if (fixedFee < 0)
            throw new ArgumentException("Плата за діагностику не може бути від'ємною.",
                                        nameof(fixedFee));
        FixedFee = fixedFee;
    }

    public override decimal GetTotal() => FixedFee;
}
```

**Що тут варто помітити.**

У списку `orders` лежать об'єкти трьох різних класів, але оголошений він як `List<RepairOrder>`. Цикл у `PrintAll` нічого не знає про різновиди: він викликає `ToString()` і `GetTotal()`, а яка саме реалізація виконається, вирішується під час виконання; додайте четвертий різновид — цей цикл не зміниться.

Гарантійна заявка показала «до сплати 0,00», хоча її `RepairCost` дорівнює 1250 грн. Це не помилка: оголошена вартість робіт лишилася в базовому полі (вона потрібна для звіту перед виробником), а `GetTotal()` повернув те, що платить клієнт. `PaidRepair` передає в `base(...)` суму `partsCost + laborCost`, тому оголошена вартість одразу відповідає фактичній, а `Diagnostics` оголошено `sealed` — успадкувати від нього вже не можна.

У `ToString()` нащадків використано `base.ToString()`: спільна частина рядка формується один раз у базовому класі, нащадок лише дописує своє. Так само працює `protected`-метод `ShortInfo()` — він доступний нащадкам і недоступний коду поза ієрархією. І єдине місце, де знадобилося зіставлення зі зразком за типом, — звіт, бо там потрібні **особливі поля** нащадків (`FixedFee`, `RepairCost` гарантійної заявки), яких немає в базовому класі. Обчислення грошей у звіті все одно спирається на віртуальний `GetTotal()`, а не на `if` про тип.

## Завдання за вашою темою

Тема лишається та сама — за вашим номером у списку групи. Різновиди для ЛР14 підказані в описі вашої теми (колонка «Різновиди»), але ви можете уточнити їх, якщо запропонуєте змістовніший поділ.

1. **Базовий клас** — той, що написаний у ЛР13. Він лишається з усіма властивостями, валідацією й конструкторами; переписувати його не потрібно.

2. **Три похідні класи**, кожен із яких додає **щонайменше одне власне поле** (властивість), якого немає в базовому класі; має конструктор, що передає спільні поля в `: base(...)` і перевіряє власні; перевизначає віртуальний метод і віртуальну властивість `Kind`; перевизначає `ToString()` із викликом `base.ToString()`.

3. **Віртуальний метод у базовому класі** — головна величина вашої теми, яка рахується по-різному для різних різновидів: вартість, тривалість, підсумковий бал, знижка, час доставки, штраф. Реалізації в трьох нащадках мають справді відрізнятися формулою, а не лише коефіцієнтом, узятим із повітря.

4. **`protected`-член** у базовому класі, яким користується хоча б один нащадок.

5. **Один із класів оголосіть `sealed`** і поясніть у звіті, чому саме він не потребує нащадків.

6. **Одна колекція** `List<БазовийКлас>` для записів усіх різновидів. Окремих списків для кожного різновиду бути не повинно — це найгрубіша помилка цієї роботи.

7. **Меню не переписуємо.** Змінюються лише дія «додати» (вибір різновиду) і додається п'ятий пункт — звіт за різновидами з підрахунком кількості й суми по кожному.

8. **Коміт** із повідомленням `Лабораторна 14: ієрархія класів, наслідування та поліморфізм`.

Головна ідея, яку має продемонструвати ваша робота: **один список базового типу зберігає різні нащадки, і код працює з ними однаково**. Якщо у вашій програмі виведення таблиці містить `if` про тип запису — завдання виконано неправильно, цю роботу має робити віртуальний метод.

Додайте до ієрархії **четвертий різновид** запису — такий, якого немає в підказці до вашої теми, і придумайте для нього власну формулу обчислення. Зафіксуйте у звіті, скільки рядків **уже написаного** коду довелося змінити, щоб новий різновид запрацював у таблиці, у пошуку й у підсумку. Якщо ієрархію спроєктовано правильно, змін буде мінімум, і це — головний висновок завдання.

Додатково реалізуйте у звіті за різновидами **виведення найдорожчого (найбільшого за значенням віртуального методу) запису кожного різновиду**: пройдіть список один раз, тримаючи три змінні типу базового класу, для кожної перевіряйте тип через `is` і порівнюйте значення віртуального методу (LINQ у цьому семестрі не використовується, усе робиться циклами). І останнє: перевизначте в базовому класі `Equals` та `GetHashCode` так, щоб записи вважалися однаковими за номером, і продемонструйте, як після цього поводиться `orders.Contains(new ВашКлас(...))`. Поясніть у звіті, що змінилося порівняно з поведінкою за замовчуванням.

## Контрольні питання

1. Що таке наслідування? За якою ознакою перевіряють, чи доречне воно в конкретній парі класів, і чому «двигун — автомобіль» наслідуванням не описують?
2. Які члени базового класу дістаються нащадку, а які ні? Чому конструктори не успадковуються?
3. Що робить запис `: base(...)` і що станеться, якщо його не написати, а конструктора без параметрів у базовому класі немає?
4. У якому порядку виконуються конструктори базового й похідного класів? Чому саме в такому?
5. Чим `protected` відрізняється від `private` і `public`? Наведіть приклад члена свого базового класу, для якого доречний саме `protected`.
6. Для чого метод позначають `virtual`? Що станеться, якщо в нащадку написати `override` для методу, не позначеного `virtual` у базовому класі?
7. Чим `override` відрізняється від `new`? Поясніть на прикладі, чому виклик методу через змінну базового типу в цих двох випадках дає різний результат.
8. Що таке поліморфізм і пізнє зв'язування? Хто і в який момент вирішує, яка саме реалізація віртуального методу виконається?
9. Навіщо колекцію оголошують типу базового класу? Що б довелося змінити у вашій програмі, якби для кожного різновиду записів існував окремий список?
10. Коли доречно перевіряти тип через `is` або зіставлення зі зразком, а коли така перевірка є ознакою погано спроєктованої ієрархії?

## Зміст звіту

1. Титульна сторінка: назва закладу, дисципліна, номер і тема роботи, група, прізвище та ім'я студента, номер і назва теми проєкту, прізвище викладача.
2. Мета роботи.
3. Схема спроєктованої ієрархії (як на початку цієї методички): базовий клас, три нащадки, їхні власні поля й перевизначені члени.
4. Обґрунтування поділу: що винесено в базовий клас і чому, чим відрізняються нащадки, за якою формулою кожен із них обчислює віртуальний метод, який клас оголошено `sealed` і чому.
5. Лістинг базового класу (можна навести лише доданий і змінений код щодо ЛР13), повний лістинг файлу з нащадками та змінені частини `Program.cs` — зі створенням об'єкта потрібного різновиду й звітом, з коментарями українською мовою.
6. Вивід програми: таблиця з записами всіх трьох різновидів і звіт за різновидами.
7. Таблиця тестування: додавання запису кожного різновиду, спроба ввести неприпустиме значення у власному полі нащадка, звіт на порожньому списку.
8. Відповідь на питання, скільки рядків коду довелося змінити при додаванні четвертого різновиду (якщо виконувалося додаткове завдання), і вивід команди `git log --oneline` з історією проєкту.
9. Відповіді на 3 контрольні питання, номери яких вказує викладач.
10. Висновок: 3–5 речень про те, що дала ієрархія порівняно з одним класом і полем «тип запису».

## Критерії оцінювання

| Бали | Критерій |
|---|---|
| 6 | Ієрархію спроєктовано правильно: базовий клас містить спільне, три нащадки — власні поля й конструктори з `: base(...)`, віртуальний метод перевизначено трьома різними формулами, є `protected`-член, один клас `sealed`. Колекція одна, типу базового класу; у виведенні немає жодного `if` про тип. Працює звіт за різновидами зі зіставленням зі зразком. Виконано додаткове завдання. Коміт зроблено, звіт повний. |
| 5 | Ієрархія повна й працює, усі обов'язкові елементи присутні, поліморфізм використано правильно. Додаткове завдання виконано частково. Дрібні недоліки: формула одного з нащадків надто схожа на базову, або `base.ToString()` не використано й спільна частина продубльована. |
| 4 | Три нащадки створено, віртуальний метод перевизначено, колекція одна. Але є суттєві недоліки: власні поля нащадків не перевіряються, `protected` не застосовано, у виведенні трапляється розгалуження за типом. Додаткове завдання не виконано. |
| 3 | Наслідування реалізовано формально: нащадки майже не відрізняються від базового класу, або замість `virtual`/`override` використано `new`, або для кожного різновиду заведено окремий список. Звіт за різновидами відсутній. |
| 2 | Похідні класи оголошено, але програма їх не використовує: у колекції лежать об'єкти лише базового класу. Програма не компілюється без виправлень або меню переписано наново. Звіт неповний. |
| 0 | Роботу не виконано, здано чужий код або студент не може пояснити, чому виклик віртуального методу в його програмі потрапляє в потрібного нащадка. |
