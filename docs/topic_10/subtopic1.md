# try, catch, finally, using

## Ідея у двох реченнях

Ви обгортаєте небезпечний код у блок `try`. Якщо всередині щось піде не так,
керування миттєво стрибає у відповідний блок `catch`, і програма не падає.

Це все. Далі — деталі, яких насправді багато, і кожна з них колись врятує вам
вечір.

## Повний синтаксис

```csharp
try
{
    // Код, який може кинути виняток.
    // Виконується згори вниз, доки все добре.
}
catch (FormatException ex)
{
    // Виконається, ЯКЩО у try кинуто FormatException (або його нащадка).
    // ex — об'єкт винятку, з якого можна дістати Message, StackTrace тощо.
}
catch (OverflowException)
{
    // Ім'я змінної можна не писати, якщо воно вам не потрібне.
}
catch (Exception ex)
{
    // Найзагальніший catch: ловить усе, що не спіймали попередні.
}
finally
{
    // Виконається у будь-якому випадку: і коли винятку не було,
    // і коли він був і його спіймали, і коли його НЕ спіймали.
}
```

Правила комбінування:

| Комбінація | Дозволено | Коли використовують |
| --- | --- | --- |
| `try` + один `catch` | ✅ | найчастіший випадок |
| `try` + кілька `catch` | ✅ | різна реакція на різні винятки |
| `try` + `finally` без `catch` | ✅ | «не ловимо, але прибрати за собою треба» |
| `try` + `catch` + `finally` | ✅ | повний варіант |
| `try` сам по собі | ❌ помилка компіляції | потрібен хоча б один `catch` або `finally` |

:::note
Фігурні дужки після `try`, `catch` і `finally` **обов'язкові**, навіть якщо
всередині один рядок. Скорочений запис, як у `if`, тут не дозволений.
:::

## Як керування рухається насправді

Найважливіше — зрозуміти, що виконання **не повертається** назад у `try`
після `catch`. Подивіться на схему.

```
             ┌─────────────────────────────┐
             │  try                        │
             │    рядок 1   ✔ виконався    │
             │    рядок 2   ✘ ВИНЯТОК ─────┼──┐
             │    рядок 3   — пропущено    │  │
             │    рядок 4   — пропущено    │  │
             └─────────────────────────────┘  │
                                              │
             ┌─────────────────────────────┐  │
             │  catch (FormatException)    │◀─┘  тип збігся
             │    обробка                  │
             └──────────────┬──────────────┘
                            │
             ┌──────────────▼──────────────┐
             │  finally                    │  виконується завжди
             └──────────────┬──────────────┘
                            │
             ┌──────────────▼──────────────┐
             │  код після всієї конструкції│  програма живе далі
             └─────────────────────────────┘
```

Рядки 3 і 4 не виконаються ніколи. Це головна причина типової студентської
плутанини: «я ж далі присвоїв змінній значення» — ні, не присвоїли,
до того рядка виконання не дійшло.

Перевіримо це кодом:

```csharp
Console.WriteLine("До try");

try
{
    Console.WriteLine("Крок 1");
    int x = int.Parse("не число");   // FormatException
    Console.WriteLine("Крок 2");     // не виконається
}
catch (FormatException)
{
    Console.WriteLine("Спіймали FormatException");
}
finally
{
    Console.WriteLine("finally");
}

Console.WriteLine("Після try");
```

**Вивід:**

```
До try
Крок 1
Спіймали FormatException
finally
Після try
```

## Кілька блоків catch: від конкретного до загального

Коли виняток кинуто, .NET перебирає блоки `catch` **згори вниз** і зупиняється
на **першому**, тип якого підходить. Не на найкращому — на першому.

Тому порядок критичний.

```csharp
Console.Write("Введіть дільник: ");
string input = Console.ReadLine() ?? "";

try
{
    int divisor = int.Parse(input);
    int result = 100 / divisor;
    Console.WriteLine($"100 / {divisor} = {result}");
}
catch (FormatException)
{
    Console.WriteLine("Це не схоже на ціле число.");
}
catch (OverflowException)
{
    Console.WriteLine("Число завелике для типу int.");
}
catch (DivideByZeroException)
{
    Console.WriteLine("На нуль ділити не можна.");
}
catch (Exception ex)
{
    // Страхувальна сітка: щось, чого ми не передбачили
    Console.WriteLine($"Несподівана помилка: {ex.GetType().Name} — {ex.Message}");
}
```

**Вивід** для різних введень:

```
Введіть дільник: 4
100 / 4 = 25

Введіть дільник: 0
На нуль ділити не можна.

Введіть дільник: чотири
Це не схоже на ціле число.

Введіть дільник: 99999999999
Число завелике для типу int.
```

### Чому саме такий порядок

Усі винятки — нащадки класу `Exception`. Це означає, що `catch (Exception)`
ловить **геть усе**. Якщо поставити його першим, решта блоків стануть
недосяжними:

```csharp
try
{
    int x = int.Parse("abc");
}
catch (Exception ex)          // ловить усе
{
    Console.WriteLine("Загальна помилка");
}
catch (FormatException ex)    // ← сюди ніколи не потрапимо
{
    Console.WriteLine("Формат");
}
```

На щастя, тут не треба нічого запам'ятовувати: компілятор **не дасть** так
написати.

**Помилка компіляції:**

```
error CS0160: A previous catch clause already catches all exceptions of this
or of a super type ('Exception')
```

Правило формулюється просто: **від конкретного до загального, зверху вниз**.
Так само, як у сортуванні пошти: спочатку «листи для Петренка», потім
«листи для нашого відділу», і лише в кінці «решта».

```
        Exception              ← найзагальніший, ЗАВЖДИ останній
            ▲
    ┌───────┴────────┐
 SystemException  ...          ← середній рівень
    ▲
 ┌──┴───┬─────────┬──────────────┐
 Format  Overflow  DivideByZero   ← конкретні, ЗАВЖДИ першими
```

:::tip Порада
Не пишіть `catch (Exception)` «про всяк випадок» у кожному методі. Ловіть
те, що ви справді вмієте обробити. Загальний `catch` доречний в одному
місці — на самому верху програми, як остання страхувальна сітка,
щоб користувач замість стек-трейсу побачив людське повідомлення.
:::

## Фільтри винятків: catch ... when

Іноді тип винятку однаковий, а реагувати треба по-різному. Класичний приклад —
`HttpRequestException` з різними кодами, або `IOException` з різними причинами.
Для цього у C# 6 з'явилися **фільтри винятків**: до `catch` дописується умова
`when`.

```csharp
try
{
    ProcessOrder(quantity);
}
catch (ArgumentException ex) when (ex.ParamName == "quantity")
{
    Console.WriteLine("Проблема саме з кількістю товару.");
}
catch (ArgumentException ex)
{
    Console.WriteLine($"Інша проблема з аргументом: {ex.Message}");
}
```

Умова у `when` — це звичайний вираз типу `bool`. Якщо він `true`, блок
спрацьовує; якщо `false`, .NET шукає далі, ніби цього `catch` не існує.

Практичний приклад — повторні спроби:

```csharp
int attempt = 0;

while (true)
{
    try
    {
        attempt++;
        Console.WriteLine($"Спроба {attempt}...");
        ReadDataFromDisk();          // може кинути IOException
        Console.WriteLine("Успіх");
        break;
    }
    catch (IOException) when (attempt < 3)
    {
        Console.WriteLine("Не вдалося, пробуємо ще раз через секунду.");
        Thread.Sleep(1000);
    }
    // якщо attempt >= 3, фільтр не спрацює, і виняток полетить далі вгору
}
```

Тут `when (attempt < 3)` каже: «перші дві невдачі мене не турбують, а третю
пропусти нагору — хай розбирається той, хто нас викликав».

:::info Цікаво
`when` — не просто синтаксичний цукор для `if` усередині `catch`. Є важлива
технічна різниця: фільтр обчислюється **до** розкручування стека. Якщо
умова хибна, стек лишається недоторканим, і у стек-трейсі зберігається повна
інформація про місце винятку. Якщо ж ви спіймали виняток і зробили
`throw;` усередині — частина контексту вже втрачена. Тому у промисловому
коді `when` цінують.
:::

## finally: код, який виконається майже завжди

Блок `finally` потрібен для **прибирання за собою**: закрити файл, закрити
з'єднання, повернути курсор миші у нормальний стан, вивести «операція
завершена».

```csharp
StreamWriter? writer = null;

try
{
    writer = new StreamWriter("report.txt");
    writer.WriteLine("Заголовок звіту");
    int x = int.Parse("bad");        // виняток!
    writer.WriteLine("Дані");        // не виконається
}
catch (FormatException)
{
    Console.WriteLine("Помилка формату даних.");
}
finally
{
    writer?.Close();                 // файл закриється у будь-якому разі
    Console.WriteLine("Файл закрито.");
}
```

Без `finally` файл лишився б відкритим, а на диску — недописаним.

### Наскільки «завжди» — це завжди

`finally` виконується:

- коли `try` завершився нормально;
- коли виняток кинуто і спіймано у `catch`;
- коли виняток кинуто і **не** спіймано (перед тим, як полетіти вище);
- коли у `try` є `return`, `break` або `continue`.

Останній пункт особливо цікавий:

```csharp
int Test()
{
    try
    {
        Console.WriteLine("У try");
        return 1;                // ← виходимо з методу...
    }
    finally
    {
        Console.WriteLine("У finally");   // ...але це все одно виконається
    }
}

Console.WriteLine($"Метод повернув {Test()}");
```

**Вивід:**

```
У try
У finally
Метод повернув 1
```

`finally` **не** виконується лише у справді екстремальних випадках:

| Ситуація | Чи виконається `finally` |
| --- | --- |
| звичайний виняток | ✅ так |
| `return` / `break` у `try` | ✅ так |
| необроблений виняток | ✅ так, перед завершенням |
| `Environment.Exit(0)` | ❌ ні — процес убивають одразу |
| `StackOverflowException` | ❌ ні — стека вже немає |
| вимкнули живлення | ❌ ні (сподіваюсь, це очевидно) |

:::warning Обережно
Ніколи не пишіть `return` усередині `finally`. Він «перебиває» і те значення,
яке метод збирався повернути, і навіть виняток, який летів угору — той
просто зникне, і ви ніколи не дізнаєтесь про помилку. Компілятор C#
на це лається (`CS0157`), і правильно робить.
:::

## using: коротший і надійніший finally

Найчастіше `finally` пишуть заради одного: закрити ресурс. Це буває так часто,
що для цього придумали окрему конструкцію.

Будь-який тип, який володіє «зовнішнім» ресурсом (файл, мережеве з'єднання,
шрифт, з'єднання з базою), реалізує інтерфейс `IDisposable` — тобто має метод
`Dispose()`, який усе звільняє.

**Було** — вручну:

```csharp
StreamReader reader = new StreamReader("data.txt");
try
{
    string content = reader.ReadToEnd();
    Console.WriteLine(content);
}
finally
{
    reader.Dispose();     // закриє файл навіть при винятку
}
```

**Стало** — оператор `using`:

```csharp
using (StreamReader reader = new StreamReader("data.txt"))
{
    string content = reader.ReadToEnd();
    Console.WriteLine(content);
}   // ← тут автоматично викликається reader.Dispose()
```

Компілятор перетворює другий варіант рівно на перший. Це не «магія» —
це скорочення.

**Стало ще коротше** — `using`-оголошення (C# 8):

```csharp
using StreamReader reader = new StreamReader("data.txt");

string content = reader.ReadToEnd();
Console.WriteLine(content);

// Dispose() викличеться в кінці блоку, у якому оголошено reader
// (наприклад, у кінці методу)
```

Зникли зайві дужки і зайвий рівень вкладеності. У сучасному C# пишуть саме так.

| Форма | Коли зручніша |
| --- | --- |
| `using (...) { ... }` | ресурс потрібен лише у невеликому шматку коду; кілька ресурсів із різним часом життя |
| `using ... ;` (оголошення) | ресурс потрібен до кінця методу; хочеться менше вкладеності |
| ручний `try/finally` | треба зробити щось складніше, ніж просто `Dispose` |

`using` чудово поєднується з `try/catch`:

```csharp
try
{
    using StreamReader reader = new StreamReader("data.txt");
    Console.WriteLine(reader.ReadToEnd());
}
catch (FileNotFoundException)
{
    Console.WriteLine("Файл data.txt не знайдено.");
}
```

Файл закриється, а виняток буде оброблено. Докладніше про роботу з файлами —
у темі 12; тут `using` цікавий саме як інструмент керування ресурсами.

## throw; проти throw ex;

Ситуація: ви спіймали виняток, щось із ним зробили (наприклад, записали в лог),
але вважаєте, що обробити його по-справжньому має хтось вище. Треба кинути
його далі. Є два записи, і різниця між ними принципова.

```csharp
catch (Exception ex)
{
    Console.WriteLine("Логуємо...");
    throw;        // ВАРІАНТ 1: кинути той самий виняток далі
}
```

```csharp
catch (Exception ex)
{
    Console.WriteLine("Логуємо...");
    throw ex;     // ВАРІАНТ 2: кинути цей об'єкт заново
}
```

Виглядає майже однаково. Але `throw ex;` **стирає стек-трейс**: .NET вважає,
що виняток народився тут, у цьому рядку, і забуває всю історію до нього.

Порівняємо на живому прикладі.

```csharp
try
{
    Level1();
}
catch (Exception ex)
{
    Console.WriteLine(ex.StackTrace);
}

void Level1() => Level2();

void Level2()
{
    try
    {
        int[] data = [1, 2, 3];
        Console.WriteLine(data[10]);      // рядок 18
    }
    catch (Exception)
    {
        throw;            // або throw ex; — порівняємо
    }
}
```

**Вивід із `throw;`:**

```
   at Program.<<Main>$>g__Level2|0_1() in C:\Demo\Program.cs:line 18
   at Program.<<Main>$>g__Level1|0_0() in C:\Demo\Program.cs:line 12
   at Program.<Main>$(String[] args) in C:\Demo\Program.cs:line 3
```

Видно все: справжнє місце падіння — рядок 18.

**Вивід із `throw ex;`:**

```
   at Program.<<Main>$>g__Level2|0_1() in C:\Demo\Program.cs:line 22
   at Program.<<Main>$>g__Level1|0_0() in C:\Demo\Program.cs:line 12
   at Program.<Main>$(String[] args) in C:\Demo\Program.cs:line 3
```

Рядок 18 зник. Замість нього — рядок 22, тобто сам `throw ex;`. Інформація
про те, що зламався саме доступ `data[10]`, втрачена назавжди.

:::danger Часта помилка
**`throw ex;` — це майже завжди помилка.** Ви руками знищуєте найцінніше,
що є у винятку: місце, де він виник. Пишіть просто `throw;`.

Виняток із правила один: коли ви **свідомо** загортаєте виняток в інший,
щоб додати контексту, і зберігаєте оригінал усередині:

```csharp
catch (FormatException ex)
{
    throw new InvalidOperationException("Не вдалося прочитати конфігурацію", ex);
    //                                    зберігаємо оригінал ↑ (InnerException)
}
```
:::

Другий аргумент конструктора стає властивістю `InnerException`, і повний
ланцюжок можна вивести так:

```csharp
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
    if (ex.InnerException is not null)
    {
        Console.WriteLine($"Первинна причина: {ex.InnerException.Message}");
    }
}
```

## Вкладені try

Блоки `try` можна вкладати один в одного. Це доречно, коли внутрішня частина
має власну, дрібнішу проблему, після якої зовнішня робота все ще має сенс.

```csharp
string[] fileNames = ["a.txt", "b.txt", "c.txt"];
int successCount = 0;

try
{
    Console.WriteLine("Починаємо обробку файлів...");

    foreach (string name in fileNames)
    {
        try
        {
            string text = File.ReadAllText(name);
            Console.WriteLine($"{name}: {text.Length} символів");
            successCount++;
        }
        catch (FileNotFoundException)
        {
            // Один файл не знайшовся — це не привід зупиняти всю обробку
            Console.WriteLine($"{name}: файл відсутній, пропускаємо");
        }
    }

    Console.WriteLine($"Оброблено успішно: {successCount} з {fileNames.Length}");
}
catch (Exception ex)
{
    // Сюди потрапить лише те, чого внутрішній catch не спіймав
    Console.WriteLine($"Критична помилка обробки: {ex.Message}");
}
```

**Вивід:**

```
Починаємо обробку файлів...
a.txt: 143 символів
b.txt: файл відсутній, пропускаємо
c.txt: 27 символів
Оброблено успішно: 2 з 3
```

Внутрішній `try` — це «дрібний ремонт на місці», зовнішній — «щось пішло
зовсім не так». Логіка та сама, що й у розкручуванні стека: виняток шукає
найближчий відповідний `catch`, і внутрішній ближчий.

:::warning Обережно
Не захоплюйтесь. Три-чотири рівні вкладених `try` роблять код нечитабельним.
Якщо вам здається, що потрібен четвертий рівень — швидше за все, шматок
логіки просто просить окремого методу.
:::

## Найгірша практика: порожній catch

:::danger Ніколи так не робіть

```csharp
try
{
    // сто рядків важливої логіки
}
catch { }        // ← ось це
```

Такий код називають *exception swallowing* — «ковтання винятків». Він робить
рівно одне: гарантує, що ви **ніколи не дізнаєтесь**, що програма зламалась.
:::

Чому це гірше, ніж просто падіння програми:

1. **Помилка нікуди не поділась** — ви лише вимкнули сигналізацію.
   Дані не збереглися, файл не записався, а програма радісно повідомляє
   «готово».
2. **Слідів не залишилось.** Немає ні повідомлення, ні лога, ні стек-трейсу.
   Наступного разу ви шукатимете причину годинами.
3. **Помилка вилізе пізніше і в іншому місці.** Замість зрозумілого
   `FileNotFoundException` під час запису ви отримаєте загадковий
   `NullReferenceException` через двісті рядків.

Класичний сюжет: студент пише калькулятор, обгортає все у `try { } catch { }`,
програма «працює», але для введення `abc` мовчки показує `0`. Викладач питає
чому — і відповіді немає, бо її зжерли.

**Як правильно.** Мінімум — сказати вголос:

```csharp
catch (Exception ex)
{
    Console.WriteLine($"Помилка: {ex.Message}");
}
```

Краще — сказати конкретно і зробити щось осмислене:

```csharp
catch (FileNotFoundException)
{
    Console.WriteLine("Файл налаштувань відсутній, використовую значення за замовчуванням.");
    settings = GetDefaultSettings();
}
```

:::note
Порожній `catch` виправданий рівно в одній ситуації: коли операція
за своєю природою «необов'язкова», ви це **свідомо** вирішили і **написали
коментар**, чому саме.

```csharp
try
{
    File.Delete(tempFile);
}
catch (IOException)
{
    // Тимчасовий файл не видалився — не критично, ОС прибере його сама.
}
```

Різниця між цим і `catch { }` — у тому, що тут видно рішення, а не лінощі.
:::

## Скільки коштує виняток

Ще одна причина не використовувати винятки як звичайний `if`.

Кинути й спіймати виняток — операція **дуже дорога** порівняно зі звичайним
кодом: треба створити об'єкт, зібрати стек-трейс, розкрутити стек, знайти
обробник. За різними вимірами це у сотні або тисячі разів повільніше
за перевірку `if`.

```csharp
// ПОГАНО: використовуємо винятки для звичайної перевірки
foreach (string s in inputs)
{
    try
    {
        int n = int.Parse(s);
        sum += n;
    }
    catch (FormatException) { /* не число — пропускаємо */ }
}

// ДОБРЕ: перевіряємо без винятків
foreach (string s in inputs)
{
    if (int.TryParse(s, out int n))
    {
        sum += n;
    }
}
```

На десяти рядках різниці не помітите. На мільйоні — перший варіант
працюватиме секунди, а другий — мілісекунди. Але головна причина навіть
не швидкість: другий варіант просто **зрозуміліший**. Про це докладно —
у наступному підрозділі.

:::tip Порада
Мнемоніка: виняток — це пожежна сигналізація, а не дверний дзвінок.
Нею користуються, коли справді щось горить, а не щоб покликати сусіда.
:::

## Типові помилки

**1. Оголосити змінну всередині `try` і використати після нього.**

```csharp
try
{
    int result = 100 / divisor;
}
catch (DivideByZeroException) { }

Console.WriteLine(result);   // помилка компіляції: result тут не існує
```

Змінна живе тільки у своєму блоці. Оголошуйте її **до** `try`:

```csharp
int result = 0;
try { result = 100 / divisor; }
catch (DivideByZeroException) { Console.WriteLine("Ділення на нуль"); }
Console.WriteLine(result);
```

**2. Ставити `catch (Exception)` першим.**
Компілятор не дасть (`CS0160`), але сама ідея «спочатку загальний» вказує
на нерозуміння. Порядок — від конкретного до загального.

**3. Обгортати винятком половину програми.**

```csharp
try
{
    // 200 рядків
}
catch (Exception) { Console.WriteLine("Щось пішло не так"); }
```

Ви не знаєте, що саме зламалось, і користувач теж. Блок `try` має бути
маленьким — рівно навколо того, що справді може впасти.

**4. Писати `throw ex;` замість `throw;`.**
Втрачається стек-трейс. Це не стилістична дрібниця, а реальна втрата
інформації про місце помилки.

**5. Забувати, що `catch` не «повторює» `try`.**
Після обробки виконання йде **далі**, а не назад у `try`. Щоб повторити
спробу, потрібен цикл — як у прикладі з `when (attempt < 3)`.

## Що далі

Ми навчилися ловити винятки. Але половина мистецтва — навчитися їх **не
допускати**: перевіряти дані до того, як вони зламають програму. У наступному
підрозділі — як кидати винятки самому, як влаштована ієрархія класів винятків
і, найголовніше, як писати введення, яке неможливо зламати.
