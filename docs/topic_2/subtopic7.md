# Компіляція та виконання програми

Процесор не розуміє C#. Він розуміє лише машинний код — послідовності байтів,
специфічні для конкретної архітектури. Перетворення тексту програми на щось,
що процесор виконає, називається **компіляцією**.

У C# цей шлях незвичний: він проходить у **два етапи**, і саме завдяки цьому
одна й та сама програма працює на Windows, Linux і macOS.

## Крок 1: C# → проміжний код (IL)

Коли ви натискаєте «Побудувати» у Visual Studio, компілятор **Roslyn**:

1. **Перевіряє синтаксис** — чи не порушені правила мови (забута `;`, незакрита дужка).
2. **Перевіряє типи** — чи не присвоюєте ви рядок цілому числу.
3. **Перекладає код** у **IL** (Intermediate Language, проміжна мова).
4. **Створює метадані** — опис усіх типів, методів і полів програми.
5. **Пакує результат** у **збірку** — файл `.exe` або `.dll`.

:::info[Що таке IL]
IL — це асемблер для уявного процесора, якого не існує в залізі. Він не прив'язаний
ні до x86, ні до ARM. Саме тому одна збірка працює на різних платформах:
під конкретний процесор код перекладається пізніше, вже на місці.
:::

Ось як виглядає IL для рядка `Console.WriteLine("Привіт!")`:

```
ldstr      "Привіт!"
call       void [System.Console]System.Console::WriteLine(string)
ret
```

Читати це не потрібно — важливо лише розуміти, що у `.exe` лежить **не** машинний
код, а ось такий проміжний.

## Крок 2: IL → машинний код (JIT)

Коли програму запускають, у справу вступає **CLR** (Common Language Runtime) —
середовище виконання .NET:

1. **Завантажує збірку** в пам'ять.
2. Коли метод викликається **вперше**, **JIT-компілятор** (Just-In-Time) перекладає
   його IL у машинний код цього конкретного процесора.
3. **Кешує** результат: при наступних викликах метод уже скомпільований і
   виконується напряму.
4. **Оптимізує** код під конкретне залізо.

:::tip[Чому JIT може бути швидшим за звичайну компіляцію]
Компілятор C++ створює код, що має працювати на будь-якому процесорі — отже,
орієнтується на найстаріший. JIT компілює на машині користувача і **знає**, який
там процесор, тому може використати сучасні інструкції. Звідси парадокс: попри
накладні витрати, .NET-код іноді випереджає заздалегідь скомпільований.
:::

## Чому програма «гальмує» перші секунди

Перший виклик кожного методу вимагає JIT-компіляції — звідси помітна затримка
під час запуску великих застосунків. Далі все працює на повній швидкості,
бо код уже скомпільований і закешований.

Це називають **проблемою холодного старту**, і для її вирішення існує AOT.

## AOT-компіляція

**AOT** (Ahead-of-Time) — компіляція IL у машинний код **заздалегідь**, до запуску.

| | JIT | AOT |
|---|-----|-----|
| Коли компілюється | Під час виконання | При побудові |
| Швидкість запуску | Повільніша | Швидка |
| Оптимізація під залізо | Так | Ні |
| Розмір файлу | Менший | Більший |
| Кросплатформність збірки | Так | Ні — під кожну платформу окремо |

AOT застосовують там, де критичний швидкий старт: мобільні застосунки,
хмарні функції, утиліти командного рядка.

## Роль CLR

CLR — це не лише JIT-компілятор, а повноцінна віртуальна машина, що відповідає за:

| Функція | Що робить |
|---------|-----------|
| Виконання коду | JIT-компіляція і запуск |
| Керування пам'яттю | Збирач сміття |
| Безпека типів | Перевірка коректності операцій під час виконання |
| Обробка винятків | Механізм `try/catch` — тема 14 |
| Керування потоками | Багатопотоковість — теми 29–32 |

Саме CLR абстрагує програму від операційної системи, і саме тому .NET
кросплатформний.

## Збірка (Assembly)

**Збірка** — результат компіляції, файл `.exe` або `.dll`.

| Розширення | Що це | Як запускається |
|------------|-------|-----------------|
| `.exe` | Застосунок із точкою входу `Main` | Запускається самостійно |
| `.dll` | Бібліотека класів | Підключається до інших проєктів |

Збірка містить IL-код, метадані та ресурси (зображення, тексти).

:::note[Чому чужий .NET-код легко «розібрати»]
Оскільки у збірці лежить IL із повними метаданими, спеціальні програми
(наприклад, ILSpy) відновлюють із неї читабельний код на C#, дуже близький
до оригіналу. Для захисту комерційного коду використовують **обфускатори** —
інструменти, що навмисно роблять імена й структуру нечитабельними.
:::

## Повна картина

```
   Program.cs  (ваш код на C#)
        │
        │  Компілятор Roslyn  — перевірка синтаксису й типів
        ▼
   MyApp.exe  (IL-код + метадані)      ← кросплатформний файл
        │
        │  CLR запускає, JIT компілює по методу
        ▼
   Машинний код                        ← під конкретний процесор
        │
        ▼
   Виконання процесором
```

## Помилки на різних етапах

Розуміння етапів допомагає читати помилки:

| Коли виникає | Вид помилки | Приклад |
|--------------|-------------|---------|
| Компіляція | Синтаксична, типів | `; expected`, `Cannot convert string to int` |
| Виконання | Виняток | `DivideByZeroException`, `NullReferenceException` |
| Не виникає сама | Логічна | Програма працює, результат неправильний |

Це рівно та класифікація помилок, яку ми ввели в темі 1 — тепер зрозуміло,
чому вони виявляються в різні моменти.

## Висновок

- Компіляція в C# **двоетапна**: спочатку C# → **IL**, потім під час виконання
  IL → **машинний код** через **JIT**.
- У файлі `.exe` лежить **IL, а не машинний код** — саме тому .NET кросплатформний.
- **CLR** — віртуальна машина, що виконує код, керує пам'яттю, типами й винятками.
- **JIT** компілює кожен метод при першому виклику й кешує результат — звідси
  затримка на старті.
- **AOT** компілює заздалегідь: швидший запуск, але збірка втрачає кросплатформність.
- **Збірка** (`.exe`/`.dll`) містить IL, метадані й ресурси.
