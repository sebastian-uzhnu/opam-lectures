# Керування пам'яттю та збирач сміття

Ця тема — одна з причин, чому C# вважають зручнішим за C++. Щоб зрозуміти, у чому
саме зручність, треба спершу побачити задачу, яку вона розв'язує.

## Проблема: хто прибирає за програмою

Коли програма створює об'єкт, під нього виділяється пам'ять. Коли об'єкт більше
не потрібен, пам'ять треба звільнити — інакше вона накопичуватиметься, і врешті
програма вичерпає доступну пам'ять. Це називають **витоком пам'яті** (memory leak).

Історично було два підходи:

| Підхід | Мова | Як працює | Ціна |
|--------|------|-----------|------|
| Ручний | C, C++ | Програміст сам викликає звільнення | Забув звільнити — витік. Звільнив двічі — аварія |
| Автоматичний | C#, Java, Python | Середовище саме знаходить непотрібне | Невеликі непередбачувані паузи |

C# обрав другий шлях. Механізм, що цим займається, називається **збирачем сміття**
(Garbage Collector, GC).

## Де взагалі зберігаються дані

Пам'ять програми поділена на дві області з різними правилами.

### Стек (Stack)

- зберігає локальні змінні значимих типів і параметри методів;
- працює за принципом «останній прийшов — перший пішов»;
- звільняється **автоматично**, щойно метод завершився;
- дуже швидкий, але невеликий (близько 1 МБ).

### Купа (Heap)

- зберігає об'єкти посилальних типів, створені через `new`;
- розмір обмежений лише оперативною пам'яттю;
- повільніша за стек;
- **саме тут працює збирач сміття**.

```csharp
void Example()
{
    int number = 42;                    // значення — у стеку
    int[] data = new int[1000];         // посилання у стеку, сам масив — у купі

}   // метод завершився: number зник разом зі стеком,
    // масив у купі залишився, доки до нього є посилання
```

:::note
Детально стек і купа розглядаються в темі 3 разом зі значимими й посилальними
типами. Тут достатньо розуміти, що GC працює **тільки з купою**.
:::

## Як GC визначає, що об'єкт більше не потрібен

Ключове поняття — **досяжність**. Об'єкт потрібен, якщо до нього можна дістатися
ланцюжком посилань від «коренів»: локальних змінних активних методів, статичних полів,
регістрів процесора.

```csharp
var person = new Person("Олена");   // об'єкт досяжний через змінну person
person = null;                      // посилання зникло — об'єкт став недосяжним
                                    // тепер GC може його зібрати
```

Алгоритм має назву **Mark-and-Sweep** («познач і підмети») і працює у два кроки:

1. **Mark** — GC обходить усі корені й позначає кожен досяжний об'єкт як «живий».
2. **Sweep** — усе, що не позначене, вважається сміттям, і його пам'ять звільняється.

Після цього виконується **компактування**: живі об'єкти зсуваються докупи, щоб
не залишалося «дірок» вільної пам'яті між ними.

:::tip[Чому не рахувати посилання]
Простіший підхід — рахувати, скільки посилань веде на об'єкт, і звільняти при нулі.
Він ламається на **циклічних посиланнях**: два об'єкти посилаються один на одного,
лічильники ненульові, але ззовні до них ніхто не дістанеться. Mark-and-Sweep
цю проблему не має, бо орієнтується на досяжність від коренів, а не на лічильники.
:::

## Покоління

Обходити всю купу щоразу — дорого. GC використовує спостереження: **більшість
об'єктів живуть дуже недовго** (створили в методі, метод завершився — об'єкт уже
не потрібен).

Тому купа поділена на три **покоління**:

| Покоління | Що містить | Як часто перевіряється |
|-----------|-----------|------------------------|
| **Gen 0** | Щойно створені об'єкти | Найчастіше — швидка перевірка |
| **Gen 1** | Ті, що пережили одне збирання | Рідше |
| **Gen 2** | Довгожителі | Найрідше — найдорожча перевірка |

Об'єкт, що пережив збирання в Gen 0, переводиться в Gen 1, потім у Gen 2.
Оскільки більшість «помирає» молодими, часта перевірка лише Gen 0 прибирає
основну масу сміття дешево.

## Коли запускається GC

- коли в купі бракує місця для нового об'єкта;
- коли обсяг виділеної пам'яті перевищив поріг;
- за явним викликом `GC.Collect()`.

:::warning
`GC.Collect()` викликати вручну **не треба**. Збирач знає про стан пам'яті більше
за вас, а примусовий виклик спричиняє повну зупинку програми й зазвичай погіршує
продуктивність. Це один з тих випадків, коли найкраща дія — не робити нічого.
:::

## Чого GC не вміє

Збирач сміття керує **керованою** пам'яттю .NET. Він нічого не знає про ресурси
операційної системи: відкриті файли, мережеві з'єднання, підключення до баз даних.

Для них використовують конструкцію `using`, яка гарантовано звільняє ресурс
при виході з блока:

```csharp
using (var reader = new StreamReader("data.txt"))
{
    string text = reader.ReadToEnd();
    Console.WriteLine(text);
}   // файл гарантовано закрито тут — навіть якщо сталася помилка
```

Детально роботу з файлами розглянемо в темі 13.

## Переваги й недоліки автоматичного керування

**Переваги:**

- програміст не витрачає час на ручне звільнення пам'яті;
- неможливі цілі класи помилок: подвійне звільнення, звернення до звільненої пам'яті;
- витоки пам'яті трапляються значно рідше.

**Недоліки:**

- **непередбачувані паузи**: під час збирання програма ненадовго зупиняється;
- більше споживання пам'яті: сміття лежить у купі до наступного збирання;
- менший контроль — не можна точно сказати, коли об'єкт буде знищено.

:::info[Де це має значення]
Для звичайних застосунків паузи GC (частки мілісекунди) непомітні. Але у відеоіграх,
де кадр має вкластися у 16 мс, пауза GC викликає «підвисання» картинки. Тому
розробники на Unity спеціально пишуть код так, щоб створювати менше сміття.
:::

## Що з цього треба запам'ятати зараз

Ви не будете керувати GC у цьому курсі — у цьому й сенс автоматичного керування.
Практичних висновків для вас рівно три:

1. Створені об'єкти звільняються **самі** — про це не треба думати.
2. `GC.Collect()` вручну не викликати.
3. Для файлів і з'єднань використовувати `using` — GC їх не прибере.

## Висновок

- **Стек** зберігає локальні значення й звільняється автоматично при виході
  з методу; **купа** зберігає об'єкти, і саме в ній працює GC.
- Об'єкт вважається сміттям, коли він **недосяжний** від коренів — а не коли
  на нього немає посилань за лічильником.
- Алгоритм **Mark-and-Sweep** позначає живі об'єкти й звільняє решту, після чого
  виконується компактування.
- **Покоління** (Gen 0/1/2) дозволяють часто перевіряти молоді об'єкти дешево,
  бо більшість із них живуть недовго.
- GC не звільняє **некеровані ресурси** — файли й з'єднання закривають через `using`.
- Головна ціна автоматичного керування — **непередбачувані короткі паузи**.
